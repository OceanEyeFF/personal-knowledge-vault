# 维护指南

> 项目：Personal Knowledge Vault (PKV)
> 适用版本：当前主线
> 最后更新：2026-08-21
> 维护目标：稳定、可恢复、可验证、可持续演进

---

## 1. 当前维护视角

维护 PKV 时，应该把它看作一套：

- 本地优先的知识底座
- 同时服务 CLI、MCP 与外部 Wrapper 的系统
- 以 Markdown 为事实源、SQLite 与向量索引为辅助层的架构

维护重点不是只盯某个入口，而是确保以下三件事持续成立：

1. 数据主存储完整可读
2. 索引层可恢复
3. CLI、MCP 与 Kernel 公共接口不会彼此漂移

### 1.1 当前路径合同

`<effective-data-root>` 按下列优先级解析，所有“生产数据根”表述都指这个最终单一根：

```text
PKV_DATA_ROOT（若设置）
  → %USERPROFILE%\.pkv\config.yaml 中的 storage.data_root
  → %USERPROFILE%\.pkv\data
```

- `%USERPROFILE%\.pkv\config.yaml` 是唯一可编辑的用户业务配置，可能含 Provider Key/Cookie。
- `<effective-data-root>/config/local.yaml` 是 PKV 管理、无敏感字段的 runtime snapshot，不是业务配置、不会 merge 到 `Config`，也不得手工改写。
- `PKV_DATA_ROOT` 与 `PKV_LOG_LEVEL` 是仅有的正式产品环境覆盖；`DATA_DIR`、`LOG_LEVEL` 等旧变量仅是 `PKV_TEST_OFFLINE=1` 下的测试注入，不是用户配置接口。
- checkout 中旧 `.data/`、旧 `config/local.yaml`，以及 held release candidate 的 `%LOCALAPPDATA%\PersonalKnowledgeVault` 仅是历史用户资产/证据。系统、脚本与维护者都不得自动迁移、接管、复制或删除它们；只有用户走 inspect → plan → 展示影响与备份 → 确认 → execute → smoke test 后才能处理。

## 2. 系统架构速览

### 2.1 当前入口

- `CLI`：`python -m src.cli.commands --help`（checkout 开发入口；任何指向用户数据根的实际操作都只能由用户授权执行）
- `MCP`：`python -m src.mcp`（stdio；同样不得由 Agent 指向用户数据根）

桌面 GUI 位于独立的 `pkv-GUI` 仓库，只通过 `pkv_kernel` 使用核心能力。

### 2.2 当前核心模块

- `src/workflow/`：工作流编排
- `src/processors/`：内容解析
- `src/retrieval/`：检索引擎
- `src/storage/`：Markdown / SQLite / 向量索引
- `src/ai/`：摘要、标签、Embedding
- `src/mcp/`：AI Agent 接口层

### 2.3 当前存储事实

- `Markdown`：主存储
- `SQLite`：元数据与 FTS5 索引
- `hnswlib`：向量索引

维护原则：

- Markdown 优先级最高
- SQLite 与向量索引可重建

## 3. 日常维护建议

### 3.1 每日或高频检查

- 查看日志是否有持续错误
- 确认归档是否正常写入 `<effective-data-root>/vault/`（只由用户检查；Agent 不读取）
- 确认 SQLite 未出现锁冲突
- 确认 MCP / CLI 中至少一个入口能正常读到数据

### 3.2 每周检查

- 数据库完整性检查
- 数据目录备份
- 日志体积检查
- 向量索引目录体积和文件完整性检查
- 由用户核对 `%USERPROFILE%\.pkv\config.yaml` 的预期变更与安全保管；不要把它放入 checkout 或 Git
- 仅核对 `<effective-data-root>/config/local.yaml` 的 runtime-validation 状态；它是 PKV 管理的 snapshot，不是可编辑配置

### 3.3 每次升级后

- 运行环境验证脚本
- 运行最小功能回归
- 核对数据库迁移是否执行
- 检查文档是否与当前入口和目录保持一致

## 4. 常用命令与脚本

### 4.1 环境初始化与验证

```powershell
.\scripts\setup-conda.ps1
.\scripts\test-conda.ps1
```

这些是 checkout 的本地开发环境入口，不是用户数据初始化、旧目录迁移或 release 操作。它们不得自动接管历史 checkout/release 目录；Agent 不以它们访问用户 profile、用户数据根或 Provider 凭据。

也可以手动执行：

```bash
python src/utils/verify_setup.py
```

### 4.2 数据库迁移

`run-test.ps1` 会显式拒绝 `scripts/migrate.py` 并以 exit 2 结束，不能用 FT7 Direct Python 绕过。FT7 只为仓库内 `-m`/`.py` 的 CAT-0 离线任务提供防护，不授权数据库迁移，更不授权真实数据操作。

默认自动化仅在 pytest 创建的一次性临时 SQLite 上验证迁移逻辑：

```powershell
.\scripts\run-test.ps1 -Direct -DataRoot .data-test\maintenance-migration -Command @("pytest", "tests/unit/test_migration_health_check.py", "tests/unit/test_migration_manager_additional.py", "tests/unit/test_migration_manager_runtime.py", "tests/unit/test_migration_manager_versions.py", "tests/integration/test_relations_migration.py", "tests/integration/test_review_migration.py")
```

真实快照迁移尚未执行，仍需 FT5、U1/G8 和用户明确授权。批准后也只能对从只读快照制作的一次性可写 clone 执行；原始快照保持只读。未设置路径覆盖的裸迁移命令仅是人工维护 API，可能操作生产 `<effective-data-root>/`，不是可复制的 Agent/默认自动化流程。

### 4.3 备份与恢复

可用脚本：

- `scripts/backup.ps1`
- `scripts/backup-data.ps1`
- `scripts/restore-data.ps1`

### 4.4 测试

可用脚本：

- `scripts/run-test.ps1`：将数据库、Vault、向量、日志和临时目录锁定到 `.data-test/`，不创建或加载 `.env.test`；这是受控路径与 Python 进程防护，不是 OS sandbox

例如：

```powershell
.\scripts\run-test.ps1 -DataRoot .data-test\maintenance stats
```

包装器固定 `PKV_RUN_LIVE=0` 并清理凭据/代理；`PKV_RUN_LIVE` 只是 pytest 收集开关，不能授权或开启应用网络。真实 LLM / Embedding 验证仍受 U1/G8 与用户授权阻塞，当前默认自动化不执行。

pytest 等非 CLI 命令必须通过 `-Direct` 运行，并使用显式的 `-Command @("executable", "arg", ...)` 数组：

```powershell
.\scripts\run-test.ps1 -Direct -DataRoot .data-test\maintenance-pytest -Command @("pytest")
```

仓库内普通 `-m`/`.py` Direct Python 任务还受 FT7 CAT-0 限制；该能力不改变 `scripts/migrate.py` 的 exit 2 denylist。

## 5. 数据维护

### 5.1 目录结构

默认运行时目录（未设置 `PKV_DATA_ROOT` 时）：

```text
%USERPROFILE%\.pkv\
├── config.yaml                         # 唯一可编辑的用户业务配置
└── data/                               # <effective-data-root>
    ├── config/local.yaml               # PKV 管理的 secret-free runtime snapshot
    ├── db/
    ├── logs/
    ├── tmp/
    ├── vault/
    ├── vectors/
    ├── backups/
    └── runtime/
```

关键说明：

- `<effective-data-root>/vault/` 是主存储
- `<effective-data-root>/db/knowledge_vault.db` 是 SQLite 主库
- `<effective-data-root>/vectors/` 保存向量索引
- `<effective-data-root>/logs/` 保存日志
- `<effective-data-root>/config/local.yaml` 只保存无密钥 runtime snapshot；若它与用户配置和当前数据库构建契约不一致，应提示用户评估重建 Embedding，而不是手工编辑 snapshot。

### 5.2 数据一致性原则

- Markdown 是事实源
- SQLite 与向量索引应被视为可恢复层
- 遇到索引异常时，不要先怀疑 Markdown 数据损坏

### 5.3 SQLite 健康检查

AI/自动化默认只检查测试库：

```powershell
sqlite3 .data-test/db/knowledge_vault.db "PRAGMA integrity_check;"
sqlite3 .data-test/db/knowledge_vault.db "PRAGMA foreign_key_check;"
```

以下生产库检查必须取得用户明确授权并由用户执行；AI 不执行。`<effective-data-root>` 需要先按 1.1 解析，不得把 checkout 旧 `.data/` 当作默认目标：

```powershell
sqlite3 <effective-data-root>\db\knowledge_vault.db "PRAGMA integrity_check;"
sqlite3 <effective-data-root>\db\knowledge_vault.db "PRAGMA foreign_key_check;"
```

### 5.4 VACUUM 与 REINDEX

这两项会写入生产数据库。执行前必须由用户确认备份并明确授权；AI 不执行。

```powershell
sqlite3 <effective-data-root>\db\knowledge_vault.db "VACUUM;"
sqlite3 <effective-data-root>\db\knowledge_vault.db "REINDEX;"
```

适用场景：

- 大量删除后释放空间
- 索引性能异常
- 怀疑索引状态不一致

### 5.5 从主存储重建索引

当 SQLite 或向量索引损坏时，建议思路是：

1. 先备份 `<effective-data-root>/`
2. 确认 `<effective-data-root>/vault/` 完整
3. 删除损坏的索引层
4. 重新初始化数据库和向量索引
5. 从 Markdown 重新导入

如果是数据库 schema 变更，先按 4.2 的门禁完成迁移验证；真实数据迁移必须另行取得明确授权，再考虑重建。

## 6. 日志维护

### 6.1 默认位置

- `<effective-data-root>/logs/pkv.log`

### 6.2 日志级别

主要受以下因素影响：

- CLI 启动参数
- `PKV_LOG_LEVEL` 环境变量（正式产品覆盖）
- `%USERPROFILE%\.pkv\config.yaml` 中的日志设置（仅用户维护）

### 6.3 维护建议

- 高频错误先看最近滚动日志
- 排查归档失败时，同时看 workflow、processor、storage 相关日志
- MCP 问题同时检查服务日志与客户端调用上下文
- GUI 问题优先区分是界面层异常还是底层服务异常

## 7. 入口专项维护

### 7.1 CLI

重点关注：

- 命令参数是否变化
- 输出是否仍与 SQLite / Markdown 结构匹配
- 审核流程是否与工作流配置一致

### 7.2 MCP

重点关注：

- `src/mcp/tools.py` 与底层接口是否对齐
- 参数边界与序列化是否稳定
- MCP 文档是否仍与当前 Tool 集合一致

当前维护提醒：

- MCP 已是一等能力
- 文档和接口漂移会直接影响 AI Agent 使用效果

### 7.3 GUI

GUI 位于独立的 `pkv-GUI` 仓库，不属于本仓库的模块、测试 lane 或封包入口。未来
Wrapper 只能依赖 `pkv_kernel` 的稳定公开接口，不能 import `src.*`；共享数据根时遵循
单写者/多读者合同，不自行派生第二个数据根。

## 8. 配置维护

### 8.1 配置来源

应用配置统一使用 YAML，但业务配置与 runtime snapshot 严格分层：

1. `config/config.yaml` 是 bundled、版本化的非敏感默认值。
2. `%USERPROFILE%\.pkv\config.yaml` 是唯一可编辑的用户覆盖配置和凭据位置；它不进入 Git，也不由 Agent 读取。
3. `PKV_DATA_ROOT` 覆盖用户配置的 `storage.data_root`，`PKV_LOG_LEVEL` 覆盖日志级别；两者是仅有的正式产品环境变量。
4. `<effective-data-root>/config/local.yaml` 是 PKV 管理的无敏感 runtime snapshot，不 merge 到 `Config`、不作为凭据来源，也不手工编辑。
5. 代码默认值仅用于未配置项；`storage.data_dir` 仅保留只读弃用兼容。

不要再创建或加载 `.env` 来配置 LLM、Embedding 或处理器。`DATA_DIR`、细粒度子路径变量与 `LOG_LEVEL` 只在 `PKV_TEST_OFFLINE=1` 的测试包装器内兼容。`PKV_RUN_LIVE=1` 仅是 user-only 测试收集开关，不是网络授权；CAT-0 wrapper 会强制重置为 `0`。改变 data root 不能借 `reload` 直接生效，必须走 inspect → plan → 展示影响与备份 → 用户确认 → execute → smoke test。

### 8.2 关键配置项

- 存储路径
- 日志目录与级别
- LLM 配置（`ai.llm.base_url`、`ai.llm.api_key`、`ai.llm.model`）
- Embedding 配置（`ai.embedding.base_url`、`ai.embedding.api_key`、`ai.embedding.model`、`ai.embedding.dim`）
- Embedding 模型与维度
- 检索参数

Embedding 端点、模型与维度维护要点：

- `ai.embedding.base_url`、`ai.embedding.model` 和 `ai.embedding.dim` 共同决定向量索引契约，不建议随意更换
- `ai.embedding.dim` 可设置为显式整数，也可设置为 `auto`
- `auto` 模式下，系统会在第一次成功调用 Embedding 接口后锁定真实维度
- 锁定结果会持久化到 `<effective-data-root>/runtime/embedding_dim.json`，重启后会优先复用
- 某些本地 OpenAI-compatible 服务会忽略 `dimensions` 参数，此时应优先使用 `auto`
- 一旦实际端点、模型或维度变化，runtime snapshot 应报告契约不一致；由用户决定并确认索引重建，重新生成文档级和分块级 Embedding
- 即使新旧模型维度相同，向量语义空间也可能不同，旧索引结果不再可信
- 新建索引会在元数据中记录非敏感契约指纹；后续加载时若发现端点、模型或维度不一致，会拒绝复用旧索引
- 老索引如果缺少契约指纹，系统会兼容加载并输出告警；维护者应尽快确认当前 Embedding 配置是否仍与旧索引一致

### 8.3 维护建议

- 修改 API Key 后由用户重启相关入口
- 修改路径配置前由用户先备份；换根只可经 inspect → plan → 展示影响与备份 → 确认 → execute → smoke test
- 调整检索参数时要有最小回归验证
- 修改 `ai.embedding.base_url`、`ai.embedding.model` 或 `ai.embedding.dim` 后，应按索引迁移处理，不要直接复用旧索引
- 如果服务端真实返回维度与历史索引不一致，可先切回旧的 Embedding 服务/模型/维度配置继续使用旧索引
- 如果确认切换到新模型或新维度，用户应先确认影响与备份，再清理并重建向量索引、重新生成 Embedding、执行检索或回填；不得通过手改 runtime snapshot 规避检查

## 9. 备份与恢复建议

### 9.1 推荐备份范围

- `<effective-data-root>/`（Vault、数据库、vectors、runtime、logs 与 backups）
- `%USERPROFILE%\.pkv\config.yaml`（包含本机凭据，应由用户单独加密备份，绝不能提交到 Git）
- 所用 bundled `config/config.yaml` 与版本化工作流配置的版本标识

### 9.2 恢复顺序建议

1. 停止运行中的 CLI / MCP / GUI
2. 恢复 `<effective-data-root>/`
3. 校验 SQLite 完整性
4. 必要时重建向量索引
5. 启动 CLI 做最小读写验证
6. 再验证 MCP 和 GUI

### 9.3 备份后验证

建议至少做以下检查：

- 打开 1-2 个 Markdown 文件确认可读
- SQLite `integrity_check`
- 进行一次搜索
- 读取一条详情

## 10. 文档维护也是系统维护的一部分

当前项目文档分层已经明确：

- `docs/overview/`：当前核心文档
- `docs/modules/`：模块设计细节
- `docs/specs/`：接口与规范
- `docs/history/`：里程碑、讨论与历史执行文档

维护原则：

- 不再把 `docs/history/prompts/` 当作当前路线真相源
- 当前路线以 `README.md` 和 `docs/overview/` 为准
- 每次重大方向变化后，优先更新核心文档，而不是继续累积历史 Prompt

---

## 11. 当前最值得维护者关注的风险

1. 文档比代码更旧，导致后续开发继续按错误路径推进
2. MCP 接口文档与底层实现漂移，影响 AI Agent 使用
3. GUI 演化出与 CLI/MCP 不一致的数据理解
4. 关系层未建立前，高阶功能被误写成表面包装
5. `ai.embedding.dim: auto` 会复用 `<effective-data-root>/runtime/embedding_dim.json` 中的历史维度缓存；如果底层 Embedding 服务或模型已切换，runtime snapshot/索引契约会提示不一致。维护者必须由用户确认是否重建，不能手改 snapshot 或自动搬迁旧索引

---

## 12. 一句话总结

维护 PKV 的核心不是只保证程序能跑，而是保证 **Markdown 主存储、索引可重建、三入口一致、文档不过时** 这四件事持续成立。
