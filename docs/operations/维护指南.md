# 维护指南

> 项目：Personal Knowledge Vault (PKV)
> 适用版本：当前主线
> 最后更新：2026-03-06
> 维护目标：稳定、可恢复、可验证、可持续演进

---

## 1. 当前维护视角

维护 PKV 时，应该把它看作一套：

- 本地优先的知识底座
- 同时服务 CLI、MCP、GUI 的系统
- 以 Markdown 为事实源、SQLite 与向量索引为辅助层的架构

维护重点不是只盯某个入口，而是确保以下三件事持续成立：

1. 数据主存储完整可读
2. 索引层可恢复
3. 三个入口不会彼此漂移

---

## 2. 系统架构速览

### 2.1 当前入口

- `CLI`：`python src/main.py --help`
- `MCP`：`python -m src.mcp`
- `GUI`：`python -m src.gui`

### 2.2 当前核心模块

- `src/workflow/`：工作流编排
- `src/processors/`：内容解析
- `src/retrieval/`：检索引擎
- `src/storage/`：Markdown / SQLite / 向量索引
- `src/ai/`：摘要、标签、Embedding
- `src/mcp/`：AI Agent 接口层
- `src/gui/`：桌面工作台

### 2.3 当前存储事实

- `Markdown`：主存储
- `SQLite`：元数据与 FTS5 索引
- `hnswlib`：向量索引

维护原则：

- Markdown 优先级最高
- SQLite 与向量索引可重建

## 3. 日常维护建议

### 3.1 每日或高频检查

- 查看日志是否有持续错误
- 确认归档是否正常写入 `.data/vault/`
- 确认 SQLite 未出现锁冲突
- 确认 MCP / GUI / CLI 中至少一个入口能正常读到数据

### 3.2 每周检查

- 数据库完整性检查
- 数据目录备份
- 日志体积检查
- 向量索引目录体积和文件完整性检查
- 核对配置文件与 `.env` 是否有变更

### 3.3 每次升级后

- 运行环境验证脚本
- 运行最小功能回归
- 核对数据库迁移是否执行
- 检查文档是否与当前入口和目录保持一致

## 5. 数据维护

### 5.1 目录结构

默认运行时目录：

```text
.data/
├── db/
├── logs/
├── tmp/
├── vault/
└── vectors/
```

关键说明：

- `.data/vault/` 是主存储
- `.data/db/knowledge_vault.db` 是 SQLite 主库
- `.data/vectors/` 保存向量索引
- `.data/logs/` 保存日志

### 5.2 数据一致性原则

- Markdown 是事实源
- SQLite 与向量索引应被视为可恢复层
- 遇到索引异常时，不要先怀疑 Markdown 数据损坏

### 5.3 SQLite 健康检查

建议定期执行：

```powershell
sqlite3 .data/db/knowledge_vault.db "PRAGMA integrity_check;"
sqlite3 .data/db/knowledge_vault.db "PRAGMA foreign_key_check;"
```

### 5.4 VACUUM 与 REINDEX

```powershell
sqlite3 .data/db/knowledge_vault.db "VACUUM;"
sqlite3 .data/db/knowledge_vault.db "REINDEX;"
```

适用场景：

- 大量删除后释放空间
- 索引性能异常
- 怀疑索引状态不一致

### 5.5 从主存储重建索引

当 SQLite 或向量索引损坏时，建议思路是：

1. 先备份 `.data/`
2. 确认 `.data/vault/` 完整
3. 删除损坏的索引层
4. 重新初始化数据库和向量索引
5. 从 Markdown 重新导入

如果是数据库 schema 变更，先执行迁移脚本，再考虑重建。

## 6. 日志维护

### 6.1 默认位置

- `.data/logs/pkv.log`

### 6.2 日志级别

主要受以下因素影响：

- CLI 启动参数
- `LOG_LEVEL` 环境变量
- `config/config.yaml`

### 6.3 维护建议

- 高频错误先看最近滚动日志
- 排查归档失败时，同时看 workflow、processor、storage 相关日志
- MCP 问题同时检查服务日志与客户端调用上下文
- GUI 问题优先区分是界面层异常还是底层服务异常

## 7. 入口专项维护

### 7.1 CLI

重点关注：

- 命令参数是否变化
- 输出是否仍与 SQLite / Markdown 结构匹配
- 审核流程是否与工作流配置一致

### 7.2 MCP

重点关注：

- `src/mcp/tools.py` 与底层接口是否对齐
- 参数边界与序列化是否稳定
- MCP 文档是否仍与当前 Tool 集合一致

当前维护提醒：

- MCP 已是一等能力
- 文档和接口漂移会直接影响 AI Agent 使用效果

### 7.3 GUI

重点关注：

- 是否还能正常读取和展示底层数据
- 搜索与详情视图是否跟随数据结构变化
- GUI 不应单独演化出与 CLI/MCP 不一致的事实定义

当前定位提醒：

- GUI 是工作台，不是系统唯一真相源

## 8. 配置维护

### 8.1 配置来源

优先级通常为：

1. 环境变量
2. `.env`
3. `config/config.yaml`
4. 代码默认值

### 8.2 关键配置项

- 存储路径
- 日志目录与级别
- LLM API Key (`PKV_LLM_API_KEY`)
- Embedding API Key (`PKV_EMBD_API_KEY`)
- Embedding 模型与维度
- 检索参数

Embedding 端点、模型与维度维护要点：

- `PKV_EMBD_BASE_URL`、`PKV_EMBD_MODEL` 和 `PKV_EMBD_DIM` 共同决定向量索引契约，不建议随意更换
- `PKV_EMBD_DIM` 可设置为显式整数，也可设置为 `auto`
- `auto` 模式下，系统会在第一次成功调用 Embedding 接口后锁定真实维度
- 锁定结果会持久化到 `.data/runtime/embedding_dim.json`，重启后会优先复用
- 某些本地 OpenAI-compatible 服务会忽略 `dimensions` 参数，此时应优先使用 `auto`
- 一旦实际端点、模型或维度变化，现有向量索引必须重建，并重新生成文档级和分块级 Embedding
- 即使新旧模型维度相同，向量语义空间也可能不同，旧索引结果不再可信
- 新建索引会在元数据中记录非敏感契约指纹；后续加载时若发现端点、模型或维度不一致，会拒绝复用旧索引
- 老索引如果缺少契约指纹，系统会兼容加载并输出告警；维护者应尽快确认当前 Embedding 配置是否仍与旧索引一致

### 8.3 维护建议

- 修改 API Key 后尽量重启相关入口
- 修改路径配置前先做好备份
- 调整检索参数时要有最小回归验证
- 修改 `PKV_EMBD_BASE_URL`、`PKV_EMBD_MODEL` 或 `PKV_EMBD_DIM` 后，应按索引迁移处理，不要直接复用旧索引
- 如果服务端真实返回维度与历史索引不一致，可先切回旧的 Embedding 服务/模型/维度配置继续使用旧索引
- 如果确认切换到新模型或新维度，应先清理并重建向量索引，再重新生成 Embedding、执行检索或回填

## 9. 备份与恢复建议

### 9.1 推荐备份范围

- `.data/`
- `config/`
- `.env`（必要时单独加密）

### 9.2 恢复顺序建议

1. 停止运行中的 CLI / MCP / GUI
2. 恢复 `.data/`
3. 校验 SQLite 完整性
4. 必要时重建向量索引
5. 启动 CLI 做最小读写验证
6. 再验证 MCP 和 GUI

### 9.3 备份后验证

建议至少做以下检查：

- 打开 1-2 个 Markdown 文件确认可读
- SQLite `integrity_check`
- 进行一次搜索
- 读取一条详情

## 10. 文档维护也是系统维护的一部分

当前项目文档分层已经明确：

- `docs/overview/`：当前核心文档
- `docs/modules/`：模块设计细节
- `docs/specs/`：接口与规范
- `docs/history/`：里程碑、讨论与历史执行文档

维护原则：

- 不再把 `docs/history/prompts/` 当作当前路线真相源
- 当前路线以 `README.md` 和 `docs/overview/` 为准
- 每次重大方向变化后，优先更新核心文档，而不是继续累积历史 Prompt

---

## 11. 当前最值得维护者关注的风险

1. 文档比代码更旧，导致后续开发继续按错误路径推进
2. MCP 接口文档与底层实现漂移，影响 AI Agent 使用
3. GUI 演化出与 CLI/MCP 不一致的数据理解
4. 关系层未建立前，高阶功能被误写成表面包装
5. `PKV_EMBD_DIM=auto` 会复用 `.data/runtime/embedding_dim.json` 中的历史维度缓存；如果底层 Embedding 服务或模型已切换，但维护者未清理缓存并重建索引，系统可能继续沿用旧维度。当前版本依赖 `VectorStore` 的维度检查兜底，并建议优先切回原有 Embedding 配置或执行索引重建

---

## 12. 一句话总结

维护 PKV 的核心不是只保证程序能跑，而是保证 **Markdown 主存储、索引可重建、三入口一致、文档不过时** 这四件事持续成立。
