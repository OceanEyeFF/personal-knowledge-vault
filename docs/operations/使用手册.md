## 1. 快速开始
### 1.1 5 分钟上手路线图
如果你已经具备 Python 与依赖环境，可直接从「第一次归档」开始。
- 00:00-01:00 克隆仓库
- 01:00-03:30 安装依赖 (推荐 Conda 脚本)
- 03:30-04:30 配置本机服务 (`config/local.yaml`)
- 04:30-05:00 第一次归档 + 第一次搜索
---
### 1.2 安装与环境准备
#### 方式 A: Conda 方式 (推荐)
```powershell
# 1) 克隆仓库
git clone https://github.com/OceanEyeFF/personal-knowledge-vault.git
cd personal-knowledge-vault
# 2) 安装 (自动创建 conda 环境 py311-private)
.\scripts\setup-conda.ps1
# 3) 激活环境
conda activate py311-private
```
#### 方式 B: 传统 venv (不推荐)
```powershell
# 1) 克隆仓库
git clone https://github.com/OceanEyeFF/personal-knowledge-vault.git
cd personal-knowledge-vault
# 2) 安装
.\scripts\legacy\setup.ps1
# 3) 激活虚拟环境
.\.venv\Scripts\Activate.ps1
```
#### 配置本机服务
```powershell
Copy-Item config\config.yaml config\local.yaml
notepad config\local.yaml
```
至少需要确认以下 YAML 键与当前服务一致：

```yaml
ai:
  llm:
    base_url: "https://example-llm.invalid/v1"
    api_key: "<填写本机 LLM API Key>"
    model: "<填写 LLM 模型名>"
  embedding:
    base_url: "http://127.0.0.1:12345/v1"
    api_key: "lm-studio"  # 客户端要求非空；LM Studio 可使用非敏感占位字符串
    model: "<填写 Embedding 模型名>"
    dim: auto
```

`config/local.yaml` 已加入 `.gitignore`。真实密钥只保存在该文件中，不要写入 `config/config.yaml`、命令输出、日志或 Issue。

## 2. 核心功能详解
### 2.0 CLI 总览与全局参数
CLI 名称为 `pkv`。
全局选项:
- `--verbose` : 输出更多信息 (INFO)
- `--debug`   : 输出调试信息 (DEBUG)
- `--version` : 显示版本
示例:
```bash
pkv --version
pkv --help
pkv --debug archive "https://example.com"
```
全局参数可与所有子命令组合使用。
---
### 2.1 `pkv archive` / `pkv archive-text` 归档内容
#### 用途
归档网页、聊天记录或文本内容。
归档流程:
- 抓取内容
- AI 分析 (摘要/标签)
- idea Sharpen (可选)
- 写入 Markdown + SQLite + 向量索引
#### 基本用法
```bash
# 归档网页
pkv archive <url>
# 归档聊天记录文件
pkv archive --type chat <file_path>
```
#### 主要参数
- `url_or_path` (位置参数)
  - URL 或本地文件路径
- `--type` (内容类型)
  - `auto` / `webpage` / `chat` / `news`
  - `auto` 会自动识别并选择处理器
- `--skip-sharpen`
  - 跳过 idea Sharpen 交互
- `--tags`
  - 手动指定标签
  - 逗号分隔，例如 `"AI,技术,教程"`
- `--quiet`
  - 静默模式，减少输出
  - 会默认跳过 idea Sharpen
#### 常见场景
场景 A: 归档技术博客
```bash
pkv archive "https://example.com/python-async"
```
场景 B: 归档聊天记录
```bash
pkv archive --type chat "C:/data/chat.json"
```
场景 C: 快速批量归档 (不交互)
```bash
pkv archive "https://example.com/a" --skip-sharpen --tags "AI"
pkv archive "https://example.com/b" --skip-sharpen --tags "Python"
```
#### 纯文本归档
`archive-text` 将位置参数始终当作字面文本，而不是本地文件路径。它使用
`archive-text` 工作流归档到 Markdown 与 SQLite；辅助 AI/向量步骤不可用时，
核心存储完成会以 `degraded` 终态返回零退出码。

```bash
pkv archive-text "这是一条可归档的离线笔记。" --title "第一条文本笔记"
pkv archive-text "这是一条可归档的离线笔记。" --title "第一条文本笔记" --format json
```

- `--title` 可选；省略时从文本提取。标题是显示文本，不能包含路径分隔符或控制字符。
- `--format json` 输出 `terminal`、`knowledge_id`、`title`、`tags`、相对 `file_path` 与公开问题列表，适合脚本调用。
- 纯文本内容仍可能进入配置的 AI 分析步骤；默认自动化请通过测试包装器运行，且不要把真实敏感文本送到未获授权的 Provider。
#### 输出说明
典型输出字段:
- 标题
- 标签
- 文件路径
- 条目 ID
#### 常见问题
- 网络错误
  - 检查 URL 是否可访问
  - 使用 `--debug` 查看详细错误
- API Key 错误
  - 检查 `config/local.yaml` 中的 `ai.llm.api_key` 与 `ai.embedding.api_key`
- idea Sharpen 交互阻塞
  - 使用 `--skip-sharpen` 或 `--quiet`
---
### 2.2 `pkv search` 搜索知识库
#### 用途
在本地知识库中检索条目。CLI 可显式选择 BM25、向量与混合策略；其中向量/混合策略按需构造 Embedding Provider。M13 GUI 发布搜索只保证 BM25，不把 GUI 中的向量、混合或自动路由列为支持合同。
#### 基本用法
```bash
pkv search "Python 异步"
```
#### 主要参数
- `query` (位置参数)
  - 搜索关键词
- `--strategy`
  - `auto` / `bm25` / `vector` / `hybrid`
  - `auto` 会根据查询长度选择策略
- `--limit`
  - 返回结果数量，默认 10
- `--format`
  - 输出格式: `table` / `json` / `markdown`
#### 示例
```bash
# 使用 BM25
pkv search "Python 异步" --strategy bm25
# 使用向量检索
pkv search "深度学习原理" --strategy vector
# 限制 5 条
pkv search "Python" --limit 5
# 输出 JSON
pkv search "Python" --format json
# 输出 Markdown
pkv search "Python" --format markdown
```
#### 搜索技巧
- 短查询 (1-3 个关键词): 优先 BM25
- 长描述性问题: 使用 vector 或 hybrid
- 想要高召回: 使用 hybrid
#### 输出说明
表格模式包含:
- ID
- 标题
- 得分
- 标签
你可以用 `pkv show <id>` 查看完整内容。

### 2.4 `pkv list` 列表与过滤
#### 用途
列出知识库中的条目。
#### 基本用法
```bash
pkv list
```
#### 主要参数
- `--tag` : 按标签过滤
- `--sort`: 排序字段 (time/title/id)
- `--desc`: 降序
- `--limit`: 限制数量
#### 示例
```bash

# 只显示 20 条

```

### 2.4.1 `pkv tags` 标签统计
#### 用途
只读列出 SQLite 中已归档标签及其使用次数；不提供标签写入，以免破坏 Markdown 与 SQLite 的投影一致性。

```bash
pkv tags
pkv tags --limit 50 --format json
```

- `--limit` 范围为 `1..200`。
- JSON 输出为 `{status, total, tags}`，每个标签含 `name` 与 `count`。

### 2.4.2 `pkv related` 相似知识
#### 用途
按已有的文档向量索引列出与指定条目最相近的知识。这是**向量近邻**查询，不是关系图查询；它不构造 Embedding Provider，也不会创建、恢复或改写向量索引。

```bash
pkv related 42
pkv related 42 --limit 5 --format json
```

- `knowledge_id` 必须为正整数；`--limit` 最大为 `20`。
- 缺少索引或该条目的文档向量时，命令会以 `degraded` 和零退出码返回明确问题，而不是伪装成空结果。
- JSON 结果会排除请求条目自身，返回邻居的 ID、标题、摘要、标签、来源类型和 `0..1` 的相似度分数。

### 2.5 `pkv config` 配置管理
#### 用途
查看与管理配置。
支持显示、读取、写入配置。
#### 基本用法
```bash
# 查看完整配置
pkv config show
# 获取单个配置
pkv config get ai.llm.model
# 设置配置
pkv config set ai.llm.model deepseek-chat
```
#### 说明
- `config/config.yaml` 保存可提交的项目默认值，`config/local.yaml` 保存本机覆盖值。
- `config/local.yaml` 会递归覆盖默认配置，并已被 Git 忽略。
- `config set` 只接受 YAML 点号路径，并写入 `config/local.yaml`。
- 数据目录和日志级别等进程级覆盖只用于运行隔离，不用于保存 API Key 或模型配置。

## 3. 配置和定制
### 3.1 本机配置 `config/local.yaml`
应用配置统一保存在 Git 忽略的 `config/local.yaml`。首次使用时从默认配置复制一份：

```powershell
Copy-Item config\config.yaml config\local.yaml
```

常用键：

- `ai.llm.base_url`、`ai.llm.api_key`、`ai.llm.model`
- `ai.embedding.base_url`、`ai.embedding.api_key`、`ai.embedding.model`、`ai.embedding.dim`
- `processors.zhihu.cookie`

只把需要覆盖的本机值写入该文件即可。可用 `pkv config show` 查看生效配置，API Key 会保持脱敏。

注意：

- 未配置服务所需的 API Key 会导致对应功能失败。
- `ai.embedding.base_url`、`ai.embedding.model`、`ai.embedding.dim` 是向量索引契约，不是普通显示偏好。
- 不建议随意更换 Embedding 模型；如果更换端点、模型或维度，必须重建向量索引并重新生成已有文档级、分块级 Embedding
- 即使新旧 Embedding 维度相同，模型变化也可能导致语义空间不一致，旧索引检索结果不再可信

`DATA_DIR`、`DB_PATH`、`VAULT_DIR`、`VECTOR_DIR`、`LOG_DIR`、`TMP_DIR` 和 `LOG_LEVEL` 仅作为进程级运行隔离或诊断开关。不要用环境变量保存 AI 服务密钥或模型配置。
---
### 3.2 默认配置 `config/config.yaml`
这是可提交的项目默认配置文件。本机 endpoint、模型、Cookie 和密钥应写入 `config/local.yaml`，不要写入此文件。
主要包含以下模块:
- `storage` 目录配置
- `ai` AI 服务参数
- `retrieval` 检索参数
- `processors` 处理器参数
- `workflows` 工作流默认配置
- `jieba` 中文分词
- `logging` 日志配置
示例片段:
```yaml
storage:
  vault_dir: ".data/vault"
  db_path: ".data/db/knowledge_vault.db"
  vector_index_dir: ".data/vectors"
  log_dir: ".data/logs"
ai:
  llm:
    base_url: "https://api.deepseek.com/v1"
    api_key: ""
    model: "deepseek-chat"
    max_tokens: 2000
    temperature: 0.7
  embedding:
    base_url: "https://api.openai.com/v1"
    api_key: ""
    model: "text-embedding-3-small"
    dim: 1536
retrieval:
  bm25:
    k1: 1.5
    b: 0.75
  hybrid:
    bm25_weight: 0.4
    vector_weight: 0.6
```
调整建议:
- `storage` 修改数据目录位置
- `ai.llm` 与 `ai.embedding` 调整模型
- `retrieval` 调整权重与 top_k
---
### 3.3 工作流配置 `config/workflows/*.yaml`
PKV 只从真实文件加载带 `schema_version` 的 YAML 工作流；缺失、字段非法或未知字段会在任何 step 副作用发生前拒绝。当前受支持工作流只有:
- `archive-url.yaml`
- `archive-text.yaml`

检索直接由 Retrieval 层及其 CLI/MCP adapter 执行；`search.yaml` 不存在，也不是受支持的回退配置。不要在 `config/config.yaml` 中恢复内嵌 steps 或创建同名搜索工作流来绕过该边界。
#### 归档工作流 (archive-url)
常见步骤:
- `fetch_content`
- `ai_analyze`
- `idea_sharpen`
- `store_entry`
你可以调整:
- 超时时间
- 重试次数
- idea Sharpen 触发条件
#### 文本归档工作流 (archive-text)
该工作流接收由 adapter 构造的文本 Entry，按 YAML 声明的顺序执行分析与持久化步骤；AI 分析失败可按 `on_error: continue` 进入显式 `degraded`，不得被伪装为完整成功。

工作流的公开终态只有 `success`、`degraded`、`error`。继续执行的错误写入 `warnings`/`issues`，致命错误写入 `errors`/`issues`；调用方必须检查 `terminal`，不能只把空结果当成成功。
修改后记得重启 CLI。

### 3.4 自定义词典 `config/custom_dict.txt`
用于 jieba 中文分词。
适合添加行业术语或产品名。
格式:
```
词语 词频 词性
知识管理 1000 n
向量检索 1000 n
```
添加后:
- 重新运行 CLI 即可生效
- 词频越高，分词优先级越高

### 3.5 个性化建议
- 将常用标签写入脚本，减少输入
- 为不同内容类型建立标签规范
- 定期清理 `.data/tmp` 与旧日志

## 4. 故障排查
### 4.1 常见错误与解决方案
#### 1) API Key 未配置
错误示例:
```
LLM API Key 未配置
Embedding API Key 未配置
```
解决方案:
- 检查 `config/local.yaml` 是否存在
- 确保 `ai.llm.api_key`、`ai.embedding.api_key` 等 YAML 点号路径拼写正确
- 使用 `pkv config show` 核对生效配置；不要打印或粘贴真实密钥
- 修改后重新运行 CLI
#### 2) 网络超时或限流
可能原因:
- 网络不稳定
- API 速率限制
解决方案:
- 稍后重试
- 使用 `--debug` 查看详细日志
- 减少频繁批量归档
#### 3) SQLite CHECK 约束错误
错误示例:
```
CHECK constraint failed: source_type IN (...)
```
解决方案:
- 删除旧数据库后重建:
```bash
rm -f .data/db/knowledge_vault.db
```
- 重新运行归档命令
#### 4) 向量索引异常
现象:
- 搜索结果为空
- 向量索引加载失败
解决方案:
- 删除向量目录重新生成:
```bash
rm -rf .data/vectors
```
- 重新归档一条内容
#### 5) PowerShell 脚本无法执行
错误示例:
```
无法加载脚本，因为在此系统上禁止运行脚本。
```
解决方案:
```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```
#### 6) hnswlib 安装失败
原因:
- 缺少 C++ 编译环境
解决方案:
- 安装 Visual Studio Build Tools
- 选择 “使用 C++ 的桌面开发”
#### 7) Python 3.13 兼容问题
现象:
- `lxml` / `greenlet` 编译失败
解决方案:
- 使用 Conda 安装 Python 3.11
- 重新执行 `setup-conda.ps1`

## 5. 测试环境使用 ⭐ **NEW**

> **新增于 v0.6.1**: AI 安全测试功能

### 5.1 为什么需要测试环境

在开发新功能、测试配置或与 AI 协作时，直接操作生产数据存在风险：
- ❌ 可能误删除重要数据
- ❌ 可能写入测试数据污染知识库
- ❌ 无法回滚错误操作

**测试环境提供受控数据路径与 Python 进程防护（不是 OS sandbox）**：
- ✅ 测试数据写入 `.data-test/`
- ✅ 生产数据完全不受影响
- ✅ 可随时清理测试数据

### 5.2 快速使用测试环境

**方法 1: 使用 PowerShell 脚本（推荐）**

```powershell
# 生成固定的合成测试数据；输出精确位于所选 DataRoot
.\scripts\run-test.ps1 -Direct -DataRoot .data-test\manual-seed -Command @(
  "python", "scripts\setup-test-db.py", "--seed", "42", "--count", "20",
  "--output", ".data-test/manual-seed/db/knowledge_vault.db"
)

# 查看测试环境统计
.\scripts\run-test.ps1 -DataRoot .data-test\manual-seed stats

# 只用 BM25 搜索合成数据
.\scripts\run-test.ps1 -DataRoot .data-test\manual-seed search "Python" --strategy bm25
```

`run-test.ps1` 会为当前子进程自动设置完整的 `.data-test` 数据库、Vault、向量、日志和临时目录，不读取额外的测试配置文件；脚本也不会把本机 API Key 写入测试配置。默认自动化验证必须从该包装器启动。

默认模式只接受 PKV CLI 子命令。运行 pytest 或 Python 脚本时必须使用 `-Direct`，并通过 `-Command @("executable", "arg", ...)` 显式传入命令数组，例如：

```powershell
.\scripts\run-test.ps1 -Direct -Command @("pytest", "tests\unit", "-q")
.\scripts\run-test.ps1 -Direct -Command @("python", "src\utils\verify_setup.py")
```

安全入口按调用类型分层：pytest 先经 `tests/offline_entrypoint.py pytest` 在 pytest/plugin 导入前建立离线基线，根 `tests/conftest.py` 再维持逐用例隔离；CLI/MCP 由 `tests/offline_entrypoint.py` 启动；FT7 Direct Python 只接受仓库内的 `-m module` 或 `.py` 脚本，并在同一进程内保留配置、网络和子进程 guard。`-c`、stdin 和解释器 flags 会被拒绝。该 Python guard 是 CAT-0 合成数据验证的纵深防护，不是 OS sandbox，也不授权读取真实快照、真实数据目录或本机配置。非 Python 的 `-Direct` 命令不属于这项 Python G0 保证。

`scripts/migrate.py` 目前未接入 base-only 配置入口；`run-test.ps1` 会明确拒绝它并返回退出码 `2`。涉及真实 LLM 或 Embedding 服务的测试默认关闭；CAT-0 自动化不得通过设置 `PKV_RUN_LIVE=1` 绕过离线边界。

### 5.3 环境检测

检查测试环境是否可用：

```powershell
.\scripts\check-environment.ps1
```

`check-environment.ps1` 会通过 `run-test.ps1` 把配置检查和数据库统计固定到 `.data-test/check-environment`，并隔离数据库、Vault、向量、日志和临时目录；它不会读取或写入生产 `.data/`。其他测试仍应通过 `run-test.ps1` 启动，不要依赖当前终端中残留的路径变量。

### 5.4 清理测试数据

测试完成后，可先核对具体场景的数据量：

```powershell
# 以下以 batch-import 场景为例；请替换为实际场景目录
.\scripts\run-test.ps1 -DataRoot .data-test\batch-import stats
```

`stats` 只读取统计信息，不执行清理。本文不提供直接递归删除命令；清理应通过具备以下防护的专用流程完成：规范化目标绝对路径、确认目标严格位于仓库 `.data-test` 下，并递归拒绝 junction、symlink 等 reparse point。没有这样的清理工具时，保留 Git 已忽略的测试数据，待用户人工核对后处理。

## 6. 数据库升级 ⭐ **NEW**

> **新增于 v0.6.1**: 数据库增量迁移系统

### 6.1 为什么需要数据库升级

当系统添加新功能时（如 M6 CLI 统计表），数据库 Schema 需要升级：
- ❌ **传统方式**：删除旧数据库，重新初始化（丢失所有数据）
- ✅ **增量升级**：自动检测版本，仅执行待升级脚本（保留老数据）

### 6.2 当前 P0 边界与自动化检查

截至当前 P0 收口，尚未执行真实数据迁移。`run-test.ps1` 对任何 `scripts/migrate.py` / `scripts.migrate` 调用都返回退出码 `2`；不要把该拒绝误解为迁移测试失败，也不要绕过包装器裸跑迁移 CLI。

默认自动化只验证 pytest 创建的临时 SQLite 数据库，覆盖 fresh install、迁移顺序、幂等性和健康检查等代码契约：

```powershell
.\scripts\run-test.ps1 -Direct -DataRoot .data-test\migration-unit -Command @(
  "pytest",
  "tests\unit\test_migration_manager_versions.py",
  "tests\unit\test_migration_manager_runtime.py",
  "tests\unit\test_migration_health_check.py",
  "-q"
)
```

这些测试先经 offline pytest bootstrap 建立离线基线，根 `tests/conftest.py` 再维持逐用例隔离，且只操作测试自己创建的临时 SQLite；通过并不等于旧库升级兼容门禁已经完成。

### 6.3 真实迁移前置门禁

真实迁移仍由 FT5 加上 U1/G8 和用户明确授权共同阻塞。在这些门禁全部满足前：

- 真实快照只读，不运行版本检查、dry-run、health-check 或迁移命令；
- 不从真实快照复制内容到默认 CAT-0 自动化目录；
- 不执行生产备份、恢复或迁移命令；
- 不把合成临时 SQLite 的结果表述成真实数据验证。

获批后的验证对象也必须是由已授权快照制作的 **disposable writable clone**，不得原地修改快照。迁移前后均应记录 Schema 版本、关键表行数、关系边、FTS 查询、索引及完整性基线；任一差异无法解释就停止。

### 6.4 执行升级

当前文档不提供可执行的真实升级命令，因为 FT5、U1/G8 与用户授权尚未完成。进入获批窗口后，应在专门 Runbook 中固定克隆来源、写入目标、备份/回滚点、迁移命令和验收指标，并由用户逐项确认后执行。

### 6.5 回滚（如果升级失败）

回滚会替换数据，同样不属于默认自动化。只有在真实迁移已获批、disposable writable clone 演练通过并且用户再次确认准确恢复目标后，才能按专门 Runbook 执行；CAT-0 包装器和 FT7 guard 不提供恢复授权。
