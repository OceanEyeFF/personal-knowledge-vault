# 使用手册（Personal Knowledge Vault）

**适用基线**：当前内部使用的 headless PKV Core
**文档修订**：2026-08-21
**适用对象**：日常 CLI / MCP 使用者，以及未来 GUI 的同一数据根使用者

> PKV 是个人知识数据库：管理互联网信源、历史新闻和过往文章。CLI、MCP 与未来 GUI 共用一个 PKV 数据根；`个人文章` 等应用是调用方。当前不做 PyPI 发布，也不把历史 held test candidate 当作正式 release。MCP 仅支持 stdio；外部 GUI 只能调用 `pkv_kernel`，不能 import `src.*`。

> 默认测试和 AI 自动化与本手册的用户流程严格分开：测试只经 `scripts/run-test.ps1` 使用 `.data-test` 合成数据，不读取真实 Vault、真实配置、Key 或 Provider。本手册中的 Provider、URL 与用户 profile 命令只能由用户明确选择并执行。

## 1. 运行布局与安全边界

### 1.1 唯一用户配置和单一数据根

```text
%USERPROFILE%\.pkv\
├── config.yaml                   # 唯一可编辑业务配置，可含 Key/Cookie
└── data\                         # 默认 data root
    ├── config\local.yaml         # PKV 管理的无密钥 runtime snapshot
    ├── db\knowledge_vault.db
    ├── vault\                    # Markdown 主存储
    ├── vectors\                  # 向量索引与 generation
    ├── logs\
    ├── tmp\
    ├── backups\
    └── runtime\
```

数据根的优先级固定为：

```text
PKV_DATA_ROOT → storage.data_root → %USERPROFILE%\.pkv\data
```

- `PKV_DATA_ROOT`：当前进程/终端的正式临时换根覆盖。
- `storage.data_root`：写在唯一用户配置中的持久根设置。
- `PKV_LOG_LEVEL`：唯一正式日志级别环境覆盖。
- `<data-root>/config/local.yaml`：**不是用户配置**，不参与 `Config` merge，且不得存放 Key、Cookie、Token、endpoint 或业务设置。

不要使用 `DATA_DIR`、`DB_PATH`、`VAULT_DIR`、`VECTOR_DIR`、`LOG_DIR`、`TMP_DIR`、`LOG_LEVEL` 来配置产品；它们仅为隔离测试内部保留。

### 1.2 旧目录的处理

历史 checkout 可能含有 `config/local.yaml` 与 `.data/`；历史 held candidate 也可能位于 `%LOCALAPPDATA%`。这些都不是当前根。本手册不读取内容、不复制、不删除、不迁移这些路径。

若将来需要处理旧数据，顺序必须是：**inspect → plan → 展示影响范围与备份/保留策略 → 用户确认 → execute → smoke test**。在明确确认前，不要手工复制、移动、删除或让新 root 接管旧目录。

## 2. 首次使用：配置、检查、计划、确认

### 2.1 准备环境

源码 checkout 推荐使用 Conda/Python 3.11：

```powershell
.\scripts\setup-conda.ps1
conda activate py311-private
```

或在已激活的 Python 3.11+ 环境中：

```powershell
python -m pip install -r requirements.txt
```

依赖安装可能访问包源；它不会自动初始化或迁移用户数据。

### 2.2 创建唯一配置（无覆盖）

下面的 PowerShell 片段只在用户配置不存在时复制无密钥模板。请由用户执行；已有配置不会被覆盖：

```powershell
$pkvProfile = Join-Path $env:USERPROFILE '.pkv'
$userConfig = Join-Path $pkvProfile 'config.yaml'
New-Item -ItemType Directory -Path $pkvProfile -Force | Out-Null

if (-not (Test-Path -LiteralPath $userConfig)) {
    try {
        [System.IO.File]::Copy(
            (Resolve-Path -LiteralPath .\config\config.yaml).Path,
            $userConfig,
            $false  # overwrite = false；并发创建时绝不覆盖另一份配置
        )
    } catch [System.IO.IOException] {
        if (-not (Test-Path -LiteralPath $userConfig)) { throw }
    }
}

notepad $userConfig
```

首次 fresh setup 会验证 LLM 与 Embedding Provider，因此必须填入可用配置。Key 和 Cookie 只能留在这个本机文件中，不要放进仓库、命令行、日志、Issue 或 `<data-root>/config/local.yaml`：

```yaml
ai:
  llm:
    base_url: "https://your-llm.example/v1"
    api_key: "<local-only>"
    model: "<llm-model>"
  embedding:
    base_url: "https://your-embedding.example/v1"
    api_key: "<local-only>"
    model: "<embedding-model>"
    dim: 1536

# 可选的持久 data root；不设则用 %USERPROFILE%\.pkv\data。
# storage:
#   data_root: "D:\\PKV\\data"
```

如需只为当前 PowerShell 临时换根或调日志：

```powershell
$env:PKV_DATA_ROOT = 'D:\PKV\data'
$env:PKV_LOG_LEVEL = 'DEBUG'
```

### 2.3 只读检查与计划

不要手工创建数据库、`vectors`、`runtime` 或 snapshot。用户先运行：

```powershell
# 只读：不创建文件，不启动 Provider，不写日志。
python -m src.main inspect

# 仍只读：输出动作、影响范围、保留/备份说明、网络要求和 PLAN_ID。
python -m src.main setup
```

检查以下内容：

- 解析后的目标 data root 是否正确；
- readiness 与是否为 fresh root；
- 每项动作的影响、`requires_network`、备份/保留说明；
- 刚刚生成的 `PLAN_ID`。

fresh setup 通常会进行最小 LLM/Embedding 健康探测、创建新的数据库与派生目录，并写入无密钥 runtime snapshot。Provider 探测会访问配置的 endpoint，可能发送探测请求并产生网络流量或费用。

### 2.4 明确确认执行

确认计划后，再使用该次输出的精确 ID：

```powershell
$planId = '从上一条 setup 输出复制的 PLAN_ID'
python -m src.main setup --apply --confirm $planId --allow-network

# 只读复核，预期为 READY。
python -m src.main inspect
```

`--apply`、`--confirm PLAN_ID` 和计划要求的 `--allow-network` 是缺一不可的授权。配置、data root 或运行态在确认后改变时，旧计划会变 stale；重新 `inspect` / `setup`，不要复用 ID。已有或异常数据根不应按 fresh setup 处理：先用 `python -m src.main repair` 获取只读计划。

## 3. 日常 CLI

源码 checkout 的入口是 `python -m src.main`。以下示例均假设前一节的 `inspect` 已显示 `READY`。

### 3.1 查看状态与配置

```powershell
python -m src.main --help
python -m src.main inspect
python -m src.main stats
python -m src.main config show
python -m src.main config get storage.data_root
```

`config show/get` 会遮罩敏感值。`config set` 可以写入唯一用户配置，但敏感 Key/Cookie 会被拒绝作为命令行参数；请直接编辑 `%USERPROFILE%\.pkv\config.yaml`。

```powershell
python -m src.main config set logging.level DEBUG
```

### 3.2 归档

```powershell
# URL 归档：可能抓取网页、调用 Provider、产生费用，并写入共享 data root。
python -m src.main archive "https://example.com/article" --skip-sharpen

# 纯文本归档：位置参数按字面文本处理，不会因看起来像路径而读取文件。
python -m src.main archive-text "这是一条可归档的笔记。" --title "第一条笔记"
python -m src.main archive-text "这是一条可归档的笔记。" --format json
```

归档写入 Markdown、SQLite 和（配置/流程允许时）向量索引。完整文章、Prompt 等本地审计信息可用于复现，但任何日志/诊断都不得含 API Key、Authorization、Cookie 或 URL 中的凭据。

### 3.3 搜索、查看和统计

```powershell
# BM25 不主动构造 Embedding Provider。
python -m src.main search "关键词" --strategy bm25

# 向量/混合检索按需使用 Embedding 能力，可能受索引契约和 Provider 状态影响。
python -m src.main search "描述性问题" --strategy hybrid

python -m src.main show 42
python -m src.main list --limit 20
python -m src.main tags --format json
python -m src.main related 42 --limit 5 --format json
python -m src.main stats
```

`related` 是严格只读的向量近邻查询：它不会创建、恢复或修改索引。索引或文档向量缺失时，会返回明确的 `degraded`，而不是把问题伪装为空结果。

### 3.4 `repair` 的正确用法

当 `inspect` 指出 snapshot drift、数据库异常或需要 repair 时：

```powershell
# 只读计划，不执行修复。
python -m src.main repair
```

仔细检查新计划的影响、备份/保留说明、网络与 `PLAN_ID`。只在用户确认后才使用同样的 `--apply --confirm PLAN_ID --allow-network` 模式。不要直接删除数据库、向量目录、日志或 runtime snapshot 来“修复”。

## 4. MCP 与共享数据根

启动 MCP stdio server：

```powershell
python -m src.mcp
```

- MCP 只支持 stdio，不支持 HTTP/Bearer。
- CLI、MCP 与未来 GUI 解析同一个用户配置和 data root。
- 读操作可同时进行；任何时刻同一 data root 只允许一个写操作。
- 当 MCP 写请求遇到别的写操作时，它会以稳定、可恢复的 `write_busy` 响应。调用方应停止当前写请求、等待后重试，不应另起一个并发写入者。
- 外部 GUI 必须通过 `pkv_kernel` 的稳定公开接口接入；它不能依赖相邻源码 checkout 或 `src.*`。

## 5. 配置、数据与 Embedding

### 5.1 用户配置

`%USERPROFILE%\.pkv\config.yaml` 是唯一可编辑配置，覆盖随源码/包提供的 `config/config.yaml` 默认值。常用键包括：

- `storage.data_root`
- `ai.llm.base_url`、`ai.llm.api_key`、`ai.llm.model`
- `ai.embedding.base_url`、`ai.embedding.api_key`、`ai.embedding.model`、`ai.embedding.dim`
- `processors.zhihu.cookie`
- `logging.level`

`PKV_DATA_ROOT` 覆盖 `storage.data_root`；`PKV_LOG_LEVEL` 覆盖 `logging.level`。两者适用于启动它们的进程，不会把值写回配置文件。

### 5.2 runtime snapshot

`<data-root>/config/local.yaml` 记录不含秘密的运行时兼容事实。它会把当前数据库、Embedding fingerprint、维度与索引 generation 绑定到同一不可变配置 snapshot。不要用文本编辑器修它、从旧路径复制它，或把它当用户配置备份。

### 5.3 Embedding 与索引

Embedding endpoint、模型与维度共同构成索引契约。更换任一项后，旧向量即便维度相同也可能处于不同语义空间：

1. 先运行 `inspect` 了解 drift 和影响；
2. 查看后续 `repair` / Embedding lifecycle 的只读计划；
3. 确认范围、网络、费用与保留 generation 后，才执行精确计划；
4. 完成后再次 `inspect`，再运行所需搜索 smoke test。

不要通过删除 `<data-root>/vectors`、手工改维度缓存或编辑 runtime snapshot 触发重建。

### 5.4 数据文件位置

在最终 `<data-root>` 下：

```text
vault/                 Markdown 主存储
db/knowledge_vault.db  SQLite 元数据与全文索引
vectors/               文档/分块向量与 generation
logs/pkv.log           本地运行日志
backups/               生命周期计划使用的备份位置
runtime/               内部 runtime 状态
config/local.yaml      无密钥 runtime snapshot
```

用户可以编辑自己的 Markdown 内容，但在修改、移动或恢复数据前应先备份并理解 SQLite/向量投影会随之失配。不要让多个写入者同时对一个 root 作业。

## 6. 故障排查

### 6.1 Provider 未配置或探测失败

1. 由用户打开 `%USERPROFILE%\.pkv\config.yaml`，检查 LLM 与 Embedding 的 `base_url`、`api_key`、`model`、`dim`；
2. 不要在终端、日志、Issue 或聊天中输出 Key、Cookie、token、Authorization 或 URL 凭据；
3. 重新运行 `inspect` / `setup` 获取新计划；修改配置后旧 `PLAN_ID` 不能继续使用。

### 6.2 `setup` / `repair` 没有写入

这是有意的默认行为。命令默认只展示计划。查看输出里的影响、`PLAN_ID` 与 `requires_network`，由用户决定是否以 `--apply --confirm PLAN_ID --allow-network` 授权。

### 6.3 `write_busy`

另一个 CLI、MCP 或 GUI 写操作持有 data-root writer lease。停止或等待那个写操作完成后重试。不要用强制删除 lease 文件、并行启动新归档或手工修改索引来绕过它。

### 6.4 日志与诊断

日志位于 `<data-root>/logs/pkv.log`。设置当前终端的调试级别：

```powershell
$env:PKV_LOG_LEVEL = 'DEBUG'
python -m src.main inspect
```

日志可以记录用于复现的操作和内容摘要/文本，但不应出现 API Key、Cookie、Authorization、Token 或 URL 凭据。报告问题时，仅提供已人工核对不含秘密的最小相关片段。

### 6.5 旧 `.data/`、旧 `config/local.yaml` 或历史安装目录

保留它们，不要复制到新 root，也不要通过删除来“修复”。先运行当前 root 的只读 `inspect`，再等待明确的旧数据迁移/接管决策；当前流程不会自动迁移。

## 7. 隔离测试与历史数据

### 7.1 开发/AI 协作测试

默认测试必须使用 `.data-test`：

```powershell
.\scripts\run-test.ps1 -Direct -DataRoot .data-test\manual-seed -Command @(
  "python", "scripts\\setup-test-db.py", "--seed", "42", "--count", "20",
  "--output", ".data-test/manual-seed/db/knowledge_vault.db"
)

.\scripts\run-test.ps1 -DataRoot .data-test\manual-seed stats
.\scripts\run-test.ps1 -DataRoot .data-test\manual-seed search "Python" --strategy bm25
```

测试包装器固定其子进程到隔离 root，并阻止测试读取用户 profile、真实 Provider 或真实 Vault。测试通过仅证明合成/离线合同，不证明真实数据、网络、费用、迁移或发布。

### 7.2 历史数据库升级说明

仓库中仍保留历史数据库迁移和 held candidate 文档，供追溯用；它们不是当前用户操作 runbook。真实迁移、恢复或旧目录接管目前不提供可直接复制的命令，且绝不能通过 `run-test.ps1` 的合成测试 lane 执行。

未来获批的真实流程必须固定源快照、可写 clone、目标 root、备份/回滚点、影响清单、明确确认和 smoke test；未经授权不得读取、复制、删除或迁移任何用户数据。
