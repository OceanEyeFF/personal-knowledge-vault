# 开发环境搭建指南

> Personal Knowledge Vault 的源码开发环境。本文描述当前 headless Core 的本地使用与隔离验证，不是安装器、PyPI 或 release 指南。

**最后更新**：2026-08-21
**目标读者**：本仓库开发者；AI Agent 仅可执行隔离测试，不可执行用户 profile 操作

> **执行边界**：用户 profile 配置、用户数据根初始化、真实 URL、Provider 探测和任何旧目录处理，都只能由用户在本机明确执行。AI Agent 的默认自动化只能经 `scripts/run-test.ps1` 使用 `.data-test` 合成根；不得读取真实 Vault、`%USERPROFILE%\.pkv\config.yaml`、真实 Key 或 Provider 输出。

---

## 1. 当前数据与配置布局

PKV 管理一个可由 CLI、MCP 与未来 GUI 共用的数据根；外部应用（例如 `个人文章`）是调用方。当前唯一有效布局如下：

```text
%USERPROFILE%\.pkv\
├── config.yaml                   # 唯一可编辑用户配置，可含 Key/Cookie
└── data\                         # 默认 data root
    ├── config\local.yaml         # PKV 管理的无密钥 runtime snapshot
    ├── db\knowledge_vault.db
    ├── vault\
    ├── vectors\
    ├── logs\
    ├── tmp\
    ├── backups\
    └── runtime\
```

数据根的解析顺序是：

```text
PKV_DATA_ROOT → storage.data_root → %USERPROFILE%\.pkv\data
```

`PKV_LOG_LEVEL` 与 `PKV_DATA_ROOT` 是仅有的正式环境变量。`DATA_DIR`、`DB_PATH`、`VAULT_DIR`、`VECTOR_DIR`、`LOG_DIR`、`TMP_DIR` 与 `LOG_LEVEL` 不属于产品配置；它们仅在 `PKV_TEST_OFFLINE=1` 的测试注入中兼容。

`<data-root>/config/local.yaml` 不是另一份 `config.yaml`，也不参加配置 merge。它只保存无密钥运行态事实（数据库与 Embedding 契约等），读取时对任何 credential 形字段 fail-closed。不要编辑、复制、删除或向其中写入 API Key、Cookie、Token、endpoint。

历史 checkout `config/local.yaml`、`.data/`，以及 held candidate 的 `%LOCALAPPDATA%` 布局仍可能存在，但不是当前政策。开发环境脚本和本指南不读取内容、不复制、不删除、不迁移这些路径；后续处理必须先 inspect、展示影响范围/备份策略，再由用户确认单独方案。

## 2. 系统要求

| 组件 | 建议 |
|---|---|
| 操作系统 | 当前 checkout 优先 Windows PowerShell |
| Python | 3.11+；推荐 3.11 |
| 环境管理 | Conda（`py311-private`）或 venv |
| 存储 | 足够容纳 Markdown、SQLite 和向量索引的本地磁盘 |
| 网络 | 仅用户主动安装依赖、Provider 健康探测、归档或 Embedding 时需要 |

默认测试不要求网络，也不需要真实 Key。

## 3. 安装依赖

### 3.1 Conda（推荐）

```powershell
git clone https://github.com/OceanEyeFF/personal-knowledge-vault.git
Set-Location personal-knowledge-vault

# 只安装开发依赖；不会初始化数据库、创建用户 data root 或接管旧目录。
.\scripts\setup-conda.ps1
conda activate py311-private
```

该脚本可以在配置不存在时以 no-clobber 方式准备 `%USERPROFILE%\.pkv\config.yaml` 的模板，但不会覆盖已有用户配置。依赖安装可能访问 Conda/Python 包源。

### 3.2 venv（手动）

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

不要使用旧 `scripts/legacy/` 流程来决定当前用户配置或数据根；它们只能作为历史开发辅助，仍须遵守本文件的 profile 与生命周期规则。

## 4. 创建唯一用户配置（由用户执行）

`config/config.yaml` 是随源码提供的无密钥默认模板。用户配置只在 `%USERPROFILE%\.pkv\config.yaml`；下面的命令已有文件时不会覆盖：

```powershell
$pkvProfile = Join-Path $env:USERPROFILE '.pkv'
$userConfig = Join-Path $pkvProfile 'config.yaml'
New-Item -ItemType Directory -Path $pkvProfile -Force | Out-Null

if (-not (Test-Path -LiteralPath $userConfig)) {
    try {
        [System.IO.File]::Copy(
            (Resolve-Path -LiteralPath .\config\config.yaml).Path,
            $userConfig,
            $false  # overwrite = false；并发创建时绝不覆盖另一份配置
        )
    } catch [System.IO.IOException] {
        if (-not (Test-Path -LiteralPath $userConfig)) { throw }
    }
}

notepad $userConfig
```

配置可按需覆盖默认值。例如：

```yaml
storage:
  # 可选；不设则为 %USERPROFILE%\.pkv\data
  data_root: "D:\\PKV\\data"

ai:
  llm:
    base_url: "https://your-llm.example/v1"
    api_key: "<local-only>"
    model: "<llm-model>"
  embedding:
    base_url: "https://your-embedding.example/v1"
    api_key: "<local-only>"
    model: "<embedding-model>"
    dim: 1536
```

为了 fresh setup 的 Provider 验证，LLM 与 Embedding 配置都必须可用。`dim: auto` 会要求已确认的 Embedding 探测才能写入运行态契约；模型、endpoint 或维度变更会使现有向量索引发生 drift。

临时覆盖仅作用于当前终端：

```powershell
$env:PKV_DATA_ROOT = 'D:\PKV\data'
$env:PKV_LOG_LEVEL = 'DEBUG'
```

## 5. 初始化数据库与 runtime（显式生命周期）

不要调用旧的手工 `init_db.py`、手工创建 `db/vectors` 子目录，或通过删除目录来“重建”。用户应当在配置完成后依次运行：

```powershell
# 只读：不会创建根、数据库、快照或日志文件。
python -m src.main inspect

# 只读：展示确切目标、影响范围、保留/备份说明、网络要求及 PLAN_ID。
python -m src.main setup
```

首次 fresh plan 通常包含：

1. 对配置的 LLM 和 Embedding endpoint 做最小健康探测；
2. 在计划中的单一数据根创建新 SQLite 与必要目录；
3. 写入 `<data-root>/config/local.yaml` 无密钥 runtime snapshot。

Provider 探测可能产生网络流量和费用。确认计划输出中的根、影响、`PLAN_ID` 与 `requires_network` 后，用户才能执行：

```powershell
$planId = '从上一条 setup 输出复制的 PLAN_ID'
python -m src.main setup --apply --confirm $planId --allow-network
python -m src.main inspect
```

最后一次 `inspect` 应显示 `READY`。计划仅对当时的配置和运行态有效：配置、root 或状态在确认后改变时会得到 stale 提示，必须重新检查和确认。非空/不完整/旧数据根不允许被当作 fresh 初始化；用 `python -m src.main repair` 先获取只读计划，不要自行迁移或删除。

## 6. 使用与调试

```powershell
python -m src.main --help
python -m src.main config show
python -m src.main config get storage.data_root
python -m src.main stats
python -m src.main search "关键词" --strategy bm25

# MCP 仅 stdio。
python -m src.mcp
```

`config show/get` 会遮罩敏感值。`config set` 只写 `%USERPROFILE%\.pkv\config.yaml`，并拒绝把敏感值作为命令行参数；Key/Cookie 应由用户直接编辑配置文件。CLI、MCP 与未来 GUI 共享同一 root 时，读操作可并行，写操作必须串行；MCP 的写冲突会以 `write_busy` 返回。

需要真实 URL archive、Provider 或 Embedding 时，用户应明确知道请求目标、会发送的内容和可能费用。开发环境自动化不替代这些真实验证。

## 7. 隔离测试与验证

所有开发自动化都通过包装器并明确选用 `.data-test` 根：

```powershell
.\scripts\test-conda.ps1

.\scripts\run-test.ps1 -Direct -DataRoot .data-test\unit -Command @(
  "python", "-m", "pytest", "tests\\unit", "-q"
)

.\scripts\run-test.ps1 -Direct -DataRoot .data-test\verify-setup -Command @(
  "python", "src\\utils\\verify_setup.py"
)
```

这些命令使用合成数据、fake Provider 和离线 guard。测试成功不能表述为真实 Provider、用户数据、迁移或发布已验证；真实迁移仍需 inspect → plan → 展示影响/备份 → 用户确认 → execute → smoke test 的独立授权流程。

## 8. 故障排查

### `setup` 只显示计划

这是预期行为。检查 `PLAN_ID`、目标 root、`requires_network` 和动作影响，再使用精确的 `--apply --confirm PLAN_ID --allow-network`。不要通过重复执行、直接建目录或手工写 snapshot 绕过确认。

### Provider 结构或连通性失败

确认 `%USERPROFILE%\.pkv\config.yaml` 中的 LLM/Embedding `base_url`、`api_key`、`model` 和 `dim`，但不要把 Key 输出到终端、日志或 Issue。修正后重新 `inspect` / `setup`；旧计划不会因配置修改而自动变新。

### Embedding 发生 drift

endpoint、模型或维度构成向量索引契约。请先 `inspect`，再按后续 `repair` / Embedding lifecycle 的明确计划重建；不要删除 `<data-root>/vectors` 或 runtime snapshot。

### hnswlib 安装失败

优先使用 Python 3.11 Conda 环境。若本机只能源码编译，则需要匹配的 C++ 工具链；这属于依赖安装问题，不要借此改动数据根。
