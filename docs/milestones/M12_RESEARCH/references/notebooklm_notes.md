## 笔记 001: DeepSeek API 核心特性与使用限制

**创建日期**: 2026-02-20
**来源文档**: DeepSeek 官方文档（由 NotebookLM 自动提取）

### 一、核心特性

#### 🔹 领先的模型能力

1. **推理能力全球领先**
   - DeepSeek-V3.2 的推理能力达到 GPT-4o 和 Claude-3.5-Sonnet 的水平

2. **思考能力集成**
   - `deepseek-reasoner` 模型（思考模式）支持长思维链推理
   - 特别在数学、代码和逻辑验证上表现卓越
   - 部分基准测试中媲美 o1-preview

3. **首创思考融入工具调用**
   - DeepSeek-V3.2 是首个支持在思考模式下调用工具的模型
   - 可通过多轮"思考+工具调用"给出更详尽准确的回答

#### 🔹 超长上下文与模型细节

1. **上下文窗口**: **128K** tokens（DeepSeek-V3.2）
   - 远超大多数模型（GPT-4 Turbo 128K，Claude 3.5 200K）

2. **双模型体系**:
   - `deepseek-chat`: 适合日常问答和通用任务
   - `deepseek-reasoner`: 专注深度逻辑推理

#### 🔹 开发友好功能

1. **JSON 输出与工具调用**
   - 两款模型均支持 JSON 模式输出和 Function Calling

2. **上下文缓存（Context Caching）**
   - 缓存重复的系统提示词或上下文
   - **缓存命中价格仅为未命中的 1/10**（极大降低输入成本）

3. **补全模式**
   - 支持聊天前缀补全（Chat Prefix Completion）
   - `deepseek-chat` 还额外支持 FIM（Fill-in-Middle）补全

#### 🔹 极致的性价比

**API 价格**（极具竞争力）:
- 输入（缓存未命中）: **$0.28/1M tokens**
- 输出: **$0.42/1M tokens**
- 缓存命中: **$0.028/1M tokens**（仅为未命中的 1/10）

### 二、使用限制与注意事项

#### 🔹 Token 与输出限制

1. **单次输出长度**:
   - `deepseek-chat`: 默认最大 4K，最高可设为 **8K** tokens
   - `deepseek-reasoner`: 默认最大 32K，最高可设为 **64K** tokens

2. **思维链输出规则**（⚠️ 重要）:
   - 思维链内容（`reasoning_content`）是**只读**的
   - 开发者在多轮对话时，**不得**将该内容回传至下一次请求
   - 违反会破坏上下文管理系统

#### 🔹 请求限制与并发

1. **无硬性并发限制**
   - DeepSeek 官方表示不限制用户并发量

2. **动态节流**（⚠️ 高峰期影响）:
   - 流量高峰期，系统会动态限流
   - 可能导致 **429 错误**或响应延迟

3. **连接超时**:
   - 请求发出 10 分钟后仍未开始推理 → 服务器强制关闭连接

#### 🔹 技术兼容性限制

1. **工具调用适配**
   - 思考模式目前未充分适配使用非标准工具调用的组件（如 Cline、RooCode）
   - 建议此类场景使用非思考模式

2. **Reasoner 模型功能缺项**
   - `deepseek-reasoner` 目前不支持 FIM 补全功能

3. **Speciale 模型限制**
   - 临时研究版 Speciale 不支持工具调用
   - 仅支持思考模式对话

#### 🔹 无状态机制（⚠️ 核心约束）

**API 是无状态的**:
- DeepSeek 不会通过服务器自动记忆对话历史
- 开发者必须在每次调用时手动发送完整的对话上下文（Context Replay）
- **影响**: M12 必须实现客户端对话历史管理

#### 🔹 隐私与合规

1. **数据存储**: 位于**中国内地**的云服务器
2. **数据使用**: 用户未手动关闭"数据用于优化体验"时，输入输出数据可能用于模型训练

### ✅ 应用到 M12

#### 设计影响

1. **模型选择**: 使用 `deepseek-chat`（通用对话）
   - 理由: M12 不需要深度逻辑推理，`deepseek-chat` 性价比更高

2. **无状态机制应对**:
   - 客户端维护完整对话历史（存储在 `chat_sessions.messages` JSON 列）
   - 每次 API 调用发送完整上下文（最近 10 轮）

3. **Token 限制应对（单轮输出质量控制）**:
   - **核心策略**: 限制单轮输出 tokens，保证输出质量
   - **单轮输出限制**: `max_tokens=2000`（确保回复质量和完整性）
   - **会话轮数管理**:
     - 3 轮对话后显示提示："对话已进行 3 轮，建议结束当前会话或新建会话以保持回复质量"
     - 不强制结束，由用户决定是否继续
   - **对话历史管理**:
     - **不自动压缩**：保留完整对话历史
     - 利用 DeepSeek 128K 上下文窗口，充分发送历史消息
     - 仅在逼近 128K 时才考虑手动截断（实际场景中很少发生）
   - **System Prompt 优化**:
     - 固定内容利用上下文缓存（节省 90% 成本）
     - 预估 ~150 tokens
   - **知识上下文注入**:
     - 根据检索结果动态注入相关知识
     - 无硬性 token 限制，由检索引擎控制返回数量

4. **限流应对**:
   - 实现指数退避重试
   - 监听 429 错误 + Retry-After Header

5. **成本优化**:
   - 利用上下文缓存（System Prompt 固定，每次命中节省 90% 成本）

### 🔥 M12 实现要点

根据 NotebookLM 整理的限制，浮浮酱总结出以下实现要点：

1. ✅ **客户端对话历史管理**（SQLite `chat_sessions.messages` JSON 列）
2. ✅ **动态限流处理**（指数退避 + 429 检测）
3. ✅ **Token 预算控制**（截断历史消息 + 知识上下文字符数限制）
4. ✅ **上下文缓存利用**（固定 System Prompt）
5. ⚠️  **10 分钟连接超时**（需要在 UI 显示超时提示）
