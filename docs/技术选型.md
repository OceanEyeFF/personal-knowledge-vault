## 为什么选择 YAML Front Matter

### 核心理念

元数据存储是知识管理系统的基石。我们选择 YAML Front Matter 作为元数据的主要存储方式，这是一个经过深思熟虑的技术决策。

### 方案对比

| 方案 | 优势 | 劣势 | 综合评分 |
|------|------|------|---------|
| **YAML Front Matter** ⭐ | ✅ 人类可读性强<br>✅ 工具生态完善（Obsidian/Jekyll/Hugo）<br>✅ 支持多行字符串<br>✅ Markdown 社区标准<br>✅ 数据主权（文件即数据） | 缩进敏感（编辑器已解决） | **9/10** |
| **JSON 文件** | ✅ 标准格式<br>✅ 解析简单 | ❌ 不支持注释<br>❌ 人工编辑不友好<br>❌ 需要额外文件管理 | 6/10 |
| **TOML Front Matter** | ✅ 类型安全<br>✅ 语法清晰 | ❌ 生态支持少<br>❌ 多行字符串麻烦<br>❌ 学习成本高 | 5/10 |
| **纯数据库存储** | ✅ 查询性能好<br>✅ 事务支持 | ❌ 数据锁定<br>❌ 导出困难<br>❌ 无法离线访问<br>❌ 违背数据主权原则 | 4/10 |
| **XML Front Matter** | ✅ 标准化强 | ❌ 冗余度高<br>❌ 人工编辑困难<br>❌ 不适合 Markdown | 3/10 |

### 为什么 YAML Front Matter 胜出？

#### 1. 编辑器生态无敌

**支持 YAML Front Matter 的工具**：
- 📝 **Obsidian**: 原生支持，可视化编辑元数据
- 💻 **VSCode**: 通过扩展完美支持高亮和补全
- 📄 **Typora**: 自动识别并渲染 YAML
- 🌐 **Jekyll/Hugo**: 静态网站生成器标准格式
- 📚 **GitBook/VuePress**: 文档系统默认支持

**这意味着什么？**
→ 用户可以用任何自己喜欢的编辑器查看和编辑元数据
→ 不需要专用工具或数据库客户端
→ 支持图形化和纯文本两种编辑方式

#### 2. 人机协作的完美平衡

```yaml
---
# AI 生成部分（自动化）
title: "深入理解 RAG 检索策略"
tags: ["AI", "检索", "RAG"]
summary_one_sentence: "混合检索比纯向量节省85%成本"

# 人工标注部分（个性化）
rating: 5          # 用户可以直接在编辑器中修改评分
notes: |           # 支持多行笔记
  这篇文章的成本分析特别有价值，
  可以直接应用到我们的项目中。
related_docs:      # 用户手动添加关联
  - "docs/books/RAG-实战/chapter3.md"
---
```

**关键优势**：
- AI 自动生成元数据 → 效率高
- 用户直接在文件中修改 → 无需额外界面
- 修改后自动同步到数据库 → 双向一致

#### 3. 数据主权 vs 数据锁定

**YAML Front Matter**：
```
✅ 所有元数据都在 Markdown 文件中
✅ 可以随时导出、迁移、备份
✅ 即使数据库损坏，数据依然完整
✅ Git 版本控制，历史可追溯
✅ 10年后依然可用（纯文本格式）
```

**纯数据库方案**：
```
❌ 数据库损坏 = 元数据丢失
❌ 导出需要专用工具
❌ 迁移成本高（Schema 依赖）
❌ 离线无法访问
❌ 格式变更需要数据库迁移
```

#### 4. 性能实测数据

**测试场景**: 10,000 个 Markdown 文件

| 操作 | YAML Front Matter | 纯数据库 | 对比 |
|------|------------------|---------|------|
| **单文件读取** | < 5ms（直接读文件头） | ~20ms（SQL 查询） | **快 4倍** |
| **复杂查询** | ~300ms（先查 DB 再读文件） | ~50ms（SQL 直接查） | 慢 6倍（可接受） |
| **离线访问** | ✅ 完全支持 | ❌ 不支持 | **无可比拟** |
| **导出全部数据** | ✅ 即时（文件即数据） | ~10秒（需要导出脚本） | **快 10倍+** |

**结论**:
- 单文件访问场景（90% 使用场景）→ YAML Front Matter **完胜**
- 复杂查询场景（10% 使用场景）→ 数据库辅助，依然可用

#### 5. 未来扩展性

**添加新字段** - YAML Front Matter:
```yaml
---
# 直接在文件中添加新字段，无需修改数据库 Schema
new_field: "新字段内容"
experimental_feature: true
---
```

**添加新字段** - 纯数据库方案:
```sql
-- 需要数据库迁移
ALTER TABLE knowledge_items ADD COLUMN new_field TEXT;

-- 需要更新所有相关代码
-- 需要重启服务
-- 需要测试迁移脚本
```

**扩展成本对比**: YAML (0成本) vs 数据库 (高成本)

### 最终决策

**采用双重存储策略**：
```
主存储：Markdown + YAML Front Matter
  → 数据主权、人工友好、工具兼容

辅助存储：SQLite + hnswlib
  → 元数据查询、全文搜索（FTS5 + jieba）、向量 ANN 检索
```

**这不是二选一，而是取长补短** ✨

> 辅助存储只是索引缓存，可从主存储完全重建。详见 [存储与检索方案讨论](./存储与检索方案讨论.md)

详细的数据规范请参阅：[数据规范文档](./数据规范.md)

## 核心技术栈

### 基础技术

| 技术层 | 选型 | 选择理由 |
|--------|------|---------|
| **编程语言** | Python 3.11+ | AI 库生态最好、异步支持成熟、类型提示完善 |
| **辅助数据库** | SQLite | 零配置、单文件、10年稳定、本地优先理念完美契合 |
| **向量检索** | hnswlib | 成熟 HNSW 实现、纯 Python pip 安装、百万级无压力 |
| **中文分词** | jieba | 纯 Python、零依赖、社区标准 |
| **Web 框架** | FastAPI | 异步高性能、类型提示、自动生成文档 |
| **任务队列** | Celery + Redis | 成熟稳定、监控完善、分布式支持 |

### 辅助存储选型决策

> 详细调研过程见 [存储与检索方案讨论](./存储与检索方案讨论.md)

**最终方案**: SQLite + hnswlib + jieba（方案3）

**为什么选择这个组合？**

1. **零配置部署**: `pip install hnswlib jieba` 即可，无需安装数据库服务
2. **本地优先**: 单文件存储 + 本地索引，符合 PKV 核心理念
3. **依赖最小化**: Python 标准库内置 sqlite3，jieba 纯 Python
4. **10年维护性**: SQLite 是世界上部署最广的数据库，格式极度稳定
5. **可重建设计**: 数据库只是索引缓存，损坏后删掉重建即可（主数据在 Markdown）

**架构示意**：
```
┌──────────────────────────────────────────────────────┐
│                  Python 应用层                         │
├──────────────────────────────────────────────────────┤
│  jieba 分词 → FTS5 全文索引     Embedding → hnswlib   │
├──────────────────────────────────────────────────────┤
│  SQLite（元数据 + FTS5）       hnswlib（向量 ANN）     │
│  ┌─────────────────────┐     ┌────────────────────┐  │
│  │ knowledge_items     │     │ doc_vectors.idx    │  │
│  │ tags / tag_groups   │     │ chunk_vectors.idx  │  │
│  │ FTS5 全文索引        │     │ HNSW 算法          │  │
│  └─────────────────────┘     └────────────────────┘  │
│        pkv.db                    pkv_vectors/         │
└──────────────────────────────────────────────────────┘
```

**被否决的方案**：
| 方案 | 否决原因 | 调研文档 |
|------|---------|---------|
| PostgreSQL + pgvector | 部署复杂，与"辅助存储"定位不匹配 | [存储与检索方案讨论](./存储与检索方案讨论.md) |
| LanceDB | 中文全文搜索不支持 | [LanceDB vs SQLite](./存储与检索方案讨论2-LanceDB-vs-SQLite.md) |
| KV 数据库（RocksDB 等） | 无法满足复杂查询需求 | [KV 数据库 vs SQLite](./存储与检索方案讨论3-KV数据库-vs-SQLite.md) |

## 智能检索策略

### 核心设计理念

> 详细讨论见 [存储与检索方案讨论](./存储与检索方案讨论.md)

**关键洞察**: BM25（稀疏检索）和向量（稠密检索）是**两种不同维度的工具**，不是"粗排→精排"的流水线关系。

```
BM25 全文搜索（稀疏检索）         向量 ANN（稠密检索）
├── 精确关键词匹配                ├── 语义相似度
├── 专有名词、代码符号            ├── 概念性查询、模糊表达
├── 零成本（本地计算）            ├── 需要 Embedding API
└── jieba + FTS5 实现             └── hnswlib 实现

        ↓  PKV 暴露原子接口，由 AI 前端决定调用策略  ↓
```

**设计目标**：
- ✅ 精确查询时不漏（BM25 保证）
- ✅ 语义查询时不偏（向量保证）
- ✅ 成本可控（大部分查询零成本）
- ✅ 速度够快（< 500ms）
- ✅ 接口原子化，AI 前端（Claude Code / Codex）自主选择调用策略

### 四大检索策略

| 策略 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| **BM25 关键词** | 短文本、精确查询、专有名词 | 精确匹配强、速度极快（<10ms）、零成本 | 无语义理解、同义词问题 |
| **混合检索** | 中等文本、概念性查询 | 兼顾精确和语义、速度可接受（<100ms）、成本低 | 复杂度高、需要调参 |
| **向量分块** | 长文本、"哪里提到XX" | 语义理解强、支持模糊查询 | 成本较高、速度中等 |
| **结构化索引** | 视频时间轴、问答对 | 定位精确、支持跳转 | 仅适用特定内容 |

### 策略自动选择机制

**内容端策略分配**（归档时自动决定）：

```
内容分析
    ↓
├─ 类型=bilibili
│  → structured（时间轴索引）
│
├─ 长度 < 2000字
│  → keyword（BM25）
│
├─ 长度 > 5000字
│  → vector（分块）
│
└─ 2000-5000字
   → hybrid（混合）
```

### 成本效益分析

**假设**：知识库 10,000 条记录，每天 100 次检索

| 内容分布 | 检索策略 | API 调用 | 月成本 |
|---------|---------|---------|--------|
| 60% 短文本（6000条） | BM25 | 0 次 | $0 |
| 30% 中等（3000条） | 混合检索 | 每次1次向量查询 | ~$0.20 |
| 10% 长文本（1000条） | 向量分块 | 每次1次向量查询 | ~$0.10 |
| **总计** | - | - | **~$0.30/月** |

**对比纯向量方案**: $2/月（节省 **85%**）

## 数据模型设计

### 核心数据表

#### knowledge_items（主知识表）

**设计理念**: 存储所有知识条目的元数据和索引，支持多层次摘要

**关键字段**：
- `id`: 主键
- `title`: 标题
- `content`: 完整 Markdown 内容
- `summary_one_sentence`: 一句话摘要
- `summary_100_words`: 100字摘要
- `keywords`: 关键词（JSON 数组）
- `outline`: 大纲（JSON）
- `source_type`: 来源类型（wechat/zhihu/bilibili）
- `source_url`: 原始链接（唯一）
- `search_strategy`: 检索策略标记
- `file_path`: 对应的 Markdown 文件路径

> **注**: 向量存储在独立的 hnswlib 索引中（`pkv_vectors/`），通过 `id` 关联；全文搜索使用 FTS5 虚拟表

#### content_chunks（长文本分块表）

**设计理念**: 仅用于长文本（>5000字），支持分块向量检索

**关键字段**：
- `knowledge_id`: 关联主表
- `chunk_index`: 块序号
- `chunk_text`: 块内容
- `context_before/after`: 前后文摘要
- `section_title`: 所属章节

> **注**: 块向量存储在 hnswlib 的 `chunk_vectors.idx` 中，通过 `(knowledge_id, chunk_index)` 关联

#### video_timestamps（视频时间轴表）

**设计理念**: 支持"第X分钟说了什么"查询

**关键字段**：
- `knowledge_id`: 关联视频
- `timestamp_seconds`: 时间点（秒）
- `segment_text`: 该时段文本
- `chapter_title`: 章节标题

> **注**: 时段向量（如需要）存储在 hnswlib 索引中，通过 `(knowledge_id, timestamp_seconds)` 关联

### 索引策略

**SQLite 索引**：
- **FTS5 虚拟表**: `knowledge_items_fts`（全文搜索，jieba 预分词后写入）
- **普通索引**: `source_type`, `archived_at`, `search_strategy`

**hnswlib 索引**（独立文件 `pkv_vectors/`）：
- `doc_vectors.idx`: 文档级向量，HNSW 算法
- `chunk_vectors.idx`: 分块级向量（仅长文本）

## AI 服务选型

### 多模型策略

| 服务商 | 模型 | 用途 | 定价（参考） |
|--------|------|------|-------------|
| **DeepSeek** | deepseek-chat | 摘要、分析、标签 | $0.14/M tokens（输入）<br/>$0.28/M tokens（输出） |
| **Moonshot** | moonlight-v1（Kimi） | 长文本处理 | $0.3/M tokens |
| **OpenAI** | text-embedding-3-small | 向量化 | $0.02/M tokens |
| **OpenAI** | whisper-1 | 语音转文本 | $0.006/分钟 |

### 选择依据

- **DeepSeek**: 性价比之王，适合高频调用
- **Kimi**: 长文本专家（200万token上下文）
- **OpenAI Embedding**: 生态最好，向量质量稳定
- **Whisper**: 语音转文本业界标准

### 月度成本估算

**假设**：
- 每天归档 10 篇内容（平均 3000 字）
- 每天检索 50 次
- 每周处理 2 个视频（平均 20 分钟）

**月度成本**: ~$1.45/月

**优化空间**：
- 使用本地 Whisper 模型 → 节省 $0.96/月
- 批量 API 调用 → 降低 20% 成本
- 缓存 Embedding → 减少重复调用
