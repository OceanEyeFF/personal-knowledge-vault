## 1. 目标

把已有的检索、关系解释和 citation 能力收束为一项可审阅、可追溯、可在重启后继续查看的
知识成果。v1 只交付一种成果类型：**研究简报（`research_brief`）**。

其最小闭环为：

```text
Topic（一次具体问题）
  -> Evidence ledger（经验证的条目 / chunk / relation locator）
  -> Claim（用户明确提出的、带支持或反证状态的主张）
  -> Outcome（可渲染的研究简报草稿）
  -> explicit review（批准、退回或标记过期）
```

任何没有有效 Evidence 的 Claim 必须显示为 `insufficient`；任何检索、定位或来源版本降级
都必须成为 Outcome 的限制，而不是被渲染为已证实的知识库事实。

## 2. 已有可复用基线

P1-B 不是从零开始：

- `EvidenceCollectionService.collect_evidence()` 已产出文档 / chunk 级 evidence、稳定
  citation locator、关系解释、`chunk_retrieval_status` 和显式 limitation。
- `RelationQueryService` 已提供一跳、多跳受限子图和关系解释；自动落库的边仍只来自低歧义
  显式信号。
- 检索层已有 `success` / `no_hits` / `invalid` / `error` / `degraded` 五态合同，R4 已提供
  READY generation 的读者边界。
- R3/R3.1 已固定所有持久 mutation 的 root writer lease、DataRoot containment、审计和
  restart-safe 原则。

本线不得把 `find_bridges`、`timeline_of`、`contrast` 的 `implementation_level=partial`
表述改写成 full；它们只可作为未来逐 Tool 升级的候选输入，不能成为 v1 Claim 的唯一事实依据。

## 3. v1 设计决定

### 3.1 Topic 是一次 inquiry，不是全局分类法

`Topic` 表示用户发起的具体问题与成果上下文，而不是标签树、知识图谱节点或自动分类。
现有最小字段为：opaque `topic_id`、标题、问题、创建时间、状态、当前 evidence/claim revision。
W3 另以 `input_revision` 与 `input_digest` 表示完整 render input；它们不能只用某个 Claim
的 revision 或更新时间代替，具体边界见 3.5。

### 3.2 Evidence 是版本绑定的证据引用，不复制原文

每项 Evidence 至少绑定：

- `knowledge_id`；
- 安全的 entry 或 chunk locator；
- 当时的 source/content revision digest；
- 取得方式（检索、显式关系、用户选择）；
- 取得时的 retrieval / relation 限制与状态。

v1 不保存原始网页、Provider 请求/响应、私有文件路径、密钥，亦不以复制 source body 的方式
伪造可复现性。读取时若 locator 消失、条目被删除或 revision 漂移，Evidence 的有效状态为
`stale` / `unavailable`，关联 Claim 降为 `insufficient`、Outcome 有效状态进入 `needs_review`；
render 拒绝该输入。观察结果不写回持久输入或 review state，绝不静默改指向新版正文。
对于 entry/chunk locator，首次绑定要求 Markdown 主记录与 SQLite/chunk projection 一致；之后
任一侧漂移都使 Evidence=`stale`，Markdown 不可读取则为 `unavailable`。digest 只保存 opaque
hash，不把正文或本地路径带入 Outcome DTO、日志或公开 envelope。

### 3.3 Claim 与证据强度显式分离

Claim 不是知识条目、关系边或自动事实。v1 的 Claim 状态固定为：

```text
draft | supported | contested | insufficient | withdrawn
```

它保存 statement、支持 / 反证 Evidence 引用、用户说明与稳定 limitation codes；不保存未经
确认的“置信事实”。`supported` 只表示它有当前有效的关联证据，绝不表示系统断言其为真。

### 3.4 Outcome 默认等待人工审阅

`research_brief` 是 Claim 与 Evidence 的确定性 Markdown 投影，状态固定为：

```text
draft -> awaiting_review -> approved
                    \-> returned
任何 evidence drift / delete / degraded -> needs_review
```

用户显式批准只批准该 Outcome revision；不会回写原 Entry、自动新建关系、加入检索语料或把
内容提升为 Vault 事实。批准后的输入漂移仍会使它 `needs_review`。

**W3 已实现：版本绑定的 v2 review。** 调用方必须把实际审阅的 `outcome_id`、`expected_revision`、
`content_sha256`、`expected_input_revision` 一并作为确认条件提交；不能只提交 `topic_id` 后由
服务端选择最新版。approve/return 在 root writer lease 下复核 source 与投影，再在同一 SQLite
事务中校验这四项、当前 Topic input binding、brief 的 rendered input binding 和允许的状态，
以 CAS 同时提交 review state 与确定性 review receipt。任一版本、输入、摘要或状态不匹配均拒绝且不写 review state，要求
重新读取并审阅。相同元组重复提交且当前仍为该动作的目标状态时，可幂等返回；不能撤销后来
的状态转换，也不能作用于后来生成的版本。
同一 brief revision 的 `returned` 保持终态；必须重新 render 生成下一 revision 才能再次进入
`awaiting_review`，不能在同一确认元组上来回 approve/return。
receipt 与状态提交后，终结审计 append 失败不改变成功事实、不补记虚假的业务失败；精确重放
按同一 receipt 返回。审计失败也不能覆盖原本的版本冲突错误。

最终切换目标是 API-major-2；W1 已在
[v2 接口冻结合同](../specs/interfaces/生命周期一致性v2接口冻结合同-2026-10.md) 固定具体签名、
迁移说明和至少一个兼容 SDK 版本的 `DeprecationWarning` 阶段。W3 本地 SDK 0.9.0 保持 API 1.0.0，
增加独立 v2 DTO/入口及 `kernel.traceable-outcomes.v2`；新协议不读取 latest 来代填确认字段。
旧入口保持既有签名、成功语义并发出弃用警告。正式切换 major 2 后，旧无版本
approve/return 即使保留兼容 stub，也必须 fail-closed 并给出明确迁移错误；major-1 Wrapper
应在握手时被拒绝。不得在 major 1 静默增加必填参数，也不得以获取 latest 后代填确认字段作为
兼容方案。切换前 v1 漏洞保持 known_gap；W3 未切换 API major，也不授权发行。
W3 只能验收新协议实现与兼容弃用准备；major-2 握手、旧无版本入口拒绝及 R04 关闭必须等到
W5 实际切换后取证，不能用提前编写的 v2 代码或弃用提示代替切换证明。

### 3.5 SQLite 为结构状态权威，Markdown 是可重建投影

Topic、Evidence、Claim、Outcome status/revision/citation binding 的权威来源为新 SQLite schema；
人可读 research brief Markdown 是由该 revision 确定性生成的投影，置于由 RuntimeLayout 明确
声明且受 containment/lease 保护的 outcome 路径。两者不能各自成为可编辑、可冲突的真相源。

**复审基线与 W3 改变。** 2026-10-24 复审时，r2 及以后的不同输入 orphan 可能长期占用同一路径，
输入 mutation 与 brief 失效也分属两个 commit。W3 保留先发布不可覆盖 Markdown、再提交 SQLite
pointer 的顺序，以 publication identity、完整 CAS 和同事务输入失效替代上述缺口；合同如下，
实际验收范围见第 7 节与 W3 实施记录。

#### 3.5.1 输入变更与失效的一个提交点

- `input_revision` 是 Topic 级单调整数，覆盖 Topic 文本、Evidence 的增删/显式绑定及持久状态、
  Claim 文本/状态/limitations、Claim↔Evidence 边的新增/修改/删除等所有会改变 render input 的
  mutation。一次实际改变输入的成功操作只递增一次；规范化后无变化的操作幂等返回且不递增、
  不额外失效 brief，失败回滚不递增。仅 render 或 review state 变化不递增。
- 同一 SQLite 事务必须一起提交：输入行/边变更、`input_revision += 1`、新 `input_digest`、
  已有 brief 的 `state = needs_review`。不得以两个 Store 方法各自 commit，也不得以 writer
  lease、审计成功或事后补偿代替该事务。任意语句后中断，重启只能看到全部旧状态或全部新状态。
- `input_digest` 是版本化 canonical、body-free render input 的 SHA-256：包括 `input_revision`、
  持久保存的 `render_contract_version`、会出现在 Markdown 中的 Topic/Claim/Evidence 字段、captured source digest
  和确定性排序后的边；不包括 brief review state、审计时间、观察时间、绝对路径或 source body。
  renderer 合同版本改变必须显式推进 input binding 并失效旧 brief，不能由 read 隐式更新。
  捕获输入必须携带该版本；重启后不能识别该版本或没有对应 renderer 时拒绝发布，不能静默
  选择当前默认 renderer 生成同 identity 的不同字节。
  普通 render 始终使用 Topic 已绑定版本，render/read 均不得自行递增 input revision；软件升级
  不再支持该版本时，必须明确拒绝并进入受控输入合同迁移/重新生成计划，不得自动换 renderer
  却保留旧 input digest。
  该定义保证 A→B→A 的修改不会把较新的 input revision 误识别成旧 orphan 的完全相同输入。
- brief 在 pointer commit 时保存 `rendered_input_revision` 与 `rendered_input_digest`。
  reader 使用同一个 SQLite read transaction 取得 Topic、Evidence、Claim、边和 brief，核对
  rendered binding 与当前 input binding；缺失或不匹配时，effective state 必须为 `needs_review`，
  即使持久 state 仍为 approved。source revalidation 与投影摘要检查继续生效；read 不持有 writer
  lease、不改状态、不修文件，也不为旧行猜测或补写 binding。
- renderer 只消费持久输入，不把实时 Evidence/Claim overlay 写进同一 publication identity。
  历史持久 Evidence 若仍为 `stale` / `unavailable`，即使来源已恢复到 captured digest，也须显式
  detach/reattach 并重新链接证据后再 render；不得一边生成 `insufficient` 文本、一边按实时恢复
  的来源将其批准为 supported。普通 render 同时要求持久绑定与当前来源复核均为 current。

#### 3.5.2 任意 revision 的不可变发布与恢复

Topic 在创建事务中预留一个稳定 opaque `outcome_id`；预留身份不是 brief pointer，也不表示
成果已经生成。既有 Topic 的身份由 014 migration 明确建立，已有 public identity 必须保留。
首次与后续 render 使用完全相同的状态机：

1. 捕获一致 input binding 和已提交 pointer。令 `candidate_revision = committed_revision + 1`；
   没有 pointer 时 committed revision 为 0。render 字节只能由这份捕获输入及固定 renderer
   合同产生，不夹入实时 timestamp 或可变 review state。
2. 以带域标识的 canonical hash 从 `(outcome_id, candidate_revision, input_digest)` 派生
   `publication_id`。不可覆盖的文件路径必须包含该 opaque identity，不能仅由 outcome ID 和
   revision 决定。相同输入重试得到同一 identity；输入变化得到不同 identity，即便其 candidate
   revision 仍为 2，也不会与旧 r2 orphan 争用路径。
3. 先安全发布 Markdown。目标已存在时仅在字节完全相同时复用；不同字节必须返回完整性冲突，
   不覆盖、不采用。只有 file publication 尚无 pointer commit 时，它才是 reader 不跟随的 orphan。
4. 在 writer lease 下复核来源及文件，再在单一 SQLite 事务中 CAS 比较原 pointer 和捕获的
   `input_revision/input_digest`，一起提交新 pointer、`publication_id`、`content_sha256`、
   rendered input binding、`state = awaiting_review` 与新 committed revision。**只有该 commit
   才递增 brief revision**。CAS 不匹配或提交失败时保留当前已提交 pointer（包括竞争者已经
   提交的版本），不得退回捕获时的旧 pointer；已发布文件保留，仅未被已提交 pointer 引用的
   publication 才是 orphan。若同输入竞争者已提交同一 publication，它仍是有效投影。
5. pointer 前中断后，相同输入可按完全相同的字节收养 orphan；输入改变则使用新的 publication
   identity，旧 orphan 保留。pointer 后但响应前中断，reader 必须在新进程看到已经提交的版本；
   不得靠再次 render 才使它有效。此规则覆盖 r1、r2 及任意后续 revision，不新增自动 orphan 清理。

每次只读访问仍须通过 containment/no-follow 与 `content_sha256` 复核已提交投影：仅可直接
确认的缺失显示 `projection_state=unavailable`，字节漂移显示 `projection_state=stale`，两者
effective state 均为 `needs_review`；权限、I/O 或路径不确定成为安全错误。输入不匹配只改变
effective review state，不把字节仍正确的投影误报为文件损坏。

#### 3.5.3 旧数据的证明边界

W3 已按[迁移冻结方案](../specs/database/生命周期一致性迁移冻结方案-2026-10.md) 实现
014/schema `1.2.8` 的 private-work-copy 迁移；原 013/schema `1.2.7` 不变。
升级时不能把“当前 input”补填为历史 brief 的 rendered input 以保留 approved。不能证明
历史绑定的行应保留原 pointer/文件与历史 state，标记 binding 未验证；有效状态为 `needs_review`，
在显式重新 render/review 前不可批准。测试只操作合成旧 schema；直接 v2 read 遇旧 schema
返回升级要求，不自动迁移。真实数据升级仍须独立授权，本次未执行。字段/事务细节见
[SQLite Schema 规范](../specs/database/SQLite_Schema完整规范.md)。

这避免把高度结构化的 evidence graph 塞进 Entry Front Matter，也避免把 Outcome Markdown 混入
现有知识条目 / FTS / vector generation 的内容事实。

### 3.6 v1 不隐式调用 Provider

v1 的 evidence acquisition 默认只允许显式选择已有 public evidence 或严格 BM25 路径；不在
创建 Topic、附着 Evidence、管理 Claim、渲染或批准 Outcome 时构造 LLM / Embedding Provider。
已有 READY generation 上的 vector/hybrid evidence、自动 LLM 起草、费用预估、授权、reservation
和异步恢复必须另立 plan/confirm/execute 合同，不能借 Outcome v1 绕过 R4 的预算或 lease 规则。

## 4. 公共边界与状态机

Core 先定义 `OutcomeService` 与严格 DTO；`pkv_kernel` 再提供版本化 façade；CLI/MCP 只做
协议投影。外部 Wrapper 永远不得导入 `src.*`、Store、lease、路径或 relation internals。

v1 公开操作按以下语义分组：

| 类别 | 操作 | side effect / 约束 |
| --- | --- | --- |
| 只读 | inspect topic / get outcome / list evidence | 零 lease、零 Provider、零隐式 refresh；显示 stale/degraded。 |
| 显式 mutation | create topic / attach or detach evidence / add or revise claim / render outcome / approve or return | root writer lease、schema/locator/revision 校验、审计、stable public envelope。 |
| 禁止 | auto-claim、auto-approve、静默重抓或改绑 locator、自动 Provider 调用 | fail-closed；不以空结果或成功遮掩。 |

具体 CLI 命令、MCP Tool 名称和 Kernel capability 只在 B0 contract review 后冻结；不得先让
CLI/MCP 直接组合 SQLite、Markdown、RelationService 或 RuntimeLayout。

## 5. 失败边界

| 事实 | 外部可观察结果 | 不允许的行为 |
| --- | --- | --- |
| 没有可用 Evidence | Claim=`insufficient`，Outcome 有 limitation | 生成“已证实”结论。 |
| Evidence 来源被删或 revision 漂移 | Evidence stale，Outcome=`needs_review` | 自动重绑到最新正文。 |
| 检索 / relation 返回 degraded | 收录稳定 limitation 和 provenance | 把 degraded 伪装为完整证据。 |
| 写入竞争 | `write_busy`，零半成品 Outcome | 队列、隐式合并或覆盖另一 writer。 |
| 输入 mutation 中断 | 输入、input binding 与 brief invalidation 同事务全旧或全新 | 新输入已提交而旧 brief 仍有效 approved。 |
| Markdown 投影失败或 pointer CAS 失败 | 本次不改变当前已提交 pointer/revision；已发布但未引用的文件保留为 orphan | 先递增公开 revision、覆盖旧 orphan 或退回竞争者提交前的 pointer。 |
| 旧版本 review 请求 | 四项确认条件任一不匹配则冲突且零 review state 写入 | 自动改为批准/退回最新版。 |
| 客户端输入含路径 / URL 凭据 | Topic/question/Claim/BM25 query/候选标题均 stable invalid/error，且日志/公共 envelope 脱敏 | 回显 source body、绝对路径、凭据或 Provider 文本。 |

## 6. 分阶段实施

以下 B0–B3 描述原实施分段；其历史完成记录不关闭本次复审问题。修复按
[总计划](./生命周期一致性修复设计与分阶段计划-2026-10.md) 执行：W0 补齐规则，W1 冻结字段、
canonical digest、migration 和 review v2 签名/兼容方案；W3 已实现事务、reader、任意 revision
发布恢复和版本绑定 review。最终收口仍需本文件 OC 矩阵与同树公开进程证据；W4/W5 的预算、
恢复和 major 切换不由本阶段代替。B4 不得越过这些门禁继续扩展能力。

### B0 — Contract freeze（先行）

- 固定 Topic、Evidence、Claim、Outcome 的 schema/version、状态转移、public envelope 和
  citation/revision binding。
- 冻结 SQLite-authoritative / Markdown-projection 的原子写入与恢复策略；确定 Outcome 是否有
  独立 audit operation journal。
- 明确 `collect_evidence` 的可复用部分与严格 BM25 / 用户选择的 v1 acquisition boundary。

**退出条件：**契约、migration 草案、fault matrix、redaction rules 和 API diff 经独立 review；
没有新增 CLI/MCP mutation。

### B1 — Core persistence 与 deterministic render

- 增加 migration-owned Topic / Evidence / Claim / Outcome tables，使用 opaque ID 与严格 revision。
- 实现 locator revalidation、source drift 检查、lease-owned mutation、审计和 deterministic
  Markdown renderer。
- 用 crash / compensation / write-busy / stale-source 单元与集成测试固定不变量。

**退出条件：**任何重启都能得到同一结构状态；没有 valid Evidence 的 Outcome 无法显示为 approved。

### B2 — Application / Kernel façade

- 由 `KnowledgeApplication` 组合 OutcomeService；对外仅通过新增版本化 Kernel capability/DTO。
- 只读 API 保持零写；mutating API 只接受严格类型和 user-confirmed action。
- Kernel 不泄露 Store、path、lease、source body 或可伪造 private handle。

**退出条件：**公开 API compatibility、redaction、stale / degraded state projection 通过。

### B3 — CLI / MCP 公开闭环

- CLI 真子进程和 MCP stdio/JSON-RPC 分别覆盖 create → evidence → claim → render → review →
  fresh-process inspect。
- 每个场景使用独立 `.data-test/<scenario>`；MCP 继续只支持 stdio。
- 黑盒以 public JSON envelope / exit code / 重启后的可观察行为优先，可检查测试拥有的 durable
  SQLite ledger，但不能调用私有 Service 伪造成功。

**退出条件：**无固定端口、sleep、global Config 污染、真实 Provider/Vault/URL；source blackbox
与独立 review 通过。

### B4 — 单项 `partial-v1` 升级（后续、按真实场景）

只选择一个真实产物所需的 Tool（优先 `collect_evidence` 的 strict acquisition contract），为它
建立 full 语义、oracle 和失效边界。`find_bridges`、`timeline_of`、`contrast` 分别排队，不能整体
批量升级标签。

## 7. 验收矩阵

| 场景 | 入口 | 关键断言 |
| --- | --- | --- |
| Topic / Claim 基本闭环 | Core + CLI/MCP 黑盒 | 新进程可读取相同 opaque ID、revision、状态和 citation。 |
| 无证据与反证 | Core + public envelope | `insufficient` / `contested` 明确可见，不能成为 approved factual outcome。 |
| source drift / delete | Integration + fresh process | locator 不被重绑，Outcome becomes `needs_review`。 |
| degraded retrieval | Core + adapter | limitation/provenance 保留，绝不退化为空成功。 |
| writer race / crash | Core fault tests | 无双写、无半发布 Markdown、无假批准。 |
| brief projection drift / delete | Core + fresh CLI process | SQLite pointer 的 contained Markdown/digest 必须复核；`projection_state=stale/unavailable` 与 effective `needs_review`，不信任遗留 `approved`。 |
| public redaction | CLI/MCP blackbox | 无绝对路径、URL credential、source body 或私有异常泄露。 |
| offline discipline | 全部自动化 | 只经 `scripts/run-test.ps1`、独立 `.data-test`、零真实 Provider / Vault / URL。 |

### 2026-10 一致性修复验收合同

下列 ID 是固定验收项，不能以历史通过数替代。进程内 fault injection 验证每个提交边界；标为
跨进程的项还必须用真实独立 CLI/MCP 或受控子进程与 barrier/事件同步验证，不能仅新建同进程
Application 或用 sleep 模拟。所有数据、故障工件与日志只在独立 `.data-test` 中。

| ID | 场景与入口 | 必须满足的 oracle |
| --- | --- | --- |
| OC-01 | 每类 input mutation；事务中各语句后和 commit 前注入故障 | 输入行/边、input revision/digest、brief needs_review 全部回滚；不得观察到混合状态。 |
| OC-02 | input mutation commit 后响应前终止；另一进程读取 | 新输入、恰好递增一次的 input revision 与 needs_review 同时可见；无需重试修复。 |
| OC-03 | 旧 brief 缺 rendered input binding，或 binding 与当前输入不符 | 即使 stored state=approved 且 Markdown digest 正确，read effective state=needs_review，review 拒绝；读取零写。 |
| OC-04 | r1、r2、rN 的文件发布后/pointer commit 前终止；相同输入在新进程重试 | 相同 publication identity 和字节可收养；只产生一次 pointer revision 前进，既有文件不覆盖。 |
| OC-05 | 与 OC-04 同一切点，但随后改变输入；另覆盖 A→B→A 与 renderer 合同版本变更 | 新 input digest 产生不同 publication identity；重启可发布，旧 orphan 字节不变，无永久路径冲突。 |
| OC-06 | barrier 后另一 writer 改 input/pointer；另覆盖同 input/publication 并发 render、pointer commit 后响应前终止 | CAS 输家不覆盖/回退已提交 pointer；竞争者引用的同一 publication 仍有效，不误判 orphan；commit 后 fresh process 直接读到新提交，revision 不提前递增。 |
| OC-07 | 进程 A 审阅 r1，进程 B 生成 r2；另覆盖 B 只改输入尚未 render | A 的旧确认元组均失败，不能批准/退回 r2，也不能批准旧输入的 r1；零 review state 写入。 |
| OC-08 | 精确当前确认元组 approve/return；同元组重复请求、后续状态转换及新 revision | 合法请求只改变目标 review state；仅当前仍为该动作目标状态才幂等，不增 input/brief revision；旧请求不撤销后续状态转换、不作用于新版本。 |
| OC-09 | source drift/delete、投影改字节/缺失、EACCES/EIO 与不确定路径 | drift/missing 保留既有显式降级；未知错误 fail-closed；正确的版本元组也不能绕过复核。 |
| OC-10a | W3 新 review 协议、v2 准备与 major-1 兼容弃用阶段 | 新协议完整传递四项确认字段，兼容阶段有规定的 DeprecationWarning；不静默改变 major-1 必填参数。只证明准备完成，R04 仍为 known_gap。 |
| OC-10b | W5 实际切换 major 2 后的 SDK 握手、CLI/MCP 旧无版本 review 与 v2 公开调用 | 拒绝 major-1 握手及无版本 stub 并给出迁移错误；绝不批准 latest，v2 通过真实公开进程闭环。此证据与关联验收齐备后才可关闭 R04。 |
| OC-11 | 并发 reader 在 input transaction/pointer transaction 两侧读取 | bundle 来自同一 DB read snapshot；input binding 与 effective state 一致；零 lease、零状态/投影写入。 |
| OC-12 | 合成 schema 1.2.7 升级、升级中断重启、缺字段/摘要不明的历史 brief | 保留既有 public ID/pointer/文件，不伪造历史 rendered binding；未知绑定需重 render/review；非授权 read 不隐式迁移。 |

## 8. 需要产品裁决的事项

推荐默认如下；任何偏离都会改变 B0/B1 的范围：

1. **首个产物：**`research_brief`，而不是自由编辑的长文、聊天回答或通用项目管理器。
2. **证据获取：**v1 使用用户选择 / strict BM25；vector-hybrid 或 LLM 草拟另开确认与费用合同。
3. **审批：**所有 Outcome revision 默认 `awaiting_review`；批准不回写知识库事实。
4. **内容漂移：**不复制 source body；发现 drift 后一律 `needs_review`。
5. **结构存储：**SQLite authoritative + deterministic Markdown projection；Outcome 不进现有 Entry/FTS/vector。

## 9. 明确非目标

- 不做自动写作、自动事实判定、自动批准、长期后台 worker、Q2 public resume 或 daemon。
- 不做 GUI、图谱可视化、多人协作、云同步、Node、Docker、真实 Vault/URL/Provider 验证。
- 不解锁 held Artifact/release compliance hold，也不将 source acceptance 写成 release acceptance。
- 不将 `partial-v1` 探索能力整体升级或以 Outcome 输出掩盖其限制。
