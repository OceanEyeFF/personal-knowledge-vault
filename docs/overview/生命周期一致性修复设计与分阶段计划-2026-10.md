## 3. 必须一致的跨模块规则

### 3.1 身份、确认与版本

新网络 rebuild 的公共 plan identity 必须显式包含稳定的 `data_root_identity_sha256`、
`runtime_snapshot_sha256`、source digest/count、active pointer/manifest、Embedding contract、
policy fingerprint、action/schema version、force 与 `budget_check_period`。预算检查期间
包含 timezone/local_day/local_month，进入用户确认的 plan identity；跨期必须重新展示并
确认。material-transition replay key 排除 force 与该期间，不能因跨午夜或 force 切换而给
仍 active/awaiting_publish 的同一工作重复调用 Provider。snapshot 指纹来自已经验证无密钥的
runtime snapshot 原始字节，并与发布 CAS 使用同一 revision；不得对用户秘密配置生成公开
可验证指纹。Core 的进程私有 Config-source HMAC 继续负责一次执行内的漂移检测，但不能
替代跨进程根与状态绑定。安全哈希不授予路径访问权。publish-only plan 绑定原 operation
及当前发布材料，不以新预算期间开启第二次网络执行或预留。

review 确认元组为 `outcome_id + expected_revision + content_sha256 +
expected_input_revision`，只能来自用户实际审阅的 DTO。批准和退回都不得在参数缺失或
过期时读取最新版并代为确认。校验、状态变更及对应持久凭据在同一事务内完成。
同一确认元组且已处于相同目标状态时可幂等返回；`returned` 是该 brief revision 的审阅
终态，重新批准必须先生成新 revision，不能让旧确认重放改变后续审阅决定。

### 3.2 Outcome 原子输入与任意版本发布

Topic 持有 `input_revision/input_digest`；brief 保存
`rendered_input_revision/rendered_input_digest`。影响渲染的 Topic/Evidence/Claim mutation
必须在同一 SQLite 事务内修改输入、递增 input_revision、刷新 digest 并使现有 brief
`needs_review`。writer lease 不能代替这项原子性。只读 bundle 使用一致的 SQLite snapshot，
再复核外部证据与投影；发现输入绑定不匹配时不能继续显示 approved。
Topic 创建事务预留稳定 outcome_id 并记录 render_contract_version；真实输入变化才递增 input_revision，no-op、
render 和 review 不自行递增。input digest 覆盖 input_revision 与 renderer/template 版本，
因此 A→B→A 不会误收养旧输入的发布文件。普通 render 使用 Topic 持久绑定的
render_contract_version；升级后该版本不可用时须明确拒绝，并进入受控输入合同迁移或
重新生成计划，不能更换 renderer 却沿用旧 digest。

任意 revision 的发布顺序为：捕获一致输入 → 确定 candidate revision 与 publication_id →
发布不可覆盖 Markdown → 事务内重检 input/previous pointer → CAS 提交新 pointer。
`publication_id` 绑定 outcome、candidate revision 与 input digest；输入摘要含版本化的
renderer 规则和 input_revision，不包含审批状态、读取时间等易变观察值。
同输入重试只能收养字节相同的完整 orphan；新输入生成不同 publication_id。当前可见 revision
只在 pointer 提交时推进。不能为绕过 orphan 而覆盖旧文件、跳过完整性检查或修改旧 pointer。
CAS 竞争失败必须保留竞争者当前已提交的 pointer，不回退为本操作捕获时的旧 pointer。

旧 schema 不具有这些绑定时，不得凭当前内容猜测历史批准对象。迁移必须有显式计划；
无法证明的 brief 进入 needs_review/待重新生成。迁移号与物理 schema 在 W1 冻结，该阶段
没有修改 013 或执行迁移。W3 已新增 `014`，在合成 fixture 验证 schema `1.2.8`：保留旧
brief 的 state、版本、pointer 与字节，标记 legacy_unverified，不制造历史绑定或 receipt。
真实用户数据迁移仍未执行。

### 3.3 手动重建的前置拒绝与发布继续

本节为 W4 的冻结规范，现已实现并完成范围验收，完整运行与去重证据见 W4 实施记录；
W3 的历史 Outcome 证据不代替下列恢复、proof 或预算能力的独立验收。

A 阶段取锁失败仍是零 Provider、零 operation reservation、零 stage 的前置 `write_busy`。
B/C 完成后 D 取锁失败，属于已有操作的发布等待，不能声称 Provider 从未执行，也不能把
已退出请求永久表示成正在运行。

C 只可在窄 stage grant 内封存 publish-ready proof，绑定 operation/root/plan/source/contract、
generation manifest 与全部 artifact digest，以及最小用量事实；不写正文、凭据或共享 ledger。
未取得根 lease 时，不能为更新状态而写共享 ledger、snapshot、audit 或日志。只读 inspect
通过有效完整 proof 与当前 pointer 推导 effective `awaiting_publish`；下一次获得 lease 后
才协调持久 ledger。无完整 proof 的 B/C 强杀场景仍属于已明确后置的恢复范围，不能伪装为
awaiting_publish。

publish-only 继续必须经过独立 operation inspect → publish plan → 用户确认 → execute，
携带原 operation_id 与当前可验证计划；它只重检、结算和发布，不新建 Provider、不再预留
同一笔用量。stage grant 到期禁止继续写，不能让合法封存的 proof 永远失去验证/采用路径；
重新采用须有新的发布权限和完整验证。根、source、contract 或 pointer 漂移时终结该发布
尝试或进入明确 repair，并处理已发生用量，不自动重新嵌入。

费用记录区分本地估算、Provider usage 与未知事实。不得把 unknown 当零，也不能因无租约
而无权写入时伪称已释放预算。新一次已授权写入中的 reconciliation 必须处理该 operation
的已完成/待发布/失败事实；正常 D 争锁不能依赖后台 daemon 或手工修改 ledger 才恢复。

预算拒绝若没有 Provider effect、没有 reservation、没有可发布 stage，只记录拒绝事实，
不永久占用 material replay 身份。新的显式提交按当前时区的日/月额度重新预检；
仍超限仍拒绝，额度恢复则可建立新的 operation。活跃操作、待发布操作、已完成操作及
外部影响未知操作的防重复规则分别定义，不能统一为“所有历史终态都永久 consumed”。

### 3.4 Q1 本地恢复与未来 AI retry

archive/delete/apply_ai_patch 必须经过语义一致的 Q1 执行分发。消费者只能领取能执行或能
按明确规则终结的任务；单轮 bounded drain 不得把全部额度耗在同一个没有进展的任务上。
退避、阻塞原因与独立有效任务的推进规则必须可验证。

应用已经持久化的 patch、重建本地提交凭据、推进已提交 handoff，不等于发起新的 Provider
attempt。未来显式 AI retry 基线继续约束后者；不得借修复队列饥饿恢复旧的无限自动收费。
当前 legacy task 与未来 attempt 模型不能无证明地相互接管。

## 4. 公开协议与兼容决策

当前事实为本地兼容 SDK `0.10.0`、API `1.0.0`：保留既有 v1 capabilities，已实现并声明
`kernel.traceable-outcomes.v2` 与 `kernel.embedding-rebuild.v2`。新旧符号并存；
W1 的 SDK `0.8.1` / registry 不变及 W3 的 SDK `0.9.0` 记录只属于各自冻结时点。

W5 目标采用 API-major-2 强制版本绑定的 review 协议，并拒绝旧无版本审批。
manual rebuild 的 operation inspect/publish-only 继续协议已在兼容阶段作为
`kernel.embedding-rebuild.v2` 声明。完整参数、错误码与 schema 在 W1 一次冻结，CLI/MCP
与 SDK 使用同一 DTO，不能各自补“最新版”默认值。

兼容交付必须先经过至少一个兼容 SDK 版本的弃用阶段：保留旧符号、可观察
DeprecationWarning、替代说明与目标 major；满足该阶段后才切换 major。文档声明不等于
已经完成这个版本过程。切换后的旧无版本 approve/return 调用必须明确拒绝，即使为了
诊断保留 stub 也不得批准最新版；要求 API-major-1 的 Wrapper 必须在握手阶段拒绝。
major-1 中不能静默增加必填参数或改变审批成功语义。

兼容期内旧调用的缺陷保持 known_gap，不能把 v2 新入口存在写成旧入口已安全。最终关闭
R-04 的条件包括 major 切换、旧入口拒绝、SDK/CLI/MCP 同步迁移和验收。W3 的本地兼容 build
不构成正式发布，不代替上述 W5 退出条件。

## 7. 完成定义与不变边界

文档修订完成只表示目标规则已补齐并能追踪到验收，不能关闭产品缺陷。产品修复完成
要求八项对应证据齐全，审批旧协议处理完毕，普通争锁/预算恢复/孤儿重试均可经公开入口
完成或安全终结。只有不发新 Provider 的本地恢复可以复用已有输出；任何新付费 attempt
仍受其独立确认与费用合同约束。

本计划不提前执行下一主线的 URL 谱系/immutable AI artifact，不引入 daemon、GUI、
HTTP MCP、跨平台支持、真实 Vault/凭据/迁移、PyPI 或发布。现有 Artifact/release hold、
用户配置与默认数据根政策不变。B/C 强杀后没有完整 proof 的恢复与 stage cleanup 仍需
独立设计和证据，不能用正常 D 争锁修复宣称它们已经完成。
