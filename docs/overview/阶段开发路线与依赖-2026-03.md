## 2. 总目标与总限制

### 2.1 总目标

当前路线的总目标只有一句话：

**把 PKV 从“检索型知识库”推进到“AI 可调用的可推理知识环境”。**

### 2.2 总限制

以下内容当前不作为主战场：

- 不把 GUI 作为近期主产品竞争力
- 不优先做重 UI 翻新与复杂交互体验
- 不优先做图谱可视化
- 不在关系层未定义前继续堆高阶界面功能
- 不让历史文档继续承担当前路线定义职责

---

## 3. 总依赖链

后续工作按以下顺序推进：

`Phase 0 基线校准` → `Phase A 关系层基础` → `Phase B 推理型 MCP` → `Phase C 评测与验证` → `Phase D GUI 工作台适配`

说明：

- `Phase 0` 是所有后续工作的共同前置依赖
- `Phase A` 是 `Phase B` 的硬依赖
- `Phase C` 可以在 `Phase B` 进行时同步准备样例，但正式验收依赖 `Phase B`
- `Phase D` 依赖 `Phase B` 的结果结构基本稳定

---

### 4.2 Limit

- 不全面重写历史文档
- 不在本阶段设计新功能
- 不追求一次性清理所有遗留文档

### 4.3 Priority

1. 盘点代码真实能力边界
2. 对照 README、PRD、架构、战略文档找关键 mismatch
3. 输出“当前事实基线”文档
4. 输出差异清单与真相源层级
5. 固定后续 Phase 的文档更新规则

### 4.4 Dependencies

- 无上游依赖
- 是 Phase A/B/C/D 的共同前置依赖

### 4.5 Deliverables

- `当前事实基线-2026-03.md`
- `文档与代码差异清单-2026-03.md`
- 差异清单
- 真相源层级与更新规则

### 4.6 Exit Criteria

- 核心文档与代码的关键冲突已被显式标记
- 后续开发有统一引用的静态上下文
- 真相源优先级明确
- 后续增量更新流程明确

## 5. Phase A：Relation Foundation（当前开发 Phase 1）

说明：

- 当前准备启动的 `Phase 1` 默认指本节的 `Phase A`
- `docs/history/prompts/PHASE1_DEV_PROMPT.md` 中的旧 `Phase 1` 已归档完成，不再作为当前实施计划
- 当前分支名若仍使用 `phase1-*`，其语义也应理解为“当前路线里的 Phase A”，而不是历史归档中的旧 `Phase 1`
- 后续如需继续拆分分支，优先使用 `phase-a-*`、`phase-b-*` 或直接使用能力名，避免和历史阶段命名重叠

当前状态（2026-03-31）：

- `Batch 1 / T1+T2` 已完成：关系模型、关系存储、迁移脚本与迁移健康检查已落地
- `Batch 2 / T3` 已完成：Markdown 显式链接、Front Matter `related_docs`，以及 Front Matter 关系字段 `children` / `version_of` 的低歧义关系抽取与 backfill 路径已落地
- `Batch 3 / T4+T5` 已完成：内部一跳 relation query service 与最小验证闭环已落地
- `Batch 4 / T6` 已进入收尾：`README`、事实基线、路线文档、`CHANGELOG`、关系层模块设计文档与接口契约文档已同步当前实现边界
- 当前工作区在 `T6` 之外，额外补上了 `query_subgraph` 作为 `Phase B` 的最小起步能力

过渡归属说明：

- 这批改动的**主归属**应按 `Phase A` 收尾理解，因为它仍在固定边界、补齐文档、建立回归基线
- `query_subgraph` 只应视为 `Phase B` 的 **bootstrap / kickoff baseline**，不是 `Phase B` 已整体启动或已形成稳定对外能力
- 如果后续需要拆提交说明，建议把它表述为：`Phase A closeout with Phase B bootstrap`

### 5.1 Target

- 让“关系”成为系统一等数据
- 建立关系抽取、存储、查询的最小可演化底座

### 5.2 Limit

- 不优先做图谱可视化
- 不追求第一版覆盖全部关系类型
- 不在基础模型未稳定前做复杂推理编排
- 不在第一版引入图数据库或新的主存储
- 不在 relation query service 稳定前直接暴露高阶 MCP Tool

### 5.3 Priority

1. 定义 relation types 与统一结果结构
2. 设计基于现有 `SQLite + Markdown` 的 relation schema / storage model
3. 定义第一版 relation extraction sources 与边界
4. 实现内部 relation query service
5. 准备最小测试数据、回填路径和示例查询

### 5.4 建议的第一版关系范围

- 显式关系：链接、引用、标签、来源、时间
- 结构关系：主题层级、系列内容、版本演化

第二版再扩：

- 语义关系：相似、对比、补充、争议、因果
- 工作流关系：摘要、任务、审核、评论等派生链路

补充约束：

- 第一版优先使用当前仓库中可稳定提取的静态信号，例如 `tags`、`source_url`、Markdown 显式链接、Front Matter 字段和已存在的派生元数据
- 第一版不把 AI 推断出的语义关系当作主线依赖，只为后续扩展预留 schema 和 source 标记

### 5.5 建议的首轮实施顺序

1. 先补关系层设计与返回结构，明确 relation type、direction、source、evidence、weight 等核心字段
2. 再落 SQLite relation schema / migration，确保可增量写入、可回填、可按来源清理
3. 然后实现第一版 relation extraction / backfill，只覆盖显式关系和结构关系
4. 在数据稳定后实现内部 relation query service，先服务代码内部调用与测试，不急于暴露 MCP 接口
5. 最后补最小样例集、黑盒/集成测试和示例查询，作为进入 `Phase B` 的门槛

### 5.6 Dependencies

- 依赖 `Phase 0` 的静态上下文
- 为 `Phase B` 提供唯一可靠底座

### 5.7 Deliverables

- 关系类型与结果结构说明
- 关系存储结构或迁移脚本
- 第一版 relation extraction / backfill 实现
- 内部 relation query service
- 对应测试样例与示例查询

### 5.8 Exit Criteria

- 至少两类第一版关系可稳定落库、可查询
- 关系抽取、存储、查询边界明确，且不依赖 GUI 或高阶 MCP 包装
- 内部 relation query service 可以返回稳定且可解释的关系结果
- 已有最小样例集和自动化验证，能支撑进入 `Phase B`
- 系统不再只能依赖向量近邻表达“关联”

### 5.9 任务拆分（建议 T1-T6）

#### T1. 关系模型与结果结构定义

目标：

- 固定第一版 relation type、source type、direction、evidence、weight 等核心字段
- 定义内部 query service 的统一返回结构

建议落点：

- `src/relations/` 或 `src/knowledge_graph/` 模块骨架
- 对应设计说明同步到架构或接口文档

建议产物：

- `models.py` 或等价结构定义
- 第一版 relation type 清单
- query result schema 草案

完成标准：

- 显式关系和结构关系都有明确枚举与字段约束
- 后续 `Phase B` 不需要重新发明返回结构

#### T2. 关系存储 Schema 与迁移

目标：

- 基于当前 `SQLite` 底座落最小可演化的关系存储
- 支持增量写入、幂等回填、按 source 清理

建议落点：

- `scripts/migrations/`
- `src/storage/sqlite_store.py`
- 如有必要，新增 `src/storage/relation_store.py`

建议产物：

- 第一版 `knowledge_relations` 主表
- 必要索引与版本迁移脚本
- 最少量的 SQLite 读写封装

完成标准：

- 迁移脚本可重复执行
- 至少支持 relation insert / upsert / list by knowledge_id / filter by relation_type
- 不引入新的主存储或图数据库依赖

#### T3. 第一版 Relation Extraction 与 Backfill

目标：

- 从当前稳定可得的数据中提取第一版关系
- 为历史知识条目提供一次性或可重复执行的 backfill 路径

建议信号源：

- Markdown 显式链接
- Front Matter 字段（如 `tags`、`related_docs`、来源信息）
- SQLite 中已有元数据（`source_url`、`archived_at`、标签映射）

建议落点：

- `src/relations/extractors.py` 或等价模块
- `scripts/` 下的回填脚本
- 必要时补充 `MarkdownStore` / `SQLiteStore` 的辅助读取能力

完成标准：

- 第一版至少覆盖显式关系和结构关系中的最小子集
- backfill 可在测试环境跑通
- 对重复执行、坏数据、缺字段有可预期降级

#### T4. 内部 Relation Query Service

目标：

- 为后续 `query_subgraph`、`explain_relation`、`collect_evidence` 提供内部查询底座
- 先面向代码内部调用，不急于暴露 MCP Tool

建议能力范围：

- `get_neighbors(seed, relation_types, limit)`
- `get_relations_between(a, b)`
- `list_relations(seed, source, direction)`

建议落点：

- `src/relations/query_service.py` 或等价模块
- 与 `src/mcp/tools.py` 解耦，避免直接把 MCP 参数层当作内部模型

完成标准：

- 返回结构稳定
- 查询边界明确
- 可被单元测试和集成测试直接调用

当前实现状态（2026-03-09）：

- 已新增 `src/relations/query_service.py`
- 当前只支持一跳查询：`list_relations`、`get_neighbors`、`get_relations_between`
- 当前不做 BFS、多跳扩展、路径推理或 MCP 暴露
- 查询结果优先按 `relation_type` 分组，组内按稳定规则排序

#### T5. 测试样例与验证闭环

目标：

- 为 `Phase A` 建立最小但可信的验证集
- 确保关系层不是“写了表和接口但没有真实行为”

建议落点：

- `tests/unit/`：模型、存储、抽取器、query service
- `tests/integration/`：SQLite schema + backfill + service 联通
- `tests/fixtures/`：关系样例 Markdown / metadata 数据

完成标准：

- 至少覆盖迁移、抽取、查询三类核心路径
- 包含正常样例、重复样例、缺字段样例、坏链接样例
- 能作为进入 `Phase B` 的回归基线

当前实现状态（2026-03-09）：

- 已新增 `tests/unit/test_relation_query_service.py`
- 已新增 `tests/integration/test_relation_query_pipeline.py`
- 当前已覆盖 `migration -> backfill -> query` 联通路径
- 关系层回归集当前为 24 个测试通过，可作为进入 `Phase B` 前的最小回归基线
- 当前工作区已进一步补充两跳子图查询单测与 `backfill -> query_subgraph` 集成验证

#### T6. 文档同步与 Phase B 交接面

目标：

- 固定 Phase A 产出边界
- 为下一阶段高阶 MCP Tool 明确输入条件

建议落点：

- `README.md`
- `docs/overview/当前事实基线-2026-03.md`
- `docs/operations/CHANGELOG.md`
- 相关模块文档

完成标准：

- 已实现关系类型、数据边界、测试状态都有明确记录
- `Phase B` 的输入不再依赖聊天记录或隐含假设

### 5.10 推荐执行批次

- `Batch 1`：T1 + T2
- `Batch 2`：T3
- `Batch 3`：T4 + T5
- `Batch 4`：T6

说明：

- `T1` 不完成，`T2/T3/T4` 都容易反复返工
- `T3` 完成前，不建议开始任何对外 MCP 接口设计
- `T5` 不应拖到 Phase B 再补，否则高阶 Tool 会建立在不稳定底座上

## 6. Phase B：Reasoning MCP

### 6.1 Target

- 把 MCP 从“检索型工具集”升级成“可推理知识接口”
- 让 AI Agent 能进行多跳探索、关系解释与证据聚合

### 6.2 Limit

- 不一次性实现全部高阶 Tool
- 不把复杂 Agent 编排作为当前目标
- 不继续扩张 GUI 聊天能力来替代接口能力

### 6.3 Priority

第一优先级：

1. `query_subgraph(query, depth, relation_types)`
2. `explain_relation(a, b)`
3. `collect_evidence(question)`

第二优先级：

1. `find_bridges(seed, top_k)`
2. `timeline_of(topic)`
3. `contrast(topic_a, topic_b)`

### 6.4 Dependencies

- 强依赖 `Phase A` 的 relation query service
- 返回结构会成为 `Phase C` 和 `Phase D` 的输入
- `chunk` 证据层的定位明确为“长文档加速与定位”，不作为所有短文档的默认路径

当前实现状态（2026-03-11）：

- 已在 `src/relations/query_service.py` 增加内部 `query_subgraph(seed, depth, relation_types)` 基础能力
- 已补上内部 `explain_relation(a, b)` 最小解释能力，可返回直接关系或受限跳数内的最短解释路径
- 已新增 `src/relations/evidence_service.py`，提供文档级 `collect_evidence(question)` 证据包聚合 v1
- 已新增只读 MCP Tool：`query_subgraph`、`explain_relation`、`collect_evidence`
- 已新增 `src/relations/exploration_service.py`，提供 `find_bridges`、`timeline_of`、`contrast` 的 partial implementation
- 当前 `collect_evidence` 仍是文档级证据包基础版，不依赖 chunk 文本落库；`find_bridges`、`timeline_of`、`contrast` 也仍是受限版本，尚未形成完整高阶推理闭环
- `chunk` 设计原则：仅对超长文档（PDF/书籍/长转录）启用分块检索与定位，小文章默认保持文档级检索

建议进入 `Phase A` 完整收尾测试前，至少执行以下回归集：

- `tests/integration/test_relations_migration.py`
- `tests/unit/test_relation_store.py`
- `tests/unit/test_relation_extractors.py`
- `tests/integration/test_relation_backfill.py`
- `tests/unit/test_relation_query_service.py`
- `tests/integration/test_relation_query_pipeline.py`
- `tests/unit/test_migration_manager_versions.py`
- `tests/unit/test_migration_health_check.py`

### 6.5 Deliverables

- 至少 3 个高价值 MCP Tool
- 对应输入/输出结构说明
- 降级与错误处理规则
- 黑盒或集成测试

### 6.6 Exit Criteria

- `query_subgraph`、`explain_relation`、`collect_evidence` 可用
- 返回结果不仅有“相关性”，还有“关系说明”与“证据来源”
- AI Agent 可以稳定消费这些结构
- 有基础自动化验证

## 7. Phase C：Evaluation and Verification

### 7.1 Target

- 建立最小但可信的验证闭环
- 证明关系层和高阶 MCP 能力不是“看起来高级”的功能

### 7.2 Limit

- 不追求学术级 benchmark
- 不在工具未稳定前过度工程化评测框架
- 不追求大而全数据集

### 7.3 Priority

1. 准备多跳查询样例集
2. 准备关系解释样例集
3. 准备证据包质量样例集
4. 定义评测维度与阈值
5. 落黑盒/集成测试

### 7.4 建议评测维度

- 命中率
- 可解释性
- 噪声控制
- 结果结构稳定性
- AI Agent 二次消费可用性

### 7.5 Dependencies

- 正式验收依赖 `Phase B`
- 样例收集可在 `Phase A/B` 期间提前准备

### 7.6 Deliverables

- 最小评测集
- 自动化测试
- 质量阈值说明
- 已知问题与误差类型总结

### 7.7 Exit Criteria

- 至少有一套固定样例集
- 核心高阶 Tool 有自动化验证
- 每个核心 Tool 有最低可接受质量线
- 后续迭代不再只靠主观体验判断效果

---

## 8. Phase D：Workbench GUI

### 8.1 Target

- 给人提供最小必要的浏览、检查、调试入口
- 让关系结果和证据包可视、可查、可核对

### 8.2 Limit

- 不做重视觉打磨
- 不做复杂编辑器体验
- 不把 GUI 继续扩成主交互面
- 不反向绑架后端接口设计

### 8.3 Priority

1. 关系结果浏览
2. 证据包检查
3. 条目详情与关联路径查看
4. 配置、索引、状态、成本面板
5. 必要的归档/审核状态查看

### 8.4 Dependencies

- 依赖 `Phase B` 的结果结构基本稳定
- 依赖 `Phase C` 确认哪些结果字段值得暴露给人检查

### 8.5 Deliverables

- GUI 工作台最小适配方案
- 对应视图或交互说明
- 与 MCP/关系查询结果的映射规则

### 8.6 Exit Criteria

- 人可以检查关系结果与证据包
- GUI 能承担浏览、调试、运维职责
- 不影响主线后端能力推进

---

## 9. 跨 Phase 统一优先级

建议统一排序如下：

- `P0`：Phase 0 全部任务
- `P1`：关系类型、关系存储、关系查询服务
- `P2`：`query_subgraph`、`explain_relation`、`collect_evidence`
- `P3`：评测样例集、黑盒测试、质量阈值
- `P4`：GUI 工作台最小适配
- `P5`：桥接发现、时间线、对比分析、可视化、体验优化

## 11. 一句话总结

当前路线的关键不是“继续堆功能”，而是先固定当前事实，再按 `关系层 → 推理型 MCP → 评测 → GUI 工作台` 的依赖顺序推进，避免再次把 target、limit、priority 和 dependency 混在一起。
