## 2. 总目标与总限制

### 2.1 总目标

当前路线的总目标只有一句话：

**在已完成的可推理离线基线上，以内部自测封包验证共享应用服务与可追溯知识成果；M13 候选保持 hold，不安排正式发布。**

### 2.2 总限制

以下内容当前不作为主战场：

- 不把 GUI 作为近期主产品竞争力
- 不优先做重 UI 翻新与复杂交互体验
- 不优先做图谱可视化
- 不为发布临时扩张新的关系界面或高阶交互产品面
- 不让历史文档继续承担当前路线定义职责
- 不把真实数据验收、HTTP MCP、原地升级或三个探索 Tool 的 full 语义默认并入 M13
- 当前不安排 M13 合规收口或正式发布
- 在没有明确门禁证据前不引入常驻 Node、Docker 或云端部署

## 3. 总依赖链

后续工作按以下顺序推进：

`Phase 0 基线校准` → `Phase A 关系层基础` → `Phase B 推理型 MCP` → `Phase C 评测与验证` → `M13/W1 安全底座` → `M13/W2 功能合同` → `M13/W3-T0 Test 治理` → `M13/W3 打包链` → `M13/W4 Artifact 验收` → `P1-A 共享应用服务与内部自测包（已完成）` → `P1-C GUI 模块拆分（已完成）` → `S0/K1a 公开 Kernel 合同` → `K2 配置快照 / reload hardening` → `K1b 本地 wheel / clean-install 验证（内部验证完成）` → `R1 配置 / 数据布局` → `R2 runtime 生命周期` → `R3 受支持业务/数据 mutation lease / 审计` → `R4 staged Embedding（runtime-internal）` → `P1 R3.1 日志 / legacy writer 与按需 public rebuild adapter gate` → `P1-B 知识成果能力` → `P3 可选 Node` → `P4 可选 Docker/云端`

说明：

- `Phase 0` 是所有后续工作的共同前置依赖
- `Phase A` 是 `Phase B` 的硬依赖
- `Phase C` 可以在 `Phase B` 进行时同步准备样例，但正式验收依赖 `Phase B`
- M13 默认只验收现有 GUI；原 `Phase D` 的关系结果/证据包增量视图不自动纳入，如需启用必须先进入发布范围并补齐 W2 合同与 W4 Artifact 验收
- 截至 2026-08-01，Phase B citation/`partial-v1` 最小交付与 Phase C 固定离线评测已完成；M13 当前执行顺序为 W1 → W2 → W3-T0 → W3 → W4
- 真实快照验证是独立受控分支，必须先取得用户明确授权并完成 U1/G8；只有 migration 场景另需 FT5，M13 不等于真实数据验收

### 5.1 Target

- 让“关系”成为系统一等数据
- 建立关系抽取、存储、查询的最小可演化底座

### 5.2 Limit

- 不优先做图谱可视化
- 不追求第一版覆盖全部关系类型
- 不在基础模型未稳定前做复杂推理编排
- 不在第一版引入图数据库或新的主存储
- 不在 relation query service 稳定前直接暴露高阶 MCP Tool

### 5.3 Priority

1. 定义 relation types 与统一结果结构
2. 设计基于现有 `SQLite + Markdown` 的 relation schema / storage model
3. 定义第一版 relation extraction sources 与边界
4. 实现内部 relation query service
5. 准备最小测试数据、回填路径和示例查询

### 5.4 建议的第一版关系范围

- 显式关系：链接、引用、标签、来源、时间
- 结构关系：主题层级、系列内容、版本演化

第二版再扩：

- 语义关系：相似、对比、补充、争议、因果
- 工作流关系：摘要、任务、审核、评论等派生链路

补充约束：

- 第一版优先使用当前仓库中可稳定提取的静态信号，例如 `tags`、`source_url`、Markdown 显式链接、Front Matter 字段和已存在的派生元数据
- 第一版不把 AI 推断出的语义关系当作主线依赖，只为后续扩展预留 schema 和 source 标记

### 5.5 建议的首轮实施顺序

1. 先补关系层设计与返回结构，明确 relation type、direction、source、evidence、weight 等核心字段
2. 再落 SQLite relation schema / migration，确保可增量写入、可回填、可按来源清理
3. 然后实现第一版 relation extraction / backfill，只覆盖显式关系和结构关系
4. 在数据稳定后实现内部 relation query service，先服务代码内部调用与测试，不急于暴露 MCP 接口
5. 最后补最小样例集、黑盒/集成测试和示例查询，作为进入 `Phase B` 的门槛

### 5.6 Dependencies

- 依赖 `Phase 0` 的静态上下文
- 为 `Phase B` 提供唯一可靠底座

### 5.7 Deliverables

- 关系类型与结果结构说明
- 关系存储结构或迁移脚本
- 第一版 relation extraction / backfill 实现
- 内部 relation query service
- 对应测试样例与示例查询

### 5.8 Exit Criteria

- 至少两类第一版关系可稳定落库、可查询
- 关系抽取、存储、查询边界明确，且不依赖 GUI 或高阶 MCP 包装
- 内部 relation query service 可以返回稳定且可解释的关系结果
- 已有最小样例集和自动化验证，能支撑进入 `Phase B`
- 系统不再只能依赖向量近邻表达“关联”

### 5.9 任务拆分（建议 T1-T6）

#### T1. 关系模型与结果结构定义

目标：

- 固定第一版 relation type、source type、direction、evidence、weight 等核心字段
- 定义内部 query service 的统一返回结构

建议落点：

- `src/relations/` 或 `src/knowledge_graph/` 模块骨架
- 对应设计说明同步到架构或接口文档

建议产物：

- `models.py` 或等价结构定义
- 第一版 relation type 清单
- query result schema 草案

完成标准：

- 显式关系和结构关系都有明确枚举与字段约束
- 后续 `Phase B` 不需要重新发明返回结构

#### T2. 关系存储 Schema 与迁移

目标：

- 基于当前 `SQLite` 底座落最小可演化的关系存储
- 支持增量写入、幂等回填、按 source 清理

建议落点：

- `scripts/migrations/`
- `src/storage/sqlite_store.py`
- 如有必要，新增 `src/storage/relation_store.py`

建议产物：

- 第一版 `knowledge_relations` 主表
- 必要索引与版本迁移脚本
- 最少量的 SQLite 读写封装

完成标准：

- 迁移脚本可重复执行
- 至少支持 relation insert / upsert / list by knowledge_id / filter by relation_type
- 不引入新的主存储或图数据库依赖

#### T3. 第一版 Relation Extraction 与 Backfill

目标：

- 从当前稳定可得的数据中提取第一版关系
- 为历史知识条目提供一次性或可重复执行的 backfill 路径

建议信号源：

- Markdown 显式链接
- Front Matter 字段（如 `tags`、`related_docs`、来源信息）
- SQLite 中已有元数据（`source_url`、`archived_at`、标签映射）

建议落点：

- `src/relations/extractors.py` 或等价模块
- `scripts/` 下的回填脚本
- 必要时补充 `MarkdownStore` / `SQLiteStore` 的辅助读取能力

完成标准：

- 第一版至少覆盖显式关系和结构关系中的最小子集
- backfill 可在测试环境跑通
- 对重复执行、坏数据、缺字段有可预期降级

#### T4. 内部 Relation Query Service

目标：

- 为后续 `query_subgraph`、`explain_relation`、`collect_evidence` 提供内部查询底座
- 先面向代码内部调用，不急于暴露 MCP Tool

建议能力范围：

- `get_neighbors(seed, relation_types, limit)`
- `get_relations_between(a, b)`
- `list_relations(seed, source, direction)`

建议落点：

- `src/relations/query_service.py` 或等价模块
- 与 `src/mcp/tools.py` 解耦，避免直接把 MCP 参数层当作内部模型

完成标准：

- 返回结构稳定
- 查询边界明确
- 可被单元测试和集成测试直接调用

当前实现状态（2026-03-09）：

- 已新增 `src/relations/query_service.py`
- 当前只支持一跳查询：`list_relations`、`get_neighbors`、`get_relations_between`
- 当前不做 BFS、多跳扩展、路径推理或 MCP 暴露
- 查询结果优先按 `relation_type` 分组，组内按稳定规则排序

#### T5. 测试样例与验证闭环

目标：

- 为 `Phase A` 建立最小但可信的验证集
- 确保关系层不是“写了表和接口但没有真实行为”

建议落点：

- `tests/unit/`：模型、存储、抽取器、query service
- `tests/integration/`：SQLite schema + backfill + service 联通
- `tests/fixtures/`：关系样例 Markdown / metadata 数据

完成标准：

- 至少覆盖迁移、抽取、查询三类核心路径
- 包含正常样例、重复样例、缺字段样例、坏链接样例
- 能作为进入 `Phase B` 的回归基线

## 6. Phase B：Reasoning MCP

### 6.1 Target

- 把 MCP 从“检索型工具集”升级成“可推理知识接口”
- 让 AI Agent 能进行多跳探索、关系解释与证据聚合

### 6.2 Limit

- 不一次性实现全部高阶 Tool
- 不把复杂 Agent 编排作为当前目标
- 不继续扩张 GUI 聊天能力来替代接口能力

### 6.3 Priority

第一优先级：

1. `query_subgraph(query, depth, relation_types)`
2. `explain_relation(a, b)`
3. `collect_evidence(question)`

第二优先级：

1. `find_bridges(seed, top_k)`
2. `timeline_of(topic)`
3. `contrast(topic_a, topic_b)`

### 6.4 Dependencies

- 强依赖 `Phase A` 的 relation query service
- 返回结构会成为 `Phase C` 和 `Phase D` 的输入
- `chunk` 证据层的定位明确为“长文档加速与定位”，不作为所有短文档的默认路径

当前实现状态（2026-07-31）：

- 已在 `src/relations/query_service.py` 增加内部 `query_subgraph(seed, depth, relation_types)` 基础能力
- 已补上内部 `explain_relation(a, b)` 最小解释能力，可返回直接关系或受限跳数内的最短解释路径
- 已新增 `src/relations/evidence_service.py`，提供 chunk-aware `collect_evidence(question, include_chunks=False/True)` 证据包聚合能力，并保持默认文档级兼容
- 已新增只读 MCP Tool：`query_subgraph`、`explain_relation`、`collect_evidence`
- 已新增 `src/relations/exploration_service.py`，并按 `partial-v1` 口径交付 `find_bridges`、`timeline_of`、`contrast`；公开响应仍诚实声明 `implementation_level=partial`
- 当前 `collect_evidence` 已支持 chunk-aware 路径与文档级兼容路径，并通过 `chunk_retrieval_status` 区分 `success` / `no_hits` / `path_unavailable` / `search_error`；三个探索 Tool 的 citation/provenance 最小合同已收口，但并非 full 语义实现
- Phase B citation 合同已通过固定评测交接 Phase C；真实库回填/快照验收尚未执行，需用户明确授权与 U1/G8，其中 migration 场景另需 FT5
- `chunk` 设计原则：仅对超长文档（PDF/书籍/长转录）启用分块检索与定位，小文章默认保持文档级检索

建议进入 `Phase A` 完整收尾测试前，至少执行以下回归集：

- `tests/integration/test_relations_migration.py`
- `tests/unit/test_relation_store.py`
- `tests/unit/test_relation_extractors.py`
- `tests/integration/test_relation_backfill.py`
- `tests/unit/test_relation_query_service.py`
- `tests/integration/test_relation_query_pipeline.py`
- `tests/unit/test_migration_manager_versions.py`
- `tests/unit/test_migration_health_check.py`

### 6.5 Deliverables

- 至少 3 个高价值 MCP Tool
- 对应输入/输出结构说明
- 降级与错误处理规则
- 黑盒或集成测试

## 7. Phase C：Evaluation and Verification

### 7.1 Target

- 建立最小但可信的验证闭环
- 证明关系层和高阶 MCP 能力不是“看起来高级”的功能

### 7.2 Limit

- 不追求学术级 benchmark
- 不在工具未稳定前过度工程化评测框架
- 不追求大而全数据集

### 7.3 Priority

1. 准备多跳查询样例集
2. 准备关系解释样例集
3. 准备证据包质量样例集
4. 定义评测维度与阈值
5. 落黑盒/集成测试

### 7.4 建议评测维度

- 命中率
- 可解释性
- 噪声控制
- 结果结构稳定性
- AI Agent 二次消费可用性

### 7.5 Dependencies

- 正式验收依赖 `Phase B`
- 样例收集可在 `Phase A/B` 期间提前准备

### 7.6 Deliverables

- 最小评测集
- 自动化测试
- 质量阈值说明
- 已知问题与误差类型总结

### 7.7 Exit Criteria

- 至少有一套固定样例集
- 核心高阶 Tool 有自动化验证
- 每个核心 Tool 有最低可接受质量线
- 后续迭代不再只靠主观体验判断效果

历史验收基线（2026-07-31）：

- 固定任务集为 16 tasks / 119 checks，经真实 FastMCP `list_tools` / `call_tool` / `read_resource` 链路运行
- 结果为 `overall=1.0`、`citability=1.0`、0 failed、`thresholds_met=true`

### 8.3 W1：运行时布局与数据安全底座

目标：先证明发布物不会越界写入、静默破坏或错误解释用户数据。

### 8.5 W3：短期 Test 治理与可复现打包链

#### W3-T0：短期 Test 治理门禁

目标：在正式打包前冻结测试职责和证据边界，使源码合同、打包合同与安装后 Artifact 证据不能互相冒充，并消除会污染后续用例的 Qt 进程全局状态泄漏。

依赖与顺序：

- 输入必须是已冻结并提交的 W2 source contracts；W3-T0 不重开 W2 产品语义
- W3-T0 是正式 W3 构建链的硬门禁；完成 lane/runner 合同前可以做只读调查，但不得产出 `artifact_verified` 结论
- W4 runner 和验收用例可以按已冻结的 lifecycle matrix 开始准备，实际执行仍硬依赖 W3 交付的 Artifact、安装入口、manifest 与外置 harness

三条 lane 的唯一 owner 分工：

| Lane | 唯一主责 | 可形成的证据 | 不得替代 |
|---|---|---|---|
| `source` | W1/W2 领域语义、adapter 终态、确定性 fixture 与源码级故障注入 | `source_verified`、W4 handoff 声明 | packaging contract 或安装后 Artifact 证据 |
| `packaging-contract` | 构建入口、资源 allowlist、manifest/hash/SBOM、打包配置、外置 loopback harness 合同 | clean-checkout build 与 payload/manifest 合同结果 | W2 语义重验或 `artifact_verified` |
| `artifact-only` | 只通过安装后的 GUI/CLI/MCP 入口执行 W4 lifecycle matrix | 绑定 Artifact hash、build fingerprint、runner 环境与场景日志的 W4 evidence | 源码树 smoke、直接模块调用或 handoff 声明 |

治理范围：

- 每个行为 oracle 只登记一个 owner；跨 lane 测试只核对边界交接，不复制上游内部语义断言。新用例立即执行该原则，既有重复用例只在阻塞 W3/W4 时做小范围归属调整
- `tests/contracts/m13_w4_handoffs.v1.yaml` 只表达 W2 已定义的用户路径与 `artifact_pending` handoff，不是 W4 执行记录；只有 `artifact-only` runner 实际运行对应安装产物后，才可生成或晋级 `artifact_verified` evidence
- `artifact-only` lane 缺少 Artifact、安装入口、manifest、fixture 或所需外置 harness 时必须 **fail**，不得 skip/xfail/xpass 或回退源码入口；runner 必须从仓库外 cwd 启动，清空/隔离仓库 `PYTHONPATH`，并证明进程未从仓库路径加载或 `import src`
- 所有会修改 `QSettings` 默认格式、Qt organization/application identity 或等价且具有公开读取 API 的进程全局状态的测试，必须先快照并用 fixture finalizer/`try/finally` 在 pass、fail、skip 三种退出路径恢复；`QSettings.setPath()` 因 Qt 无公开读取 API 而在自动化中禁用，恢复失败本身应使 lane 失败

### 8.6 W4：Artifact E2E、用户文档与发布审查

W3-T0 冻结、W4 执行的 Artifact-only lifecycle matrix 如下。每行都使用合成数据并绑定实际 Artifact hash；未执行前保持 `artifact_pending`，不得用 source/packaging-contract 结果代填：

| Lifecycle / capability | 安装后入口与关键动作 | 公开 oracle |

## 12. 后 M13：内部自测封包与运行时演进

详细范围与退出条件以
[后M13开发路线-2026-08.md](./后M13开发路线-2026-08.md) 为准。本节只固定跨工作包的
执行纪律：

1. M13 release 分支当前冻结；P1 source 工作不得暗中改变其证据、目录和 hold 结论。只有未来明确恢复发布时，才重新安排合规收口。
2. 日常开发封包是 `INTERNAL TEST ONLY` 的 onedir/zip 自测包，不是 test candidate 或
   release Artifact；不得写入 `dist/release/`、不得暗示可分发，也不得改变默认安装拓扑。
3. GUI 已迁至独立 `pkv-GUI`；核心不再包含 Qt 代码、GUI 测试或 GUI 封包入口，外部
   Wrapper 只能依赖 `pkv_kernel`。
4. S0/K1a 公开 `pkv_kernel` API、版本/能力握手与兼容性合同、K2 snapshot/reload、K1b 本地 wheel/clean-install 及 R1→R4 的限定运行时合同均已通过最终隔离验证。R3 覆盖受支持业务/数据 mutation，而非所有文件系统写入；R3.1 的运行时日志/legacy writer 与按需 public rebuild adapter gate 收口后，才开始可追溯知识成果。R4 不新增公共重建接口。外部 Wrapper 不得依赖相邻 checkout 或 `src.*`，这些工作均不授予正式发布或 PyPI 上线权限。
5. Node 不是 P1 的交付前提。无真实后台或并发需求时，CLI、MCP stdio 与外部 Wrapper
   继续使用 embedded Kernel 运行方式。
6. Docker 不是开发封包替代物，且必须位于 Node 之后；云端另立产品、权限与数据同步决策。
