# 阶段开发路线与依赖（2026-03）

> 文档类型：当前执行路线
> 创建日期：2026-03-06
> 目的：把当前阶段的 target、limit、priority、dependency、exit criteria 明确拆开

---

## 1. 文档定位

本文件不重复解释项目愿景，也不承担里程碑总结职责。

它只负责定义：

- 当前阶段的总目标
- 当前阶段的总限制
- 分 Phase 的任务优先级
- 任务之间的依赖关系
- 每个 Phase 的退出条件

配套静态上下文见：

- `docs/overview/当前事实基线-2026-03.md`

---

## 2. 总目标与总限制

### 2.1 总目标

当前路线的总目标只有一句话：

**把 PKV 从“检索型知识库”推进到“AI 可调用的可推理知识环境”。**

### 2.2 总限制

以下内容当前不作为主战场：

- 不把 GUI 作为近期主产品竞争力
- 不优先做重 UI 翻新与复杂交互体验
- 不优先做图谱可视化
- 不在关系层未定义前继续堆高阶界面功能
- 不让历史文档继续承担当前路线定义职责

---

## 3. 总依赖链

后续工作按以下顺序推进：

`Phase 0 基线校准` → `Phase A 关系层基础` → `Phase B 推理型 MCP` → `Phase C 评测与验证` → `Phase D GUI 工作台适配`

说明：

- `Phase 0` 是所有后续工作的共同前置依赖
- `Phase A` 是 `Phase B` 的硬依赖
- `Phase C` 可以在 `Phase B` 进行时同步准备样例，但正式验收依赖 `Phase B`
- `Phase D` 依赖 `Phase B` 的结果结构基本稳定

---

## 4. Phase 0：Baseline Alignment / Context Freeze

### 4.1 Target

- 校验当前代码、README、核心设计文档是否匹配
- 冻结一份后续开发共用的静态上下文基线
- 明确真相源层级与后续增量更新规则

### 4.2 Limit

- 不全面重写历史文档
- 不在本阶段设计新功能
- 不追求一次性清理所有遗留文档

### 4.3 Priority

1. 盘点代码真实能力边界
2. 对照 README、PRD、架构、战略文档找关键 mismatch
3. 输出“当前事实基线”文档
4. 输出差异清单与真相源层级
5. 固定后续 Phase 的文档更新规则

### 4.4 Dependencies

- 无上游依赖
- 是 Phase A/B/C/D 的共同前置依赖

### 4.5 Deliverables

- `当前事实基线-2026-03.md`
- 差异清单
- 真相源层级与更新规则

### 4.6 Exit Criteria

- 核心文档与代码的关键冲突已被显式标记
- 后续开发有统一引用的静态上下文
- 真相源优先级明确
- 后续增量更新流程明确

---

## 5. Phase A：Relation Foundation

### 5.1 Target

- 让“关系”成为系统一等数据
- 建立关系抽取、存储、查询的最小可演化底座

### 5.2 Limit

- 不优先做图谱可视化
- 不追求第一版覆盖全部关系类型
- 不在基础模型未稳定前做复杂推理编排

### 5.3 Priority

1. 定义 relation types
2. 设计 relation schema / storage model
3. 定义 relation extraction sources 与边界
4. 实现 relation query service
5. 准备最小测试数据和示例查询

### 5.4 建议的第一版关系范围

- 显式关系：链接、引用、标签、来源、时间
- 结构关系：主题层级、系列内容、版本演化

第二版再扩：

- 语义关系：相似、对比、补充、争议、因果
- 工作流关系：摘要、任务、审核、评论等派生链路

### 5.5 Dependencies

- 依赖 `Phase 0` 的静态上下文
- 为 `Phase B` 提供唯一可靠底座

### 5.6 Deliverables

- 关系层设计文档
- 关系存储结构或迁移脚本
- 内部 relation query service
- 对应测试样例

### 5.7 Exit Criteria

- 至少两类关系可落库、可查询
- 关系抽取、存储、查询边界明确
- 内部服务可以返回稳定的关系结果
- 系统不再只能依赖向量近邻表达“关联”

---

## 6. Phase B：Reasoning MCP

### 6.1 Target

- 把 MCP 从“检索型工具集”升级成“可推理知识接口”
- 让 AI Agent 能进行多跳探索、关系解释与证据聚合

### 6.2 Limit

- 不一次性实现全部高阶 Tool
- 不把复杂 Agent 编排作为当前目标
- 不继续扩张 GUI 聊天能力来替代接口能力

### 6.3 Priority

第一优先级：

1. `query_subgraph(query, depth, relation_types)`
2. `explain_relation(a, b)`
3. `collect_evidence(question)`

第二优先级：

1. `find_bridges(seed, top_k)`
2. `timeline_of(topic)`
3. `contrast(topic_a, topic_b)`

### 6.4 Dependencies

- 强依赖 `Phase A` 的 relation query service
- 返回结构会成为 `Phase C` 和 `Phase D` 的输入

### 6.5 Deliverables

- 至少 3 个高价值 MCP Tool
- 对应输入/输出结构说明
- 降级与错误处理规则
- 黑盒或集成测试

### 6.6 Exit Criteria

- `query_subgraph`、`explain_relation`、`collect_evidence` 可用
- 返回结果不仅有“相关性”，还有“关系说明”与“证据来源”
- AI Agent 可以稳定消费这些结构
- 有基础自动化验证

---

## 7. Phase C：Evaluation and Verification

### 7.1 Target

- 建立最小但可信的验证闭环
- 证明关系层和高阶 MCP 能力不是“看起来高级”的功能

### 7.2 Limit

- 不追求学术级 benchmark
- 不在工具未稳定前过度工程化评测框架
- 不追求大而全数据集

### 7.3 Priority

1. 准备多跳查询样例集
2. 准备关系解释样例集
3. 准备证据包质量样例集
4. 定义评测维度与阈值
5. 落黑盒/集成测试

### 7.4 建议评测维度

- 命中率
- 可解释性
- 噪声控制
- 结果结构稳定性
- AI Agent 二次消费可用性

### 7.5 Dependencies

- 正式验收依赖 `Phase B`
- 样例收集可在 `Phase A/B` 期间提前准备

### 7.6 Deliverables

- 最小评测集
- 自动化测试
- 质量阈值说明
- 已知问题与误差类型总结

### 7.7 Exit Criteria

- 至少有一套固定样例集
- 核心高阶 Tool 有自动化验证
- 每个核心 Tool 有最低可接受质量线
- 后续迭代不再只靠主观体验判断效果

---

## 8. Phase D：Workbench GUI

### 8.1 Target

- 给人提供最小必要的浏览、检查、调试入口
- 让关系结果和证据包可视、可查、可核对

### 8.2 Limit

- 不做重视觉打磨
- 不做复杂编辑器体验
- 不把 GUI 继续扩成主交互面
- 不反向绑架后端接口设计

### 8.3 Priority

1. 关系结果浏览
2. 证据包检查
3. 条目详情与关联路径查看
4. 配置、索引、状态、成本面板
5. 必要的归档/审核状态查看

### 8.4 Dependencies

- 依赖 `Phase B` 的结果结构基本稳定
- 依赖 `Phase C` 确认哪些结果字段值得暴露给人检查

### 8.5 Deliverables

- GUI 工作台最小适配方案
- 对应视图或交互说明
- 与 MCP/关系查询结果的映射规则

### 8.6 Exit Criteria

- 人可以检查关系结果与证据包
- GUI 能承担浏览、调试、运维职责
- 不影响主线后端能力推进

---

## 9. 跨 Phase 统一优先级

建议统一排序如下：

- `P0`：Phase 0 全部任务
- `P1`：关系类型、关系存储、关系查询服务
- `P2`：`query_subgraph`、`explain_relation`、`collect_evidence`
- `P3`：评测样例集、黑盒测试、质量阈值
- `P4`：GUI 工作台最小适配
- `P5`：桥接发现、时间线、对比分析、可视化、体验优化

---

## 10. 每个 Phase 完成后的必做更新

每个 Phase 收尾时，至少同步更新：

1. `README.md`
2. `docs/overview/当前事实基线-2026-03.md`
3. `docs/operations/CHANGELOG.md`
4. 对应模块设计文档或接口文档
5. 如路线发生变化，更新本文件

---

## 11. 一句话总结

当前路线的关键不是“继续堆功能”，而是先固定当前事实，再按 `关系层 → 推理型 MCP → 评测 → GUI 工作台` 的依赖顺序推进，避免再次把 target、limit、priority 和 dependency 混在一起。
