# 系统架构设计

> Personal Knowledge Vault - Architecture Design
> 面向当前实现与下一阶段演进的统一架构说明

**文档版本**: v2.0
**创建日期**: 2026-01-27
**最后更新**: 2026-03-06

---

## 1. 架构目标

PKV 当前架构要解决的不是单一“文档管理”问题，而是同时满足以下目标：

- 本地优先、长期可维护
- 能被人直接使用
- 能被 AI Agent 稳定调用
- 检索和归档共享同一套底座
- 支持从“混合检索”继续演化到“关系探索与多跳推理”

---

## 2. 当前总体架构

### 2.1 核心理念

当前架构可以概括为：

**多入口 + 工作流编排 + 三层存储 + 可扩展检索与关系层**

其中：

- 多入口负责接入不同用户和 Agent
- 工作流负责组织处理过程
- 三层存储负责数据主权与检索效率
- 检索与关系层负责把知识内容转化为可探索环境

### 2.2 当前架构图

```text
┌──────────────────────────────────────────────────────────────┐
│                        交互入口层                             │
│  • CLI (`pkv ...`)                                           │
│  • MCP Server (`python -m src.mcp`)                          │
│  • GUI Desktop (`python -m src.gui`)                         │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│                      工作流与服务层                           │
│  • WorkflowEngine（归档/搜索/审核等流程编排）                │
│  • Processor 路由与内容解析                                   │
│  • AI 服务（摘要、标签、Embedding、对话）                    │
│  • Review 机制（审核、修订、历史）                           │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│                     检索与知识访问层                           │
│  • BM25 Retriever                                             │
│  • Vector Retriever                                           │
│  • Hybrid Retriever                                           │
│  • QueryRouter                                                │
│  • MCP Tools / Resources / Prompts                            │
│  • 当前关联推荐（`get_related`）                              │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│                        存储层                                 │
│  • Markdown 主存储（事实源）                                 │
│  • SQLite 元数据 / FTS5 索引                                 │
│  • hnswlib 向量索引                                           │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 下一阶段扩展位

当前架构已经具备检索型知识访问能力，但关系层仍然偏薄。

建议在现有检索层之上新增：

- `relation_index` 或等价关系层
- `knowledge_graph` 风格的查询接口
- 面向 MCP 的多跳探索和证据聚合能力

这层不是替代检索，而是建立在检索之上的“知识推理中层”。

## 3. 当前入口层设计

### 3.1 CLI

职责：

- 开发与高频操作入口
- 归档、搜索、查看、统计、配置
- 适合脚本化和快速调试

特点：

- 最接近底层能力
- 调试成本低
- 是很多工作流的直接入口

### 3.2 MCP

职责：

- 向外暴露标准化知识访问接口
- 供 Claude Code、Codex、Cursor 等 AI Agent 使用

当前已形成的能力：

- 搜索
- 详情读取
- 列表浏览
- 归档
- 关联推荐

下一阶段重点：

- 从“检索接口”升级为“可推理知识接口”

### 3.3 GUI

职责：

- 图形化工作台
- 浏览、检查、调试、配置、审核的入口

当前定位：

- 不是主产品定义
- 不是近期最优先投入方向
- 主要承担 workbench/admin 角色

## 4. 工作流与服务层

### 4.1 WorkflowEngine

`src/workflow/` 是系统编排核心。

职责：

- 加载工作流配置
- 在步骤间传递上下文和状态
- 汇总日志与错误
- 统一产出 `WorkflowResult`

工作流仍然是“归档、分析、审核、存储”这些操作的骨架。

### 4.2 Processors

`src/processors/` 负责将不同来源内容解析为统一的知识条目。

当前主要处理对象：

- 微信文章
- 知乎内容
- 通用网页
- 聊天记录
- AI 对话
- 纯文本

设计原则：

- 统一输出结构
- 来源差异封装在处理器内部
- 不让上层入口关心具体解析细节

### 4.3 AI 服务

`src/ai/` 的主要职责不是“独立成层”，而是为工作流、处理器和检索提供能力支撑。

当前主要能力：

- 摘要生成
- 标签提取
- Embedding
- GUI 对话相关能力

### 4.4 审核与修订

审核系统已经进入当前实现范围，职责是补齐 AI 输出的人类可控性：

- 审核 AI 生成摘要和标签
- 添加评论
- 重新生成
- 保存历史

这部分属于“工作流完整性增强层”。

## 5. 检索与知识访问层

### 5.1 当前检索体系

当前检索体系由以下模块构成：

- `BM25Retriever`
- `VectorRetriever`
- `HybridRetriever`
- `QueryRouter`

这套体系的作用是：

- 精确查询时优先关键词
- 模糊表达时使用语义检索
- 在成本与效果之间做平衡

### 5.2 当前 MCP 访问模式

MCP 当前更接近“结构化知识访问接口”：

- `search_knowledge`
- `get_entry`
- `list_entries`
- `list_tags`
- `get_stats`
- `archive_url`
- `archive_text`
- `get_related`

当前问题：

- `get_related` 更像近邻推荐
- 缺乏关系解释
- 缺乏多跳查询
- 缺乏证据聚合

### 5.3 下一阶段：关系层与高阶 MCP

建议引入关系层之后，优先扩展下列能力：

- `query_subgraph`
- `explain_relation`
- `collect_evidence`
- `find_bridges`
- `timeline_of`
- `contrast`

目标不是堆更多接口，而是让 AI 能沿知识网络稳定探索。

## 6. 存储架构

### 6.1 当前事实

当前存储事实已经明确为：

- `Markdown`：主存储、长期事实源
- `SQLite`：元数据和全文索引
- `hnswlib`：向量索引

这里不再使用 `PostgreSQL + pgvector` 作为当前实现事实。

### 6.2 设计原则

1. 主存储可读、可迁移、可备份
2. 索引层可重建
3. 数据主权优先于部署花哨度
4. 能支持本地长期维护

### 6.3 一致性原则

- Markdown 是事实源
- SQLite 与向量索引是辅助索引层
- 索引异常时应允许重建
- 架构设计不能让索引层反过来成为数据锁定点

## 7. 当前项目目录结构

### 7.1 源代码目录

```text
src/
├── ai/            # AI 服务与提示词
├── cli/           # CLI 命令与输出
├── gui/           # 桌面 GUI 工作台
├── mcp/           # MCP Server 与工具接口
├── processors/    # 内容处理器
├── retrieval/     # 检索引擎
├── storage/       # Markdown / SQLite / 向量索引
├── utils/         # 配置、日志、文本工具
├── workflow/      # 工作流引擎与步骤
└── main.py        # CLI 入口
```

### 7.2 配置与数据目录

```text
config/
├── config.yaml
├── workflows/
└── custom_dict.txt

.data/
├── db/
├── logs/
├── vault/
└── vectors/
```

### 7.3 文档目录的当前角色

`docs/` 当前用于项目文档，不承担知识条目主存储角色。

子目录建议理解为：

- `docs/overview/`：当前核心文档
- `docs/modules/`：模块设计与专题方案
- `docs/specs/`：接口、模型与数据规范
- `docs/operations/`：使用、运维与迁移文档
- `docs/history/`：历史 Prompt、问题、讨论与里程碑记录

## 8. 当前关键数据流

### 8.1 归档流程

```text
输入（URL / 文本）
  → 处理器解析
  → AI 分析（摘要 / 标签 / Embedding）
  → 审核步骤（按配置触发）
  → Markdown 存储
  → SQLite 索引
  → 向量索引
  → 返回结果给 CLI / MCP / GUI
```

### 8.2 检索流程

```text
查询输入
  → QueryRouter 判断策略
  → BM25 / Vector / Hybrid 检索
  → 返回 SearchResult
  → 由 CLI / MCP / GUI 展示
```

### 8.3 MCP 调用流程

```text
AI Agent
  → MCP Tool / Resource
  → PKV 检索或存储能力
  → 结构化结果返回 Agent
```

### 8.4 下一阶段关系探索流程

```text
问题 / seed topic
  → 检索候选知识
  → 关系层扩展子图
  → 路径解释 / 证据聚合
  → 返回给 MCP / GUI / CLI
```

## 9. 当前架构判断

### 9.1 已经成立的部分

- CLI、MCP、GUI 三入口并存
- 工作流编排和三层存储已经稳定成形
- 混合检索已成为核心底座

### 9.2 当前最关键的不足

- 关系层尚未系统化
- MCP 仍偏“检索型”
- 高阶知识探索能力缺失

### 9.3 近期架构重点

架构上最值得优先投入的不是再扩张入口，而是补强中间层：

- 关系建模
- 关系索引
- 多跳查询
- 证据包
- 可解释路径
