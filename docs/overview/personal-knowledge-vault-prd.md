# 产品需求文档：个人知识库系统

**版本**: 1.1
**创建日期**: 2026-01-31
**最后更新**: 2026-03-06
**作者**: OceanEye & 幽浮喵

---

## 1. 执行摘要

Personal Knowledge Vault（PKV）是一个 **AI-First、本地优先、工作流驱动** 的个人知识管理系统。

它的目标不是单纯做一个“更好看的知识库界面”，而是构建一个：

- 让用户可长期掌握数据主权的知识底座
- 让 AI Agent 可以稳定调用和探索的知识环境
- 让归档、分析、检索、审核、入库形成闭环的工作流系统

项目最初解决的是“如何更高效地保存和找回内容”，当前阶段进一步要解决的是：

- AI 如何真正理解知识之间的关系
- AI 如何沿关系网络进行多跳探索
- 系统如何从“带搜索的本地文档库”升级为“可推理知识环境”

---

## 2. 当前战略补充

本 PRD 保留原始产品方向，但从 2026-03 起补充以下收敛判断：

1. `MCP` 已经是一等能力，不再是远期扩展项
2. `GUI` 已经存在，但当前定位是工作台，不是项目主战场
3. `知识关联` 不应只停留在相似推荐，下一阶段要演化为关系层与多跳检索能力
4. 近期最重要的能力建设是：
   - 关系建模
   - 高阶 MCP Tool
   - 证据聚合
   - 路径解释
   - 多跳探索

这意味着 PKV 当前的产品定义应理解为：

**一个面向 AI 与人的、本地优先的知识操作系统内核。**

## 3. 问题陈述

### 3.1 核心痛点

目标用户面临的问题主要包括：

1. 有价值内容每天都在产生，但后续难以稳定回找
2. 手工整理、写摘要、打标签、建立分类的成本过高
3. 关键词检索与纯向量检索各有明显缺陷
4. 内容之间缺乏可利用的关系网络，难以支撑系统性思考
5. AI 即使能搜索，也很难把现有知识库当作可推理环境来使用

### 3.2 现有工具不足

- Notion / 印象笔记：记录方便，但智能归档和语义检索能力不足
- Obsidian：双向链接强，但关系建立过度依赖人工
- DEVONthink：文档管理成熟，但 AI 协作能力不足
- 纯 RAG 方案：更像检索层，不天然解决知识组织、长期维护和人机协作问题

## 4. 目标用户

### 4.1 主要用户

技术背景的知识工作者，包括但不限于：

- 软件工程师
- 产品经理
- 研究员
- 技术创业者

用户共性：

- 更偏好文字阅读而非纯视频消费
- 既关心效率，也关心系统性认知
- 希望长期掌握知识资产，而不是被平台锁定
- 希望 AI 帮忙，但不接受完全黑盒化处理

### 4.2 用户期待

- 快速归档有价值内容
- 通过混合检索找回模糊记忆中的资料
- 自动发现知识之间的关联
- 在关键节点对 AI 输出进行审核与修正
- 让 AI Agent 能把知识库当作可操作环境来调用

---

## 5. 产品目标

### 5.1 主目标

- 将单条内容的整理时间压缩到 5 分钟以内
- 将常见知识检索定位时间压缩到 1 分钟以内
- 让系统具备可验证的 AI 协作与关系探索能力

### 5.2 次目标

- 保持本地优先和低部署复杂度
- 让 CLI、MCP、GUI 共用同一套知识底座
- 通过工作流与审核机制提升 AI 输出可控性

---

## 6. 核心能力定义

### 6.1 智能内容归档

系统应支持对文字内容进行归档，包括：

- 微信文章
- 知乎内容
- 通用网页
- 聊天记录
- AI 对话
- 纯文本

归档完成后，系统应尽量产出：

- 标题
- Markdown 正文
- 一句话摘要
- 100 字摘要
- 标签与关键词
- 来源信息
- 可索引的结构化元数据

### 6.2 智能混合检索

系统应支持：

- BM25 检索
- 向量检索
- 混合检索
- 自动路由

目标不是强制所有查询走统一流程，而是按查询特点选择更合适的策略。

### 6.3 MCP 知识访问能力

系统应对 AI Agent 暴露标准化能力，使其可以：

- 搜索知识库
- 读取条目详情
- 浏览列表和标签
- 触发归档
- 获取基础关联推荐

下一阶段目标是进一步支持：

- 子图查询
- 关系解释
- 证据聚合
- 多跳探索

### 6.4 知识关联与关系探索

当前能力基线是“关联推荐”，但产品目标更高：

- 不只返回相似条目
- 还要支持解释“为什么相关”
- 允许围绕一个主题继续展开探索
- 支持时间、争议、补充、因果等关系

### 6.5 人机协作与审核

系统应允许用户在关键阶段介入：

- 在归档分析阶段做 idea Sharpen
- 对 AI 生成摘要和标签进行审核与修订
- 添加评论
- 在必要时引导 AI 重新生成

这部分保证系统不是不可控黑盒。

### 6.6 GUI 工作台

GUI 的目标是：

- 作为浏览与检查入口
- 提供归档状态、搜索结果、条目详情、配置和调试能力

当前阶段 GUI 不是主战场，因此不把“重交互编辑体验”作为核心成功标准。

## 7. 成功指标

### 7.1 效率指标

- 单条内容整理时间 ≤ 5 分钟
- 常见查询定位时间 ≤ 1 分钟
- 高频工作流程中，重复性工作自动化率 ≥ 80%

### 7.2 质量指标

- Top 5 检索准确率 ≥ 85%
- 关联推荐具有实际参考价值
- AI 摘要准确可用
- 审核后入库结果明显优于未审核结果

### 7.3 下一阶段新增指标

针对关系层和高阶 MCP 能力，建议新增：

- 多跳查询有效命中率
- 关系解释可接受率
- 证据包完整性
- 桥接知识发现成功率

---

## 8. 当前范围与分期

### 8.1 当前已落地能力

- 文字内容归档
- 混合检索
- CLI
- MCP 基础能力
- GUI 工作台基础能力
- 审核系统相关能力推进

### 8.2 当前主线

当前阶段的主线不是继续扩张入口，而是增强中间层：

1. `relation_index / knowledge_graph`
2. 高阶 MCP Tool
3. 多跳检索与证据聚合

### 8.3 当前非主线

以下内容当前不应作为优先投入方向：

- 重交互 GUI 打磨
- 视频/PDF 优先扩张
- 知识图谱可视化优先落地
- 仅为了完整性继续扩写历史 Prompt 路线

### 8.4 后续阶段建议

#### Phase A：关系层补强

- 关系类型设计
- 关系索引设计
- 基础关系查询与评测

#### Phase B：高阶 MCP

- `query_subgraph`
- `explain_relation`
- `collect_evidence`
- 其他高价值知识探索 Tool

#### Phase C：基于关系层的 GUI 增强

- 关系链检查
- 时间线视图
- 证据视图
- 更强的审阅与调试体验

---

## 9. 非目标

当前阶段明确不作为主线推进的内容：

- 做一个类 Obsidian 的重 GUI 编辑器
- 以视觉展示替代知识推理中层建设
- 在关系层缺失时过早承诺知识图谱体验
- 让历史 Prompt 文档继续承担当前路线定义职责

---

## 10. 风险与约束

### 10.1 主要风险

- 关系层设计不清晰，导致高阶 MCP Tool 只停留在表层包装
- 文档漂移，导致团队继续按旧分期推进
- 检索能力、审核能力、关系能力三条线各自前进但缺乏统一验证

### 10.2 主要约束

- 本地优先，不依赖复杂中心化基础设施
- 以 Markdown 作为长期事实源
- SQLite 与向量索引可重建
- 入口层扩展不能破坏底座一致性

## 12. 一句话总结

PKV 当前的产品核心，不是继续做更完整的前端入口，而是把现有本地知识库升级成 **AI 可调用、关系可解释、可多跳探索** 的知识环境。
