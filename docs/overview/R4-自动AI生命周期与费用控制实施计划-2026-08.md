# R4 自动 AI 生命周期与费用控制实施计划（2026-08）

> 文档类型：已确认 ADR 的实施计划；2026-09-01 按“前处理 → Q1′ 内容提交 →
> Q2 AI 派生”运行模型重基线。
> 对应 ADR：[知识变更与 Embedding Generation 一致性](./ADR-知识变更与EmbeddingGeneration一致性-2026-08.md)。
> 范围：Headless Core 的内部生命周期；不新增 public rebuild API、CLI rebuild
> 命令或 MCP rebuild Tool。

## 1. 已确认的 R4 运行模型

R4 不再把“爬取、文章存储、AI”混在一条 archive workflow 中。产品运行时由两条
持久队列和一个前处理边界组成：

~~~text
前处理 / Q0
  crawler、纯文本复制、文件解析
  ↓ PreparedDocument（不可变、无 AI）
Q1′ 内容提交队列
  archive / delete / apply_ai_patch
  Markdown + SQLite 的唯一内容写入口
  ↓ CoreMutation + durable AI handoff
Q2 AI 派生队列
  摘要、标签、实际用量、预算、Embedding generation
~~~

这里的“前处理”在产品上是 ingress；若需要跨进程/重启继续，它实现为轻量、持久的
Q0，而不是一次性内存 coroutine。Q0 与 Q1′/Q2 的职责必须严格分离：

| 边界 | 可以做什么 | 绝不可以做什么 |
| --- | --- | --- |
| Q0 前处理 | 接受 URL/纯文本/已授权文件；crawler/解析；形成 PreparedDocument | 写 Markdown/知识 SQLite、创建 AI Provider、写 vector/generation |
| Q1′ 内容提交 | 以唯一 writer 身份执行 archive/delete 和 apply_ai_patch；维护 Markdown、SQLite、内容操作 journal 与 handoff | crawler、文本解析、AI Provider、向量平铺写入 |
| Q2 AI 派生 | inspect → plan → confirm；预算、Provider、摘要/标签 patch、generation stage/CAS、用量账本 | 绕过 Q1′ 直接写 Markdown/SQLite、读取或写入 flat vector |

### 1.1 调用与自动化语义

1. archive_url、archive_text 等既有入口先在短 writer-lease admission 中登记 Q0
   请求。竞争 writer 必须先返回 write_busy，此时不得抓网页、构造 processor 或
   Provider，也不得产生 audit/log/task 副作用。
2. Q0 成功时产出有 hash、provenance 和 parser 版本的不可变 PreparedDocument。外部
   crawler 可在已持久化 admission 后运行，但其开始和完成都要有 fenced claim；它不在
   长时间网络操作中占用内容提交临界区。
3. Q1′ 消费 PreparedDocument，完成现有 StorageCoordinator 可证明的
   Markdown + SQLite 提交。用户得到“文档已入库”只在 core_committed 后。
4. Q1′ 的同一 mutation 可靠登记 ai_handoff_pending；恢复逻辑以此为权威，幂等创建
   Q2 任务、发布 non-ready generation binding，再激活 Q2。
5. Q2 自动处理摘要、标签和 Embedding。摘要/标签先成为持久 DerivationPatch，由
   内部 Q1′ apply_ai_patch 原子提交到 Markdown + SQLite；Q2 只能在最终 source
   snapshot 上 stage/validate/CAS 新 generation。

v1 仍是**持久任务 + 当前 Application 进程内有界自动 drain**，不是 daemon。若进程
退出，未完成工作保留为可恢复状态；下一次允许的 mutation/内部 lifecycle trigger 继续。
只读 status/search/related/MCP/CLI 路径绝不取 lease、drain、创建 Provider 或写 data root。

### 1.2 Q1′ 与 Q2 的状态机和交接

Q1′ 状态最少为：

~~~text
accepted → processing → core_committed → ai_handoff_pending → completed
                     ↘ retry_required / repair_required / rejected / superseded
~~~

Q2 状态最少为：

~~~text
blocked_handoff → pending → processing → completed
                      ↘ retry_required / budget_paused / authorization_required / superseded
~~~

- 所有 claim 有不可复用 token、claimed_until 和 owner fence；任何超过租约的
  processing 都能在下一次内部 trigger 中安全回收。
- retry_required 有 not_before、有界退避和 attempt_count；达到策略上限后保持明确
  的待重试状态，不无限调用 Provider。
- operation_id 是 Q1′ 和 Q2 的 handoff 幂等键。Q2 在 handoff 未完成时不可 claim。
- 删除产生 generation 重建任务，并 supersede 针对已删除/旧 revision 的派生任务；archive
  或未来 update 只允许当前 revision 的 patch 成为有效产物。
- 任一 core mutation 后立即使 binding 为 rebuild_required 或 processing。所有
  vector/related 读取只使用 generation binding；不允许旧 generation、flat fallback 或把
  不一致表示为 no_hits。

### 1.3 Q2 的派生循环

Q2 不是 Markdown/SQLite 的第二写入口。它的每个可计费阶段遵循：

~~~text
claim → policy/source/config re-check → 预算预留
  → construct Provider → provider result + normalized usage
  → persist DerivationPatch / stage evidence
  → Q1′ apply_ai_patch
  → capture final source → stage generation → validate → pointer CAS
~~~

DerivationPatch 必须绑定目标 document revision、输入 digest、schema/version 和任务
identity。patch 已成功提交后重试只跳过已完成阶段，不能重复调用 Provider 或重复计量。
Embedding generation 只在所有本次要求的内容 patch 已成功提交后捕获 source；失败时保留
processing/retry_required，不切换 pointer。

Provider 只能在 policy inspect、计划、确认、计划重检、writer lease 和预算预留之后创建。
日/月 token hard cap 是启用自动化的前提；有价格卡时才计算金额。Provider 未报告的
uncached_input_tokens、cached_input_tokens、generated_tokens 或
embedding_input_tokens 保留 unknown/NULL，绝不以 0 补齐。模型、Provider contract、
token 策略或启用的 price-card/金额策略变更都会使既有授权失效。

## 2. 持久合同和数据边界

| 合同 | 权威位置 | 写入规则 | 禁止内容 |
| --- | --- | --- | --- |
| IngressRequest / Q0 claim | SQLite task row + data-root 私有 ingress spool | admission、claim 和状态更新在 lease 内；spool 只通过受控文件操作写入 | 凭据、Provider payload、日志中的正文 |
| PreparedDocument | Q0 spool 的不可变 payload，SQLite 仅保存 identity/hash/provenance | Q1′ 成功消费后按恢复策略清理；不会写入 task ledger 正文列 | API key、AI 输出、vector |
| ContentMutationTask / Q1′ | SQLite task row + 既有 StorageOperationJournal | Q1′ 是 Markdown + SQLite 唯一内容提交者；journal 保留跨文件/SQLite 证明 | 原始 crawler 响应、Provider 原始 payload |
| durable handoff / outbox | 与 Q1′ mutation 同一权威 SQLite 事务或可恢复 journal checkpoint | Q1′ 先留可恢复 handoff，再创建/激活 Q2；禁止 best-effort fire-and-forget | 正文、凭据 |
| AIDerivationTask、reservation、usage | SQLite | Q2 state/预算/用量写入均需 writer lease 和 task fence | 正文、API key、伪造的零用量 |
| DerivationPatch | 私有 patch spool；成功后由 Q1′ 写入 Markdown + SQLite | patch 与目标 revision、task 和 digest 绑定；成功提交后可按证据清理 | Provider 原始响应、凭据 |
| generation binding/pointer | <data-root>/config/local.yaml 的无密钥 embedding_index extension | 仅 RuntimeSnapshotStore semantic merge + raw-byte CAS，在 lease 内发布 | 可编辑预算策略、正文、凭据 |

现有 StorageCoordinator 的 operation journal、Markdown identity 和 SQLite operation proof
是 Q1′ 的恢复基础，必须复用而非再造第二套跨文件事务。现有
ai_automation_tasks / reservation / usage 表是 Q2 的候选基础，但尚不具备完整租约、
调度与实际 usage 回填语义；不得仅因已有表而宣布 R4 完成。

所有 schema 演进采用新 migration，绝不改写已提交的 011。运行 archive、Q0/Q1′/Q2
worker 和测试都不得对真实 Vault 自动迁移；真实升级仍只能走 R2 inspect → plan → confirm →
execute。

## 3. 分阶段实施

当前 0b15fab 中的 generation binding、writer lease、token reservation 和自动
Embedding 路径保留为**待验证的候选基础**，不是按本计划自动验收的完成项。每个阶段先以
fake-only characterization 固定行为，再实现下一阶段；实现前重读实际触及模块指南。

### R4-A：Q1′ 内容提交任务与可恢复 handoff（首个代码阶段）

**目标**：先建立唯一内容提交者和 Q1′→Q2 durable handoff，而不迁移 URL crawler、不创建
Provider、不生成摘要/标签。

**预期触点**：

- 新 migration（编号在当前链末尾）、src/storage/ 的 task store、SQLite operation proof
  与 StorageCoordinator；
- src/application/knowledge_application.py 的内部 prepared-document port 与 Q1′ drain；
- src/runtime/embedding_lifecycle.py 的 non-ready publication 接口（仅复用，不新增 public
  rebuild capability）；
- tests/unit/test_storage_coordinator.py、新的 Q1′/handoff tests、write-lease 与 Application
  lifecycle tests。

**验收标准**：

- fake PreparedDocument 可经 Q1′ 完成一次 archive/delete，Markdown + SQLite 仍使用
  operation-bound proof；
- crash/fault 注入在 core_committed、handoff 登记、non-ready binding、Q2 创建/激活之间的
  任一点后，下一次内部 trigger 都能幂等收敛；
- Q2 在 handoff 完成前零 claim、零 Provider、零用量；
- 竞争写在任何 processor/crawler/Provider 前返回 write_busy；
- 本阶段不改变公开 CLI/MCP/Kernel capability，不使用真实网络或迁移。

### R4-B：Q0 前处理与 PreparedDocument 边界

**目标**：把 URL crawler、纯文本复制和已授权文件解析从 Q1′/workflow 内核移至 Q0，并让
它们交付同一 PreparedDocument 合同。

**预期触点**：

- ingress task/spool、Q0 claim/recovery 和 input adapter；
- src/processors/、src/application/knowledge_application.py、现有 archive workflow；
- CLI/MCP 既有 archive 入口仅映射稳定 processing/status envelope，不新增命令或 Tool；
- ingress/content task 和 fake crawler/processor tests。

**验收标准**：

- URL 竞争时 fake crawler 完全未调用；成功 admission 后的 crawler 失败、取消、重启可按
  claim/retry 状态恢复；
- URL、文本和文件解析产生相同版本化 PreparedDocument，Q1′ 不导入 crawler/processor；
- ingress spool 不进入日志、AI ledger 或 local.yaml，并具有身份/hash 校验和恢复后的安全
  清理规则；
- 用户在 Q0/Q1′ 未完成时得到明确“前处理中/入库中”，只有 core_committed 后才称文档已保存。

### R4-C：Q2 调度恢复、generation 绑定与 flat 路径收口

**目标**：在 Q1′ handoff 基础上完成 Q2 的 claim 续期/回收、stale source/policy fence、
有界 retry，以及所有实际 vector 读写入口的 generation-only 约束。

**预期触点**：

- src/storage/ai_automation_store.py、src/runtime/ai_automation_policy.py、
  src/application/knowledge_application.py；
- src/kernel/facade.py、Application/retrieval/CLI/MCP 的 legacy flat vector 入口；
- embedding lifecycle、runtime audit/writer inventory 和相应 unit/integration tests。

**验收标准**：

- 重启后的过期 Q2 processing task 可安全回收；未到 not_before 或已到最大尝试数时不创建
  Provider；
- source/config/authorization 变化会 supersede/replan stale task，任何读路径都不使用旧
  generation 或 no_hits 掩盖不一致；
- archive/delete 后 flat vector 即使存在也不被实际产品路径读写；直接 legacy facade 路径被
  安全隔离、拒绝或兼容转发，不能偷偷写 flat index；
- staged generation 仅在验证和 pointer CAS 后 ready；read-only 调用零写。

### R4-D：AI 派生产物、用量账本与费用控制闭环

**目标**：完成 Q2 的摘要/标签 Provider adapter、DerivationPatch → Q1′ apply_ai_patch
回路、实际 usage 标准化与可选价格控制。

**预期触点**：

- src/ai/ 的 LLM/Embedding usage adapter 与 fake seams；
- Q2 owner、usage/reservation store、可选 price-card resource/validation；
- Q1′ patch commit、Markdown/SQLite metadata 更新和 generation source capture；
- Application/CLI/MCP 的既有状态投影及端到端 fake tests。

**验收标准**：

- summary/tag 的成功只经 Q1′ 原子写入 Markdown + SQLite；重复执行同一 revision 不重复
  Provider 调用或写入；
- Provider usage 能标准化回填可信字段，未知字段仍为 NULL；本地估算、reservation、实际结算
  可审计区分；
- token 或金额上限在 Provider 前暂停；无价格卡时仅 token 路径正常工作且不显示推测价格；
- 价格/模型/预算策略变更要求重新确认；失败保留已安全入库文档和可操作的待重试状态；
- 所有要求的 patch 成功后才捕获最终 source、stage、验证并切换 generation。

### R4-E：恢复矩阵、文档与发布边界

**目标**：验证整个 Q0→Q1′→Q2 回路，修正文档和测试契约，但不扩大到发布、GUI、daemon、
Docker 或跨平台工作。

**验收标准**：

- 使用 scripts/run-test.ps1 与独立 .data-test 子根运行定向测试、Windows P0 和适用 MCP
  coverage gate；Provider/crawler 均为 fake，网络 guard 生效；
- 覆盖 snapshot/reload、lease 竞争、Q0/Q1′/Q2 重启、handoff crash point、stale plan、
  Q1′ patch 失败、generation pre/post-CAS 失败、预算暂停及 resume；
- 更新 Runtime/Config/Application/Workflow/AI/Storage/CLI/MCP 文档，删除与“无价格卡不估价”
  矛盾的硬编码价格叙述；
- git diff --check 通过；不将 W4 artifact、ZIP、wheel 或任何内部 smoke 提升为发布证据。

## 4. 关键验收矩阵

| 场景 | 必须结果 | 禁止结果 |
| --- | --- | --- |
| 竞争 archive_url | write_busy 先返回；fake crawler/processor/Provider、audit/log/task side effect 为零 | 先抓网页或先创建 Provider |
| Q0 崩溃/重启 | 依据 fenced claim 恢复或明确 retry；不会重复提交同一 PreparedDocument | 丢失已接受请求、重复归档 |
| Q1′ archive 成功 | Markdown + SQLite 可证明提交；保留可恢复 AI handoff | 将“请求已接受”当作“文档已保存” |
| Q1′ 在 handoff 中崩溃 | restart 幂等补齐 non-ready binding 和 Q2 activation | ready 旧 generation、丢 AI 任务 |
| Q2 processing 进程退出 | claim 到期后可恢复；未到 retry 时间/达上限均不调用 Provider | 永久卡住或无限重试 |
| AI patch 成功/重试 | Q1′ 原子应用一次；Q2 保留阶段证据和真实/unknown usage | Q2 直接写 Markdown/SQLite、重复收费 |
| archive/delete 后 generation | processing/rebuild_required 直到 stage+validate+CAS 成功 | old generation、flat fallback、no_hits 掩盖不一致 |
| token/金额上限 | Provider 前 budget_paused；无价格卡不估价 | 先调用后检查、未知 usage 写 0 |
| only-read CLI/MCP | 明确状态、并发读取、data root 零写 | status 触发 retry、日志、目录、handler sidecar |

## 5. 范围与实施门槛

- 不新增 public pkv_kernel rebuild API、CLI rebuild 命令或 MCP rebuild Tool。
- 不变更默认数据根、用户配置布局、release/install 合同或 MCP stdio-only 合同。
- Core 继续 headless；不引入 GUI/PySide6/qasync，不将 Docker/跨平台工作带回 master。
- 不使用真实 Vault、%USERPROFILE%/.pkv/config.yaml、真实 Provider 凭据、真实网络或真实
  migration。

本计划已确认 R4 的工作内容。下一次进入代码前，先以 **R4-A** 为单独实现阶段重读 Storage、
Application、Runtime、Workflow、Tests 模块指南，复核该阶段的实际文件、迁移编号和
fake-only 测试命令；R4-B 至 R4-E 不随 R4-A 一并实施。
