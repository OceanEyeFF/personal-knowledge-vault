# R4 自动 AI 生命周期与费用控制实施计划（2026-08）

> 文档类型：已确认 ADR 的实施计划；R4 已获授权并处于分阶段实施中。
> 对应 ADR：[知识变更与 Embedding Generation 一致性](./ADR-知识变更与EmbeddingGeneration一致性-2026-08.md)。
> 范围：Headless Core 的内部生命周期；不新增 public rebuild API、CLI rebuild 命令或 MCP rebuild Tool。

## 1. 已确认的产品语义

用户已选择“mutation 后 `rebuild_required`”而不是每次同步完成 successor generation，
并确认体验目标是自动完成后续 AI 工作，而不是逐文档确认。R4 的正确操作序列因此是：

```text
archive/delete 获得 R3 lease
  -> 核心文档 mutation 与 durable task/binding 状态一起提交
  -> 返回“文档已保存；AI 处理中/待重试/预算暂停”或最终 ready
  -> 有效自动化授权时，当前 Application 自动 claim task
       -> 重检 source/config/authorization/budget
       -> Provider 工作（目标为摘要、标签、Embedding）
       -> stage 完整 generation -> validate -> pointer CAS -> ready
```

`related`、vector retrieval 与 vector delete 始终从同一个 generation binding 读取状态。
没有 ready generation 时它们返回明确状态，而不是平铺索引、旧 generation 或 `no_hits`。
BM25 仍是独立的只读路径；hybrid 的 BM25 降级必须标示 vector 不可用及原因。

### 1.1 v1 宿主语义

v1 采用**持久任务 + 当前 Application 进程内自动 drain**。归档完成核心持久化后，在同一
产品操作中自动启动后续处理；暂态重试使用有限退避。若进程已退出或可恢复尝试耗尽，任务
持久化为“待重试”，下一次允许写入的内部生命周期触发才会继续。只读 status/related/search
不会为重试取 lease、创建 Provider 或写 data root。

这满足“无需逐份确认”，但**不承诺独立后台服务在所有进程退出后仍继续工作**。后者需要
单独通过 Node/持久 worker 门禁，不在本计划内。

### 1.3 当前实施进度（2026-08-31）

P0（stateful binding / 错误投影 / token-only policy）、P1（耐久任务与用量账本）和 P2
（核心归档优先、任务登记、非 ready binding）已在隔离测试中完成。当前 Application 已对
Embedding generation 执行自动的 inspect → plan → policy re-check → token reservation →
Provider → staged publish 路径，并将成功、预算暂停、授权等待和待重试持久化。

文本归档现阶段会先保存确定性的本地摘要/标签；**Provider 生成后回写摘要/标签仍需一个新的
Markdown + SQLite 原子 enrichment 合同**，尚未声明完成。它不能靠重复 archive 或覆盖已保存
文件实现。generation binding 已开始接入 Application/CLI/MCP 的 vector/related 读路径；其余
legacy flat writer 入口仍须在后续收口阶段退休或测试隔离。

### 1.2 用量优先的费用控制语义

自动化默认关闭。首次启用时，用户一次性确认 Provider contract、模型、计费时区、日/月
token hard cap、估算方法与 retry policy。每篇文档先显示本地 token 预估；每次调用记录
Provider usage（若可信）或保守 token reservation。模型、token 策略或（若启用）价格/金额
策略变化使授权失效并暂停，而非继续支出。

price card、币种和金额 hard cap 是可选能力，不是启动自动处理的前提。没有价格卡时不计算、
不显示推测价格，只记录并限制 token 用量；有价格卡时才额外显示金额预估和实际金额。为避免
隐性无上限资源使用，启用自动化必须有至少一个日/月 token hard cap；缺少 token cap、未授权
或 token 超限才 fail-closed 为暂停。价格数据不得经网络自动抓取。

## 2. 落地前的持久合同

| 数据 | 位置 | 权威与写入边界 | 禁止内容 |
| --- | --- | --- | --- |
| 自动化授权与 token 配额策略 | 唯一可编辑用户配置 `%USERPROFILE%\\.pkv\\config.yaml` | 用户确认后经既有受控 settings 写入；其 fingerprint 进入任务重检 | API key 副本、正文、运行时用量 |
| 可选的已确认 price card | 随版本打包的只读资源（拟新增版本化 YAML/JSON） | 代码审阅/发行资源；有启用时授权才保存 card ID/hash | 网络抓取值、凭据 |
| binding 与 generation pointer | `<data-root>/config/local.yaml` 的无密钥 `embedding_index` extension | `RuntimeSnapshotStore` semantic merge + raw-byte CAS，在 lease 内发布 | 凭据、正文、可编辑预算设置 |
| AI task / retry / usage ledger | SQLite（拟新增 migration `011` 或后续实际编号） | 与文档 mutation、claim、token reservation、可选金额结算原子协调；所有写入需 R3 lease | 正文、API key、原始 Provider payload |
| 审计与运行日志 | 已有 `<data-root>/logs/` | 只记录脱敏任务/授权/用量摘要/可选金额/状态；符合 R3.1 writer guard | API token、URL 凭据、完整输入输出 |

`embedding_index` 需从现有 ready-pointer-only 表示升级为版本化 stateful binding（预计 schema
v2）。它至少绑定 source revision、状态、当前/前代 generation、任务 identity 与无密钥
contract digest。旧 v1 ready pointer 只能在严格验证后迁入 v2；缺失或不一致绝不能被当作
flat index 或 ready。

数据库持久任务/账本意味着已有 Vault 可能出现 `upgrade_required`。该升级仍只能走 R2 的
inspect → plan → confirm → execute，不会由 archive、rebuild worker 或测试触碰真实数据根。

## 3. 分阶段实施

每阶段先完成相应的 fake-only characterization/回归，再做下一阶段。文件清单是预期触点；
实施前仍需在当前工作树重读对应模块指南并以实际依赖为准。

### P0：冻结内部状态、错误投影与用量/可选计价合同

**目标**：把“可安全保存”“AI 状态”“generation 状态”“费用状态”分成稳定、可测试的
内部 DTO/错误码，而不公开 rebuild capability。

**预计文件**：

- `src/runtime/embedding_lifecycle.py`、`src/runtime/runtime_snapshot.py`：stateful binding schema、
  source revision 与 strict reader；
- `src/runtime/errors.py`：`embedding_processing`、`embedding_retry_required`、
  `embedding_budget_paused`、`embedding_automation_authorization_required` 等稳定投影；
- `src/utils/config.py`：token quota / authorization schema validation；`config/` 下可选的版本化
  price-card 资源和 validation；
- `src/runtime/writer_inventory.py`：升至 inventory v2，显式列出 task、reservation 与 usage；
- `docs/specs/interfaces/EmbeddingGeneration生命周期合同.md`、相关 Config/Runtime 文档。

**测试**：扩展 `tests/unit/test_embedding_lifecycle.py`、`test_runtime_lifecycle.py`、
`test_writer_inventory.py`；验证 reader 零副作用、v1/v2 严格解析、所有非-ready 状态均不返回
`no_hits`、双空 token cap/敏感字段 fail-closed；无 price card 时保留 token-only 记录，只有
配置了金额 cap 却无法解析其 price card 才暂停。

**风险**：将“内部状态”误做成 Kernel/CLI/MCP 的新动作，或在 `local.yaml` 写入可编辑策略/密钥。

**完成标准**：一个 explicit Config snapshot 在不创建 Provider、目录或日志的情况下能解析完整
binding/authorization 决策；无 ready generation 无法被任何 vector path 误表示为正常空结果。

### P1：耐久任务与用量账本（仍无 Provider）

**目标**：把 document mutation 后的 `rebuild_required`、任务 enqueue/claim、retry、token
reservation/settlement（以及有价格卡时的金额计算）做成有 fence 的持久事务；先不调用真实
Provider。

**预计文件**：

- `scripts/migrations/011_*`（实际编号须以届时 migration 链为准）、`src/storage/sqlite_store.py`
  与 `src/storage/coordinator.py`：任务、usage/reservation 表和原子提交；
- 拟新增 `src/application/ai_automation.py`（或同职责内部模块）：任务 eligibility、claim、
  bounded retry、stale/retry 处理；
- `src/application/knowledge_application.py`、`src/kernel/facade.py`：archive/delete 先完成核心
  mutation，再标记并入队；删除不再对旧平铺 vector 做 side effect；
- `src/runtime/writer_inventory.py`、`src/runtime/audit.py`：任务/账本审核事件和 R3 guard。

**测试**：新的 `test_ai_automation.py` / `test_ai_usage_ledger.py`，以及
`test_storage_coordinator.py`、`test_knowledge_application.py`、`test_write_lease.py`：

- archive/delete 的核心数据先提交，AI task 状态可恢复；
- 两个 worker 竞争时败者在 Provider factory 之前为 `write_busy`，且无 task 双 claim、无
  额外 audit/log/reservation；
- 本地 token 估算；daily/monthly token cap 以 `settled + reserved + estimate` 判断；超限零
  Provider 调用、零网络、状态为 `budget_paused`；没有 price card 仍可继续 token-only 路径；
- fake Provider usage 的 `uncached_input_tokens`、`cached_input_tokens`、`generated_tokens`、
  `embedding_input_tokens` 分类记录，以及“不可信 usage 保留保守 token reservation”；
- 未报告的 cached/uncached/generated 字段保留 unknown，不得伪造零；有价格卡时才验证金额结算；
- reload/config drift/delete 与已 claim task 的 fence 行为。

**风险**：让 token 配额检查落在 Provider 创建之后、重复计量/计费、在已有数据根上自动执行 schema migration，
或把 data-root writer 缩窄为“仅 vector 文件”。

**完成标准**：使用 fake executor 可完整跑通 `rebuild_required → processing → retry/budget_paused`
和 token 账本审计；所有持久写均由同一 task 的 lease 证明，且默认离线测试无网络。

### P2：把 archive 流程改为“安全存储优先，AI 自动 enrichment”

**目标**：消除当前 `AI 分析 → StoreStep（含平铺 vector）` 顺序，使 archive 成功语义首先
表示 Markdown/SQLite 文档已持久化；摘要、标签和 Embedding 成为自动任务结果。

**预计文件**：

- `config/workflows/archive-url.yaml`、`archive-text.yaml`；
- `src/workflow/steps.py`、`src/workflow/engine.py`：拆分 core store 和 AI enrichment，不允许
  StoreStep 创建/改写平铺向量；
- `src/application/knowledge_application.py`：在 captured snapshot + lease 下 enqueue 并自动 drain；
- `src/processors/` 与 `src/ai/`：将摘要/标签/Embedding adapters 改为可注入、可计量、fake-only
  task dependencies。

**测试**：`test_workflow_steps.py`、`test_workflow_config_schema.py`、
`test_knowledge_application.py`、`test_processors_wechat.py`，外加新的 archive lifecycle tests：

- 无索引 → archive：先得到可读核心条目和 `embedding_processing`，不创建 flat vectors；
- fake AI 成功：摘要/标签落盘、generation 原子切换后 related 可用；
- fake AI 失败/取消：文档仍安全保存，返回 `degraded` 的 processing/retry 状态，不建议盲重试；
- archive 竞争：败者不运行 processor/Provider，成功者的旧 snapshot 不与 reload 后新 owner 混用。

**风险**：更改现有 archive 工作流的成功/降级 envelope，或让文档与任务无法原子关联。

**完成标准**：archive 的 durable result 明确包含 document identity、AI state、预估/实际 token
摘要（无敏感值）；存在 price card 时才附带金额摘要。AI 失败永不回滚已确认的主文档提交。

### P3：同一 generation binding 接入所有读写调用方

**目标**：彻底移除实际调用路径对 `config.vector_index_dir` 的平铺读写；所有 vector/related
语义只消费一次 Application-owned binding。

**预计文件**：

- `src/application/knowledge_application.py`：一次操作一次 binding reader、readonly VectorStore
  factory 和状态投影；
- `src/retrieval/vector_retriever.py`、`hybrid_retriever.py`、`query_router.py`、
  `src/storage/vector_store.py`：只接收已验证 generation directory / readonly port；
- `src/kernel/facade.py`：delete 不再调用旧 flat vector delete；
- `src/cli/commands.py`、`src/mcp/tools.py`、`src/mcp/server.py`：既有操作展示 stable state，
  不新增 rebuild command/tool；
- `src/utils/verify_setup.py`：仅报告 binding 状态，不能创建/检查 flat writer store。

**测试**：`test_vector_retriever_readonly.py`、`test_vector_retriever_contract.py`、
`test_cli_commands.py`、`tests/blackbox/test_cli_basic.py`、`test_mcp_tools.py`、
`test_mcp_server_w2.py`、`tests/integration/test_mcp_functional.py`：

- first no-index → archive → related/delete 的 `processing → ready` 与 delete 后立即 non-ready；
- flat artifacts 即使存在也完全不被读写；
- vector/related 的 processing/retry/budget/repair 不等价于 `no_hits`；
- BM25 并发零 data-root 写，hybrid 降级显式标志；
- reload 前后的 in-flight reader 只使用各自一次解析的 binding，pointer flip 只影响新操作。

**风险**：遗漏 CLI/MCP 旁路、把 pointer 状态吞掉成泛化异常，或让 read path 为“自修复”创建
目录/日志/VectorStore writer。

**完成标准**：仓库搜索和 executable tests 均证明 runtime 调用方没有平铺索引 fallback；
`related` 在所有非-ready 状态输出稳定且可操作的原因。

### P4：自动 staged rebuild、失败恢复与接口兼容收口

**目标**：把已存在的 staged core 安全接到内部 worker：只在 lease、授权、token reservation 与
重检后创建 Provider；验证完成后才 CAS publish generation。

**预计文件**：

- `src/runtime/embedding_lifecycle.py`：内部计划确认 bridge、state transition、stage/pointer
  publish 与恢复；
- `src/application/ai_automation.py`（或最终内部 owner）：Provider factory、usage capture、
  stale plan requeue；
- `src/ai/provider_factory.py`、`embedder.py`、LLM adapter：可验证 usage contract 和 fake seams；
- `src/runtime/audit.py`、`file_logging.py`、`writer_inventory.py`：用量/activation audit 与
  R3.1-safe observability。

**测试**：`test_embedding_lifecycle.py`、`test_runtime_audit.py`、`test_runtime_lifecycle.py`、
`test_write_lease.py` 和 P1/P3 测试的 fake provider variants：

- source/config/authorization/token quota（或启用的 price policy）drift 在 Provider 前 stale；
- 竞争 worker 在 Provider 前 `write_busy`；
- stage/manifest/audit pre-CAS 失败不改 active pointer；post-CAS audit completion pending 保留
  ready + reconciliation warning；
- task crash/restart/retry 不重复结算或重新使用 stale generation；
- reload 与 in-flight task 不混用 Config/owner/log binding。

**风险**：为便利而把 `confirm_embedding_rebuild()` 暴露给外部，或让自动 retry 绕过一开始的
token 配额/授权确认。

**完成标准**：fake-only end-to-end 路径实现“入库 → 自动摘要/标签/Embedding → 新 generation
ready → related 可用”；全部失败状态明确、可恢复且无 flat fallback。公开 API 表面、MCP Tool
清单、CLI 命令清单和 Kernel capability 均无 rebuild 新增项。

### P5：验证、文档和发布边界

**目标**：把新行为固定为 Windows 隔离合同，更新文档但不改变 release/install/GUI/Docker 边界。

**测试顺序**：每个小阶段先运行相关单测和 `git diff --check`；R4 收口后运行 Windows P0。
若触及 MCP envelope，再运行 MCP coverage gate。所有命令经 `scripts/run-test.ps1`，使用独立
`.data-test` 子根、fake provider 和网络 guard。

**预计文件**：`docs/specs/interfaces/EmbeddingGeneration生命周期合同.md`、Runtime/Config/
Application/CLI/MCP 模块文档、`tests/contracts/` 必要时的 topology/coverage contract。不得更新
release evidence 为“已发布”，不得把 W4 Artifact、内部 ZIP/onedir smoke 或 K1b wheel 提升为
同等级证据。

**完成标准**：定向、Windows P0 和适用 MCP gate 均通过；`git diff --check` 通过；变更说明
清楚区分“自动内部生命周期已验证”与 release/PyPI/安装器/外部 daemon，后者仍未授权。

## 4. 关键验收矩阵

| 场景 | 必须结果 | 禁止结果 |
| --- | --- | --- |
| fresh root，无 generation，archive | 文档已保存；`embedding_processing` 或授权/预算暂停；无 flat index | `no_hits`、静默 flat vector 创建 |
| 自动任务成功 | 先验证 stage，再 CAS 切 generation；related 可用 | 未验证 generation 成为 active |
| 自动任务网络/Provider 失败 | 文档安全；`embedding_retry_required`；无错误结算 | 回滚文档、假称 ready/no_hits |
| token 配额达到上限 | `embedding_budget_paused`；零 Provider/网络调用 | 先调用后才发现超限 |
| archive/delete 与竞争 worker | 败者为 `write_busy` 且 Provider/log/audit/task side effect 为零 | 双 claim、双收费、旧 generation 回答 |
| reload 或 source drift | 旧 task stale/retry，新 snapshot 重计划 | A/B Config、Layout、Provider 混用 |
| only-read CLI/MCP | 可并发读取；相关状态明确；data root 零写 | status 触发 retry、日志、目录或 handler sidecar |

## 5. 进入实施所需的确认

本计划还需要确认以下宿主边界后再开始 R4 代码实施：

1. 接受 v1 仅提供当前进程内的自动 drain；进程退出后的待处理任务显式为“待重试”，不在
   本轮偷偷引入 daemon/Node/Docker。

费用策略已调整为：默认关闭；启用时需要计费时区、日/月 token cap 和 retry policy。price card、
币种和金额 cap 可选；无 card 时照常记录 `uncached_input_tokens`、`cached_input_tokens`、
`generated_tokens`、`embedding_input_tokens`（适用时），但不估价。

确认后按 P0 → P5 执行；任何阶段发现公开 API、真实数据迁移、后台守护进程或跨平台范围
需求时，立即停在该门槛并另行请求授权。
