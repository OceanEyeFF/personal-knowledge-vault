## 1. 本轮决策

1. M13 的 Artifact 继续保持 `test_candidate` / `hold`。当前**不安排正式发布**；当前
   headless 合规权威文件中的三项 blocker 继续保持 fail-closed。拆分前候选的七项 blocker
   仅作为冻结的历史 release 证据保留；只有未来明确重开发布时，才重新成为发布判断的 P0。
2. 可以持续构建**仅供自己验证的内部自测包**，但它不是 release Artifact：不分发、
   不签名、不承诺安装/升级兼容性，也不改变当前默认用户数据根或安装拓扑。
3. PKV 的近期价值验证是“输出可追溯的知识成果”，而不是运营读者、订阅、评论或
   私域分发关系。
4. `PKV-Core` 是可复用的无头 Kernel / 领域与应用能力；`embedded` 与可选 `Node` 是
   运行宿主。daemon、Docker 和云端均不是当前价值验证的前提。
5. 桌面体验已于 2026-08-14 完全迁至相邻的 `pkv-GUI` 仓库。它像 LM Studio 围绕
   llama.cpp 一样，只消费 `pkv_kernel` 稳定接口；Core 不再保存 Qt 代码、GUI 测试或
   `pkv-gui.exe` 封包入口。

当前 Core 运行面为无头 Kernel、CLI 和 MCP stdio；外部 GUI Wrapper 可 embedded 调用
Kernel。MCP 不新增 HTTP transport 或监听端口。

## 2. GUI 剥离后的排序原则（2026-08-18）

GUI 已不再是 Core 的实现分支；它把 `pkv_kernel` 从“同仓源码门面”提升为跨仓库产品
接口。因此下一步不能直接把新的知识成果能力继续堆在一个只能靠相邻 checkout 导入的
接口上：必须先把 Kernel 的可安装性、版本兼容和 reload 语义变成可验证合同。

- **先完成 Kernel 发行与兼容性合同**：外部 Wrapper 只能依赖已安装的 `pkv_kernel`，
  不能把 `src.*`、本仓路径或 Core 内部对象当作集成方式。
- **再收束知识成果能力**：这仍是价值主线，但新增成果接口必须建立在版本化 Kernel
  合同上，CLI/MCP 与外部 Wrapper 可共同消费。
- **GUI 在外部仓库独立发布**：Qt 生命周期、视觉、桌面 smoke、封包与升级策略由
  `pkv-GUI` 负责；Core 只提供版本握手与兼容性证据，绝不重新引入 Qt。
- **Node 最后且必须过门禁**；**Docker 只能排在 Node 之后**，因为 Docker 只能包装
  已经有清晰本地服务职责的 Node，不能替代 Core、并发控制或产品验证。

因此，严格顺序是：

```text
冻结的 release 分支：M13 test candidate 保持 hold（不安排收口或发布）

当前 Core 路线：
A：应用服务边界 + 内部自测封包（已完成）
 └─ S0 / K1a：公开 Kernel 合同（既有 checkpoint）
     └─ K2：配置快照 / reload 并发合同（既有 checkpoint）
         └─ K1b：本地 wheel 与 clean-install 兼容验证（内部验证完成；仅离线验证）
             └─ R1：个人配置 / 数据布局与 snapshot 来源收敛（内部验证完成）
                 └─ R2：inspect → plan → confirm → execute 生命周期（内部验证完成）
                     └─ R3：受支持业务/数据写入的 lease、`write_busy` 与审计（内部验证完成）
                         └─ R4：Q0 admission → Q1′ content commit → Q2 AI derivation → READY generation（source acceptance 完成；runtime-internal）
                             ├─ R3.1：运行时日志写入归属、Q0 私有临时 image workspace、遗留维护 writer（source hardening 已完成）
                             ├─ P1：按需的 public rebuild adapter
                             └─ B：高阶知识成果能力（上述 gate 收口后的下一价值主线）
                                  └─ H：内部封包资源与 smoke 证据 hardening

外部协作路线：
C：pkv-GUI 独立封包与桌面验证（不回流 Core）

门禁路线：
D：可选 PKV Node（满足后台/并发/复用需求才开始）
 └─ E：可选 Docker/云端部署研究
```

不使用 `M14` 命名本轮工作；该编号在历史材料中已经指向审核系统，继续复用会造成
时间线歧义。

## 3. 工作包与退出条件

### A. 应用服务边界与内部自测封包

目标：在不改变已有用户行为的前提下，为三种入口建立同一条业务调用路径，并让开发
中的软件能以可运行包自行验证。

最小范围：

- 提取 `KnowledgeApplication`（或等价命名）的应用服务层；CLI、MCP adapter 只负责
  输入输出与协议化，不再各自直接装配 Store、Workflow 和 Provider。外部 GUI 只经
  `pkv_kernel` 的公开端口调用 Core。
- 保留当前严格的 `scripts/build-release.ps1` 作为 W3 test-candidate 检查点；不得因
  开发便利而削弱其 clean checkout、可复现和合规 hold 合同。
- 新增或设计独立的快速内部封包入口（建议 `scripts/build-internal-package.ps1`）：
  生成明确标记为 `INTERNAL TEST ONLY` 的 onedir/zip 包，输出到被忽略的
  `dist/internal/`，不提供安装器、不写入 `dist/release/`。
- 内部包至少记录构建时间、源码 revision 或 dirty 状态、构建机 Python/依赖摘要；并
  继续拒绝把密钥、`local.yaml`、Vault、日志、测试夹具打入包内。
- 内部包验收只使用 `.data-test` 合成根，至少覆盖 CLI `--help` / BM25 smoke、MCP
  stdio initialize；不读取真实 Vault 或 Provider 凭据。GUI 的启动/lifecycle smoke
  由 `pkv-GUI` 仓库独立负责。

退出条件：CLI、MCP 共用一个可测试的应用服务入口，外部 Wrapper 只依赖稳定 Kernel
接口；内部包可在仓库外目录启动并通过上述 headless smoke，但其结果只允许称为“内部
自测通过”。

实施状态（2026-08-14）：**已完成**。`KnowledgeApplication` 是 CLI/MCP 的共享业务
边界，`pkv_kernel` 是外部 Wrapper 的稳定端口；内部 onedir/ZIP 已在仓库外目录、合成
`.data-test` 根完成 CLI `--help` / BM25 与 MCP stdio `initialize` smoke，结果为
`INTERNAL SELF-TEST PASSED`。该结论不是 release、test candidate 或合规 hold 的变更。

### B. 高阶知识成果能力（R1→R4 checkpoint 后的主价值线）

目标：把现有检索、关系和证据能力收束为可交付、可审阅、可追溯的知识成果工作流。

优先顺序：

1. 定义 `Topic / Claim / Evidence / Outcome` 的最小合同：每个主张能回链到条目、
   chunk 或关系证据 locator，并能表达缺证、降级和不确定性。
2. 复用 `collect_evidence`、关系查询和 Workflow，形成
   `主题 → 证据账本 → 大纲/文章骨架/研究简报 → 审阅` 的最小闭环。
3. 将需要用户确认的步骤持久化为可恢复状态，而不是依赖某个 CLI/Rich 进程一直存活。
4. 对 `partial-v1` 探索 Tool 按真实使用场景逐个补 full 语义、专属评测和失败边界；
   不为“功能数量”整体升级实现等级。

退出条件：至少一种成果类型可由外部 GUI、CLI 或 MCP 发起，并公开其证据链与限制；不会
把没有证据的生成内容伪装为知识库事实。

### C. 外部 GUI Wrapper（2026-08-14 已完成剥离）

目标：让 GUI 是可独立演进的桌面 Wrapper，而不是 Core 内的业务实现分支。

完成范围：

1. Core 已删除 `src/gui`、GUI 单元/手工测试和 `pkv-gui.exe` 入口；Core 内部包也不再
   把 GUI 当作 smoke 项目。
2. `pkv-GUI` 是单独初始化的本地 Git 仓库，保留并迁入既有 View / ViewModel / Qt 测试；
   生产代码仅导入 `pkv_kernel`，测试通过 Kernel fake 注入而不 patch Core 实现模块。
3. 外部仓库已修复关闭窗口时 ArchiveWorker / Chat 活动任务的有序 shutdown，并保留其
   lifecycle 回归测试。

退出条件：GUI 不直接承担核心工作流/存储协调语义，不反向依赖 `src.*`；其后续封包、
视觉和 desktop smoke 由 `pkv-GUI` 的版本与测试策略负责。

### D. 可选 PKV Node（门禁项）

只有出现下列至少一项已记录的需求，才启动本工作包：

- 外部 GUI 关闭后任务必须继续执行；
- GUI、CLI、MCP 出现真实的并发写入协调需求；
- Provider、索引或长任务的复用成本已成为可测瓶颈。

前置条件：A 的共享应用服务已稳定；Vault 具备全局 `VaultLease`、维护模式、崩溃恢复和
跨进程竞争测试；需人工确认的任务具有 durable `awaiting_review` 状态。

最小范围：显式 `start/stop/status`、单写队列、版本握手和每用户本地 IPC（Windows
优先 Named Pipe）。Node 存在时，其他写入口不得绕过它直接打开 Vault。

明确非目标：自动拉起 daemon、Windows 服务、TCP/HTTP、Bearer、LAN/WAN、多人协作、
云同步。

### E. Docker 与云端部署（更晚的门禁项）

Docker 只在 D 已稳定且有 headless、可重复部署的 Node 需求时评估；它不是 GUI 自测包的
替代品。云端则需另行定义身份、租户、加密、同步冲突、费用和运维 SLA，不能从本地
Node 自然推导为当前计划。

## 4. 与当前封包链的关系

当前 `scripts/build-release.ps1` 已经能生成受合规 hold 约束的 `test_candidate`，并绑定
严格的可复现、payload 和 Artifact E2E 合同。它适合作为里程碑检查点，不适合每次外部
桌面 Wrapper 或工作流改动后的快速循环。

内部自测包是**额外的开发工具链**，不是放宽 release 工具链：

| 维度 | 内部自测包 | W3 test candidate |
| --- | --- | --- |
| 目的 | 开发者本人快速安装外验证 | 可复现 Artifact 与 W4 evidence |
| 输出 | `dist/internal/`，明确不可分发 | `dist/candidate/`，合规 hold 的候选 |
| 构建输入 | 可记录 dirty 状态 | 必须 clean checkout |
| 安装形式 | 解压/onedir 运行，不引入正式安装策略 | 受冻结 install/payload 合同约束 |
| 验收 | 合成 `.data-test` smoke | 完整 W3/W4 合同与 Artifact-only evidence |
| 结论 | 内部自测通过 | test-candidate 功能验证；仍非发布 |

## 5. 文档与实施纪律

- 所有 Node、Docker、云端内容在实现前必须保持 `planned` / `gated`，不得写成现有能力。
- 默认用户数据根、安装拓扑、MCP stdio-only 发布面和真实数据授权门禁维持当前合同。
- 每完成一个工作包，至少同步更新当前事实基线、阶段路线、对应模块接口/设计文档和
  内部包 smoke 记录；历史开发计划不回写为当前真相源。
- Core 的 Kernel 接口变更必须同步更新 `pkv_kernel` 的兼容性合同；GUI 生命周期、Qt
  依赖、桌面封包和 GUI 测试只在 `pkv-GUI` 仓库维护。
- 任何产品代码或封包自动化仍只在 `.data-test` 与合成数据上验证；真实 Vault、迁移和
  Provider 不因“内部自测”而获得额外授权。

## 6. GUI 剥离后的工作队列与门禁

以下队列替代原先把 GUI 当作 Core 工作包的排序。它们均不改变 release hold、默认数据根、
stdio-only MCP 发布面或真实数据授权门禁。

### K1a. 公开 Kernel 合同（已完成，Core）

目标：先冻结 `pkv_kernel` 的产品边界，使外部 Wrapper 有不依赖相邻 checkout、`src.*`
或内部对象的稳定编程合同；本工作包不引入发行或安装验证工作。

最小范围：

1. 固化公开 API 清单、SDK 语义版本与能力握手；握手必须允许 Wrapper 在导入后声明其
   最低/最高支持的 Kernel SDK 和所需能力。
2. 固化支持的 Python/平台范围、兼容矩阵与废弃规则：兼容版本内不移除已公开符号；
   先以可观察的 deprecation 经过一个兼容版本，再移除。
3. 增加公开 API 与依赖方向合同：`pkv_kernel` 不能反向依赖 CLI、MCP、GUI 或外部
   Wrapper；外部集成代码只可导入 `pkv_kernel`，`src.*` 始终是实现私有。
4. 明确配置和资源仍由 Kernel bootstrap 处理；不隐式改变默认用户数据根、迁移策略或
   Provider 授权。

退出条件：Core 有可执行的公开 API/能力握手/边界合同，`pkv-GUI` 可以据此声明其
最低/最高 SDK 兼容范围。它仍不是 wheel、正式发布或 PyPI 上线授权。

实施状态（2026-08-19）：**已完成**。`pkv_kernel.__all__`、`KERNEL_API_VERSION`、
版本/能力握手和 compatibility failure 由 executable contract 固定；详细规范为
`docs/specs/interfaces/KernelSDK公开合同.md`。该 source contract 没有构建或分发 wheel。

### K2. Kernel 配置快照与 reload 并发合同（已完成，Core hardening）

把 Kernel/Application 的 config、运行布局与惰性依赖发布为同一不可变快照，避免外部
Wrapper 的并发 worker 在 reload 窗口观察到 A/B 混合状态；明确显式 Config 的
`update_local_config()` 语义，并补“旧 in-flight / 新 reload”并发回归。K2 是外部 GUI
版本握手和设置页发布前的 Core 前置，不是 GUI 代码回流理由。

实施状态（2026-08-19）：**已完成**。默认 Application/Kernel 的 config graph 使用不可替换
snapshot 和递增 generation；reload 以同一生命周期锁发布新的 legacy Config identity、
Application 与 Kernel，旧 in-flight 操作保留旧 graph。归档、向量写入/读取与 vector
absent → present → related/delete 均由 Config B 的显式依赖路径覆盖回归。

### K1b. 本地 wheel 与 clean-install 兼容验证（已完成，Core）

目标：在 K1a 的公开合同和 K2 的运行时语义稳定后，验证本地构建的 wheel 能在干净目标中
仅通过 `pkv_kernel` 被导入和启动；它是离线兼容性验证，不是发布工作。

最小范围：

1. 新建可离线构建的 Python distribution 元数据并产出本地 wheel；不上传公共索引，
   不改变 release/test-candidate 链。
2. 在仓库外的干净安装目标中安装 wheel，验证 `pkv_kernel` 的版本/能力握手和最小
   Kernel 启动路径；目标不得从源码树或 `src.*` 导入。
3. 明确 wheel 中的资源定位与配置入口，并只用 `.data-test` 合成根验证；不得改变默认
   用户数据根、迁移策略或 Provider 授权。

退出条件：独立 checkout 可以只安装本地 wheel 后调用 K1a 公开 API；该结论只允许称为
本地 clean-install 兼容验证通过，不构成正式发布或 PyPI 上线授权。

实施状态（2026-08-19）：**已完成**。新增 `pkv-kernel` distribution 元数据和受控资源构建
hook；默认离线合同在仓库外临时目录构建 wheel、安装到 clean venv，并以 `-I` 子进程仅通过
`pkv_kernel` 验证 SDK/API 能力握手、wheel 内资源根和 `bootstrap_kernel()`。PKV 数据始终
留在 `.data-test` 合成根；payload 拒绝 `local.yaml`、CLI、MCP、GUI、PySide6 与 qasync。
当次 K1b 变更后的默认离线回归为 `2954 passed, 21 skipped, 219 deselected`；详见
`docs/specs/interfaces/KernelSDK本地Wheel验证合同.md`。

### R1–R4 / R3.1. 个人运行时与自动 AI 生命周期合同（source acceptance 完成，Core）

R1–R4 是 K1a/K2/K1b 后、知识成果能力前的运行时收敛包。它们已通过定向隔离回归、
最终默认隔离全量回归和 R4 的真实 CLI/MCP source blackbox，形成限定的内部 checkpoint；
所有验证只在 `.data-test` 与合成数据上进行，公开全流程另经 external deterministic Provider
harness；不改变 release hold、安装拓扑、stdio-only MCP 合同，也不构成真实数据操作授权。

1. **R1：配置和布局。** 唯一可编辑用户配置是
   `%USERPROFILE%\\.pkv\\config.yaml`，默认数据根是
   `%USERPROFILE%\\.pkv\\data`；`<data-root>/config/local.yaml` 仅为
   PKV 管理的无密钥 runtime snapshot。正式环境变量白名单只包含
   `PKV_DATA_ROOT` 和 `PKV_LOG_LEVEL`，历史路径变量只能作为
   `PKV_TEST_OFFLINE=1` 的测试注入 seam。
2. **R2：生命周期和 reload。** 运行时变更遵循 inspect → plan → 展示影响与备份
   → 用户确认 → execute；inspect 不初始化、不迁移、不探测 Provider。已启动操作
   固定使用其 snapshot，新操作只使用已原子发布的新 snapshot；数据根切换或用户配置
   源发生漂移必须重新计划，不能混用旧图和新图。外部配置与 runtime snapshot 的
   embedding provider/model/dimension/fingerprint 不匹配时，只产生需确认的重建计划，
   不自动改写活动索引。CLI 已用未创建嵌套合成 data root 回归 fresh setup plan、plan-only
   零写及 PLAN_ID / `--allow-network` 门禁，未放宽默认 wrapper 隔离。
3. **R3：共享数据根。** CLI、MCP 和未来 GUI 对受支持的业务/数据 mutation 采用一写多读；
   写操作必须先取得数据根 lease。竞争写入不会排队或隐式合并：MCP 返回可重试的
   `error_code="write_busy"`，读操作仍可继续。写操作也产生本地可追溯审计记录，且不记录
   API key、Authorization、Cookie 或 URL 凭据。
4. **R3.1：剩余 writer 与路径边界。** 运行时日志有明确的单 writer owner；Q0 在 root
   lease 下创建 task/fence 私有的短生命周期 image workspace，解析阶段在 lease 外仅可通过
   有效 Q0 claim 的窄 image-asset capability 写入。Q1′ core commit/recovery 会释放它，URL
   原始网页正文不保留本地副本。通用图片/文件附件是独立后续合同。历史 `backup*` / `restore*`
   PowerShell 入口 fail-closed，不能读配置或触碰数据根；不是当前维护 API。显式
   Config/layout-bound vector writer 同时受 DataRoot containment 和 writer lease 约束。若未来
   需要公开向量 rebuild，必须另走 inspect → plan → confirm → execute 的 public adapter。
5. **R4：自动 AI 生命周期。** archive 先进入 Q0 admission/PreparedDocument，再由 Q1′
   作为 Markdown + SQLite 和 DerivationPatch 的唯一内容 writer 提交 core mutation/handoff；
   Q2 在 policy、budget reservation 与 task fence 检查后调用 Provider，最后 stage → validate
   → 原子 pointer 发布 generation。失败不替换当前 generation，读者只绑定已验证 generation。
   该能力是 runtime 内部合同，不新增 `pkv_kernel`、CLI 或 MCP 的公共 rebuild/resume 接口，
   不引入 daemon，且只读入口不触发恢复；但在已授权的 archive mutation 内，Q2 会按正式
   Config 创建 Provider 并有界 drain。

最终验证记录（2026-09-03）：R4 lifecycle 定向回归 `103 passed`、真实 CLI/MCP 进程边界
黑盒 `2 passed`（独立重复运行也通过）、R3.1 收口后的 P0 `3284 passed, 21 skipped, 219 deselected, 35 warnings`、
MCP `779 passed, 5 deselected`（`src.mcp 95.15%`）和 Phase C `thresholds_met=true` 均已通过。
K1b 仅是本地 wheel/source-free clean-install 验证；R3.1 source hardening 已收口，R4 仍不
公开 rebuild action。只有实际需要的 public rebuild adapter gate 收口后，才进入 B 的实现主线。

### B. 高阶知识成果能力（public-adapter gate 后的下一价值主线，Core）

1. 定义 `Topic / Claim / Evidence / Outcome` 的最小合同：每个主张能回链到条目、chunk
   或关系证据 locator，并能表达缺证、降级和不确定性。
2. 复用 `collect_evidence`、关系查询和 Workflow，形成
   `主题 → 证据账本 → 大纲/文章骨架/研究简报 → 审阅` 的最小闭环。
3. 将需要用户确认的步骤持久化为可恢复状态，而不是依赖某个 CLI/Rich 进程一直存活。
4. 对 `partial-v1` 探索 Tool 按真实使用场景逐个补 full 语义、专属评测和失败边界；
   不为“功能数量”整体升级实现等级。

退出条件：至少一种成果类型可由 CLI、MCP 或兼容的外部 Wrapper 发起，并公开其证据链与
限制；不会把没有证据的生成内容伪装为知识库事实。

### H. 后续 Core hardening（不阻塞 K1 的最小交付）

1. **内部封包资源与 smoke 证据深度**：进一步消除最终 ZIP 整包读入和 PYZ
   `marshal.load()` 的资源峰值；BM25 smoke 改为断言已知合成 seed 命中，MCP smoke
   增加 `tools/list` 与只读调用。内部 smoke 仍不是 egress sandbox，也不是 release
   安全证明。
2. **无 GUI 回流门禁**：将 Core 的 Qt/GUI-free 源码、依赖、测试和 payload 约束固定为
   可执行架构合同；GUI 专属测试继续只在外部仓库维护。
3. **冻结构建环境清理**：`release-environment.v2.json` 仍是拆分前工具链快照，其中 Qt
   记录不等于运行时 payload；仅在未来明确重开 release 时，才在 GUI-free 受控环境重新
   生成并复核。
4. **Windows-first 测试基线**：当前只维持 Windows 平台的测试与内部验证；完整 POSIX/CI
   parity 测试工程留待 Rust 代码版本再重新评估，不把 fresh-install 范围外的历史数据问题
   包装成 K1/K2 已完成。
5. **R4 public rebuild adapter gate**：如要暴露向量重建，先补 inspect → plan → confirm →
   execute 的公开 adapter、稳定错误投影及专属 fake-only 回归。它不构成 release 或 PyPI
   工作。

### 外部 GUI 与后置门禁

- **`pkv-GUI` 独立发布链**：Qt/OS smoke、桌面封包、升级策略、GUI 生命周期与视觉测试
  由外部仓库所有。其首个独立发行至少应验证安装版 `pkv_kernel` 的版本握手；不得重新把
  Qt 或 `pkv-gui.exe` 带回 Core payload。
- **真实数据与历史迁移**：真实 Vault、历史向量语义扫描和原地迁移仍受 U1/G8/FT5
  user-only gate 阻塞；只可在用户授权的脱敏快照与 writable clone 上另行验证。
- **Node / Docker / 云端**：仍保持 D/E 门禁。只有后台任务、跨入口并发写入或资源复用
  出现可测需求，且 VaultLease、维护模式、持久任务状态与本地 IPC 前置完成后，才启动 Node；
  Docker 与云端继续位于其后。
