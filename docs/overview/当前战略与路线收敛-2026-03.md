## 2. 当前统一定位

Personal Knowledge Vault 当前应被定义为：

**面向 AI 与人的、本地优先的知识操作系统内核。**

它的核心不是做一个重交互、重编辑体验的知识库 GUI，而是提供：

- 稳定的知识归档能力
- 可组合的工作流能力
- 面向 AI Agent 的 MCP 能力
- 混合检索与关系探索能力
- 可验证、可维护、可重建的本地数据底座

更直接地说：

- `GUI` 是辅助工作台，不是主产品定义
- `MCP` 不是附属接口，而是一等交互面
- `关系层` 和 `多跳检索层` 是下一阶段最值得投资的差异化能力

## 3. 当前事实基线

从现有代码、README 和近期设计文档看，当前项目已经不再处于“原型设想期”，而是具备了以下现实基线：

### 3.1 已成形的能力层

- `CLI`：用于归档、搜索、浏览、统计、配置
- `MCP`：已具备搜索、详情读取、列表浏览、归档、关联推荐，以及最小关系推理与受限探索能力
- `GUI`：已经不是纯计划项，而是实际存在的桌面入口
- `Workflow`：仍然是核心编排机制
- `Storage`：Markdown 主存储 + SQLite + hnswlib 的组合已经成为事实标准
- `Relations`：已具备基础模型、存储、迁移、最小 extraction / backfill、一跳查询、多跳子图、关系解释与 chunk-aware 证据包聚合；桥接/时间线/对比已按 `partial-v1` 交付，公开合同仍为 `implementation_level=partial`
- `Evaluation`：Phase C 固定离线闭环已达到 16/16 tasks、119/119 checks、`overall=1.0`、`citability=1.0`、0 failed、`thresholds_met=true`
- `Operations`：FT7 Direct Python 离线入口与开发 vault 重建脚本已交付；合成重建演练达到 `rebuilt -> up_to_date -> checked`（schema `1.2.3`、8 migrations、3 seed）

### 3.2 当前最重要的能力缺口

当前系统已经从“检索型 MCP”进入“最小可推理知识接口”阶段，但高阶推理闭环仍未完成。

缺口主要体现在：

- `get_related` 仍更像近邻推荐，不是稳定的知识网络探索接口
- `collect_evidence` 当前已支持 chunk-aware 路径（`include_chunks=True`）与文档级兼容路径（`include_chunks=False`），并通过 `chunk_retrieval_status` 区分 `success` / `no_hits` / `path_unavailable` / `search_error`
- `find_bridges` 当前已引入局部图桥接信号与轻量文本重合，但仍缺少全局中心性与语义关系边
- `timeline_of` 当前优先使用 `event_time > published_at > archived_at` 的结构化真实时间字段；当多种时间源并列主导时 `inferred_time_field` 返回 `mixed`，但仍不代表正文事件抽取后的真实时间线
- `contrast` 当前已引入跨主题显式关系路径与 `relation_graph_signal`，但仍缺少争议/补充/因果等高级语义对比建模
- 离线最小评测闭环已经形成；尚未覆盖的是需用户授权的真实快照验证，而不是 Phase C 固定评测
- 真实快照仍受 U1/G8 与迁移 FT5 阻塞，本轮没有执行真实数据

## 4. 战略收敛结论

### 4.1 当前主战场

离线基线收口后的顺序应明确为：

1. `M13` 离线开发与发布准备
2. 根据实际需求继续增强 `partial-v1` 探索 Tool 的 full 语义能力
3. U1/G8 与 FT5 交付后，再规划用户授权的真实快照验证

M13 是离线基线后的下一阶段，不等于真实数据验收。

### 4.2 GUI 的定位

GUI 继续保留，但定位应收敛为：

- 浏览与调试工作台
- 归档结果和任务状态查看器
- 关系链和条目详情检查器
- 配置、索引、成本和系统状态面板

不再把 GUI 定义为当前阶段的主要竞争力来源，也不以“替代命令行”为近期首要成功标准。

### 4.3 审核系统的定位

审核系统属于“工作流完整性增强”，它有价值，但不应遮蔽主线判断：

- 审核系统解决的是 AI 输出可控性问题
- MCP + 关系层解决的是知识环境可推理性问题

两者都重要，但后者更接近 PKV 的长期护城河。

## 5. 近期路线建议（6~8 周）

### P0：建立关系层基础

目标：把“知识关联”从概念提升为可实现、可演化的系统层。

建议交付物：

- `relation_index` 或等价模块设计文档
- 关系类型定义
- 关系抽取/存储/查询边界
- 与现有 Markdown/SQLite/向量索引的协同方式

建议至少覆盖四类关系：

- 显式关系：链接、引用、标签、来源、作者、时间
- 结构关系：主题层级、系列内容、版本演化
- 语义关系：相似、对比、补充、争议、因果
- 工作流关系：摘要、任务、评论、审核、问题的派生链路

### P1：升级 MCP 为可推理接口

在现有 `search_knowledge / get_entry / get_related` 之上，优先考虑新增高价值 Tool：

- `query_subgraph(query, depth, relation_types)`
- `explain_relation(a, b)`
- `collect_evidence(question)`

次优先级候选：

- `find_bridges(seed, top_k)`
- `timeline_of(topic)`
- `contrast(topic_a, topic_b)`

当前状态补注（2026-07-31）：

- `query_subgraph`、`explain_relation`、`collect_evidence` 已经在代码与 MCP 层落地
- `find_bridges`、`timeline_of`、`contrast` 已按 `partial-v1` 最小可用口径交付，且继续公开 `implementation_level=partial`
- Phase B citation 合同已经收口；这不代表三个 Tool 已达到 full implementation，事件抽取、全局语义桥接与高级对比仍可后续增强
- Phase C 已在不降低 gold、proposals、119 项检查或阈值的前提下通过固定离线验收

### P2：建立评测与验证机制

如果没有验证机制，关系层和高阶 MCP Tool 很容易变成“看起来高级”的功能。

建议建立最小评测集：

- 多跳查询样例
- 关系解释样例
- 证据包质量样例
- 时间线重建样例

评测维度：

- 命中率
- 可解释性
- 噪声控制
- AI Agent 调用后的可用性

当前状态（2026-07-31）：上述最小评测集和阈值门禁已交付，固定结果为
16/16 tasks、119/119 checks、`overall=1.0`、`citability=1.0`、
0 failed、`thresholds_met=true`。后续扩展不得把该离线基线写成真实数据结论。

### P3：GUI 收敛为工作台

GUI 继续维护，但控制范围，不把资源消耗在重交互打磨上。

建议保留的重点：

- 搜索浏览
- 条目详情
- 关系结果查看
- 审核/归档状态查看
- 配置与统计

## 6. 当前阶段的非目标

以下内容不应作为当前阶段的主投入方向：

- 重视觉打磨的 GUI 设计
- 知识图谱可视化优先落地
- 视频/PDF 等多模态扩张优先于关系层
- 为了完整而继续扩张历史 Prompt 路线
- 在没有关系层设计之前直接堆更多界面功能
