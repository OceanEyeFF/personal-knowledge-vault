## 2. 当前统一定位

Personal Knowledge Vault 当前应被定义为：

**面向 AI 与人的、本地优先的知识操作系统内核。**

它的核心不是做一个重交互、重编辑体验的知识库 GUI，而是提供：

- 稳定的知识归档能力
- 可组合的工作流能力
- 面向 AI Agent 的 MCP 能力
- 混合检索与关系探索能力
- 可验证、可维护、可重建的本地数据底座

更直接地说：

- `pkv-GUI` 是独立仓库中的辅助 Kernel Wrapper，不是核心仓库的产品定义
- `MCP` 不是附属接口，而是一等交互面
- `关系层` 和 `多跳检索层` 是下一阶段最值得投资的差异化能力

## 3. 当前事实基线

从现有代码、README 和近期设计文档看，当前项目已经不再处于“原型设想期”，而是具备了以下现实基线：

### 3.1 已成形的能力层

- `CLI`：用于归档、搜索、浏览、统计、配置
- `MCP`：已具备搜索、详情读取、列表浏览、归档、关联推荐，以及最小关系推理与受限探索能力
- `pkv-GUI`：独立本地仓库中的桌面入口，只通过 `pkv_kernel` 消费稳定 Kernel API
- `Workflow`：仍然是核心编排机制
- `Storage`：Markdown 主存储 + SQLite + hnswlib 的组合已经成为事实标准
- `Relations`：已具备基础模型、存储、迁移、最小 extraction / backfill、一跳查询、多跳子图、关系解释与 chunk-aware 证据包聚合；桥接/时间线/对比已按 `partial-v1` 交付，公开合同仍为 `implementation_level=partial`
- `Evaluation`：Phase C 当前 fresh run 已达到 16/16 tasks、151/151 checks（119 项版本化声明式检查 + 32 项自动公开 envelope 检查）、`overall=1.0`、全部维度 `1.0`、0 failed、`targets_met=true`
- `Operations`：FT7 Direct Python 离线入口与开发 vault 重建脚本已交付；当前 migration chain 末端为 `1.2.6`（11 个 migration 文件），历史 1.2.4/9-migration 演练只代表当时快照
- `R4`：归档在 Application 内部经过 Q0 admission、Q1′ Markdown/SQLite commit/handoff、Q2 policy/usage/generation；真实 CLI 和 MCP stdio 已各自证明重启后 vector/hybrid retrieval 命中

### 3.2 当前最重要的能力缺口

当前系统已经从“检索型 MCP”进入“最小可推理知识接口”阶段，但高阶推理闭环仍未完成。

缺口主要体现在：

- `get_related` 仍更像近邻推荐，不是稳定的知识网络探索接口
- `collect_evidence` 当前已支持 chunk-aware 路径（`include_chunks=True`）与文档级兼容路径（`include_chunks=False`），并通过 `chunk_retrieval_status` 区分 `success` / `no_hits` / `path_unavailable` / `search_error`
- `find_bridges` 当前已引入局部图桥接信号与轻量文本重合，但仍缺少全局中心性与语义关系边
- `timeline_of` 当前优先使用 `event_time > published_at > archived_at` 的结构化真实时间字段；当多种时间源并列主导时 `inferred_time_field` 返回 `mixed`，但仍不代表正文事件抽取后的真实时间线
- `contrast` 当前已引入跨主题显式关系路径与 `relation_graph_signal`，但仍缺少争议/补充/因果等高级语义对比建模
- 离线最小评测闭环已经形成；尚未覆盖的是需用户授权的真实快照验证，而不是 Phase C 固定评测
- 真实快照仍受用户明确授权与 U1/G8 阻塞；其中 migration 场景另需 FT5，本轮没有执行真实数据

## 4. 战略收敛结论

### 4.1 当前主战场

离线基线收口后的顺序应明确为：

1. `W2 冻结 → W3-T0 短期 Test 治理 → W3 正式打包链 → W4 Artifact E2E` 已完成 M13 的功能验证链；候选继续保持 held status，当前不安排合规收口或正式发布。
2. 后 M13 的 P1-A 已收敛共享应用服务/Kernel 边界，P1-C 已把 GUI 完整迁至独立 `pkv-GUI` 仓库；GUI 剥离后的 Core 默认离线重测为 `2947 passed, 21 skipped, 219 deselected`。这些结论不改变 M13 的发布面、安装拓扑或 release 判断。
3. S0/K1a 已冻结 `pkv_kernel` 的公开 API、版本/能力握手、兼容与废弃合同，K2 已建立 snapshot/reload 语义；K1b 的离线本地 wheel/source-free clean-install 已完成内部验证。外部 Wrapper 不得继续依赖相邻 checkout 或 `src.*`，上述结果不构成 PyPI、安装器或 release 授权。
4. R1 → R4 的限定内部 checkpoint 已通过定向隔离回归与真实 CLI/MCP source blackbox：唯一用户配置、数据布局和 runtime snapshot，inspect/plan/confirm/execute，受支持业务/数据写入的 lease、`write_busy`、审计及 Q0→Q1′→Q2 自动 AI lifecycle 均有回归证据。R2 CLI 已补 nested fresh-root adapter 回归，覆盖 setup plan、plan-only 零写及 PLAN_ID / `--allow-network` 门禁。R3 不宣称所有文件系统写入已串行化；R4 仍仅为 runtime-internal 合同，未成为 Kernel/CLI/MCP 的公共重建功能。
5. R3.1 的运行时日志写入归属、Q0 私有 temporary-image workspace、路径 containment 与历史维护 writer fence 已收口；若 B 需要暴露向量重建，还须先完成相应的 public rebuild adapter gate。该独立 gate 收口后，才把现有关系、检索和证据能力收束为可追溯知识成果工作流；`partial-v1` 的 full 语义仍须按真实场景逐 Tool 补强与评测。
6. `pkv-GUI` 的封包、Qt/OS smoke、生命周期与升级策略由外部仓库负责；可选 Node 必须等到后台任务、并发写入或资源复用出现可测需求后才启动，Docker 只能在 Node 稳定后评估。
7. 用户明确授权且 U1/G8 交付后，再规划真实快照验证；只有 migration 场景另需 FT5。

M13 已完成 W3 与 W4 的拆分前 installed-Artifact 功能验证。外部 artifact-only 运行 `w4-53a45ed` 为 10 scenario / 11 matrix rows / 10 verified / 0 failed / 0 pending，`functional_verified=true`；当前 headless Artifact 仍为 `test_candidate`，`release_eligible=false`、`decision=hold`，这不等于正式发布或真实数据验收。

当前核心发布面是 Windows-first、offline、fresh-install 的 Developer Preview，支持 headless Kernel、CLI 与 MCP stdio；GUI 在独立仓库发布。HTTP MCP、原地升级、真实数据质量和三个探索 Tool 的 full 语义均不默认纳入 M13。

### 4.2 外部 GUI 的定位

`pkv-GUI` 继续作为独立 Wrapper，定位应收敛为：

- 浏览与调试工作台
- 归档结果和任务状态查看器
- 关系链和条目详情检查器
- 配置、索引、成本和系统状态面板

它不反向决定 Kernel 的内部结构，也不以“替代命令行”为核心仓库的近期成功标准。

### 4.3 审核系统的定位

审核系统属于“工作流完整性增强”，它有价值，但不应遮蔽主线判断：

- 审核系统解决的是 AI 输出可控性问题
- MCP + 关系层解决的是知识环境可推理性问题

两者都重要，但后者更接近 PKV 的长期护城河。

## 5. M13 近期执行路线（W1-W4）

2026-08-01 已确认沿用现有开发文档维护 M13，不再新建平行规划。详细范围、依赖和 DoD 以
[`阶段开发路线与依赖-2026-03.md`](./阶段开发路线与依赖-2026-03.md)
为执行真相源，本节只保留战略摘要。

### W1：运行时布局与数据安全底座

- 收口跨存储一致性、补偿/修复终态和 Vault containment
- migration 至少做到损坏库不冒充 fresh，备份或迁移失败不继续、不半提交
- 拆分 bundled 只读资源与 local config、DB、Vault、vectors、logs、tmp 等用户可写目录

W1 是 W2-W4 的硬前置；除非 M13 明确承诺原地升级，否则完整历史迁移矩阵与 FT5 不进入当前范围。

状态复核（2026-08-07）：W1 已按详细路线完成实现、合成故障注入和独立安全复审；SQLite operation-bound commit proof、Markdown identity + SHA-256 与 Vector 持久 pair marker 已纳入冻结合同。W1 冻结时离线验收为 unit `1583 passed, 19 skipped`、integration/blackbox/e2e `277 passed, 9 deselected`，其上层 W2 功能合同现也已完成。完整范围、后置风险与 DoD 仍以链接的详细路线为准；该状态不代表 W3 Artifact 或 W4 发布审查已经完成。

### W2：已发布功能合同

以下四条工作流可在 W1 合同稳定后并行：

- Workflow：真实 YAML 的 step、`on_error`、trigger、condition 与 processor 路由
- Retrieval：优先区分 `success/no_hits/invalid/error/degraded`；精确 RRF 后置 P1
- MCP：provider、SSRF 与 stdio；HTTP Bearer 仅在 HTTP transport 被纳入发布面时阻断
- GUI Chat：session 切换、双发、停止及 provider/save 失败的互斥终态

已声明的三个 `partial-v1` Tool 可以保留，但必须继续通过既有 oracle 且不得冒充 full；其他发布能力不能用含混的“部分支持”规避合同，无法满足时必须从 M13 支持面移除。

状态复核（2026-08-11）：Workflow、Retrieval、MCP 与 GUI Chat 四条线均已完成源代码实现、确定性 fixture/故障注入、adapter 终态传播和独立复审，未发现确定性 P0/P1。W2 registry 中受支持、`partial-v1` 及明确不支持的源代码能力为 `source_verified`；MCP HTTP 仍为 `defined`，W3 外置 Chat loopback harness 为 `packaging_contract_verified`、仍无产品 surface。W4 handoff 声明仍为 `artifact_pending`，其 artifact-only evidence 已独立完成。Phase C fresh run 为 16/16 tasks、151/151 checks、全部维度 `1.0`、0 failed、`targets_met=true`。详细合同与已知后置边界见上述执行真相源。

### W3-T0：短期 Test 治理

W3-T0 已于 2026-08-10 完成并通过独立 CodeReview（P0=0、P1=0）。它以已冻结并提交的 W2 为输入，现已解除正式 W3 的前置门禁：

- `source` lane 只主责 W1/W2 领域语义与 `source_verified`；`packaging-contract` lane 只主责构建入口、payload/manifest/hash/SBOM 与外置 harness 合同；`artifact-only` lane 只主责安装后 W4 evidence。每个行为 oracle 只有一个 owner，跨 lane 只验证交接边界
- W2 的 `artifact_pending` handoff 只是待验用户路径声明，不是 W4 evidence；只有 artifact-only runner 绑定实际 Artifact hash、从安装入口执行后才能产生 `artifact_verified`
- Artifact、安装入口、manifest、fixture 或所需 harness 任一缺失都必须 fail，不得 skip 或回退源码；runner 必须从仓库外 cwd 运行，隔离仓库 `PYTHONPATH` 并证明没有从仓库加载或 `import src`
- 修改 `QSettings` 默认格式、Qt organization/application identity 等可快照进程全局状态的测试，必须在 pass、fail、skip 后全部恢复；因 Qt 无公开 path getter，自动化禁止调用 `QSettings.setPath()`
- W3-T0 必须先冻结从 payload/provenance、安装/首次运行/重启，到 GUI/BM25、离线归档、URL SSRF 拒绝、semantic provider unavailable、Chat、MCP stdio、升级拒绝、卸载/数据保留、文档/版本/发布裁决的完整 W4 lifecycle matrix；精确行级 oracle 以详细路线为准
- 大规模删测/去重、通用 mutation testing、POSIX/CI parity 与性能治理后置；当前只做阻塞 W3/W4 的最小 owner 调整和确定性故障注入
- 最终证据：默认离线全量 `3492 passed, 20 skipped, 21 deselected`；MCP coverage `758 passed, 2759 deselected`、`src.mcp=95.33%`；Phase C `16/16 tasks`、`151/151 checks`、全部维度 `1.0`；显式合成 Artifact lane `12 passed`

### 正式 W3：可复现打包链

W3-T0 门禁已经通过，正式 W3 已完成可复现 test-candidate 打包链与 payload 外 loopback harness 交付。

- 从干净 checkout 通过单一非交互入口生成 Windows Artifact
- 显式打包配置、workflows、migrations、Qt/native 依赖及许可证材料
- 记录版本、构建指纹、Artifact 哈希与第三方依赖
- 交付独立的 deterministic loopback Provider E2E harness；它不进入 release payload，Artifact 只通过正常 provider 配置接入，不增加测试后门
- 保证安装包不携带密钥、local config 或 Vault 数据

### W4：Artifact E2E、文档与发布审查

W4 已完成 artifact-only installed-Artifact 执行：10 个 scenario / 11 行 matrix 均已验证，记录为 `artifact_verified`；该功能结论不解除候选的合规 hold。

- 由 artifact-only lane 在无需 Python/Conda/源码的环境中执行详细路线所列完整 lifecycle matrix，不接受源码树 smoke 或 W2 handoff 代替
- 保持默认离线全量、MCP coverage gate 和 Phase C 16-task 门禁通过
- 完成安装、数据位置、配置、备份恢复、升级/卸载、故障排查和 `partial-v1` 限制文档
- 应用、文档与 Artifact 统一为 `0.8.1`，最终给出明确 `release / hold`

### 后 M13 路线

- M13 release 分支保持 hold，当前不安排合规收口或正式发布；相关 blocker 只在未来明确重开发布时恢复为 P0。
- GUI 模块拆分以及 S0/K1a/K2/K1b 的 Kernel 基础合同已完成限定内部验证；R1 配置/布局、R2 生命周期、R3 受支持业务/数据写入 lease/审计、R3.1 writer/path hardening 与 R4 Q0→Q1′→Q2 lifecycle 亦已完成 source acceptance。按需的 public rebuild adapter 仍是独立 P1；其后才进入可追溯知识成果价值线。R4 仍不提供 Kernel、CLI 或 MCP 的公共重建接口。详细 DoD 以 [后M13开发路线-2026-08.md](./后M13开发路线-2026-08.md) 为准。
- GUI 独立发布是 `pkv-GUI` 的工作；Core 只维护公开 Kernel API、版本握手和 GUI-free 架构门禁。
- 默认休眠的真实数据线保持独立；如恢复，先取得用户明确授权并完成 `FT1 → U1/G8`，再按 migration/MCP evidence/delete 指标启用 FT5/FT6/FT3。
- Node 仅在有可测后台/并发/资源复用需求时进入开发；Docker、云端、重视觉、复杂编辑器、图谱可视化与多模态扩张继续后置。

## 6. 当前阶段的非目标

以下内容不应作为当前阶段的主投入方向：

- 重视觉打磨的 GUI 设计
- 为 M13 新增复杂编辑器或知识图谱可视化
- 视频/PDF 等多模态扩张
- 默认启用 HTTP MCP、历史库原地升级或真实数据验收
- 在没有真实需求和 full 专属评测前整体晋级三个 `partial-v1` Tool
- 为了完整而继续扩张历史 Prompt 路线
- 在没有单写者、持久任务和本地 IPC 需求证据前把 PKV 改造成常驻 daemon、Docker 或云服务

## 9. 一句话总结

PKV 已具备 **AI 可推理、可解释、可多跳探索** 的最小离线基线，并已完成 M13 W1/W2/W3 与 W4 Artifact 功能验证；当前候选保持合规 hold。GUI 已外置，S0/K1a/K2/K1b、R1→R4 与 R3.1 writer/path hardening 的限定内部合同已通过验证；R4 source acceptance 已证明 Q0→Q1′→Q2 与跨进程 semantic retrieval，但仍只作为 runtime-internal lifecycle，不提供公共 rebuild/resume 动作。按需的 public rebuild adapter 是进入可追溯知识成果前的独立 P1 gate。Node/Docker 与尚未获准执行的真实数据验收继续分开、按门禁管理。
