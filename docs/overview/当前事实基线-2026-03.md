## 2. 当前产品定义

Personal Knowledge Vault 当前应被理解为：

**面向 AI 与人的、本地优先的知识操作系统内核。**

它当前的核心不是重交互知识库 GUI，而是：

- 稳定的内容归档能力
- 工作流驱动的处理管线
- 面向 AI Agent 的 MCP 能力
- 混合检索能力
- 可维护、可重建的本地数据底座

---

## 3. 当前不是什么

以下内容不应作为当前阶段的主产品定义：

- 不是 Obsidian 风格的重编辑 GUI
- 不是以视觉和交互体验为主竞争力的桌面应用
- 不是只提供 `search/get/list` 的轻量文档库包装层
- 不是以图谱可视化为当前优先目标的知识图项目

## 4. 当前已落地能力

### 4.1 交互面

- `CLI`：归档、搜索、浏览、统计、配置
- `MCP`：通过 stdio 提供基础搜索、详情读取、列表浏览、标签统计、URL/文本归档、关联推荐；M13 不发布 HTTP/Bearer
- `pkv-GUI`（外部仓库）：桌面工作台 Wrapper；其搜索、浏览、归档、设置、统计和聊天体验不属于本 Core 的代码、测试或封包面，只经 `pkv_kernel` 访问 Kernel

### 4.2 系统能力

- `Workflow`：只从真实、版本化 YAML 加载 `archive-url` 与 `archive-text` 归档流程；`search.yaml` 不受支持
- `Storage`：Markdown 主存储 + SQLite 元数据 + generation-bound hnswlib 向量索引
- `Retrieval`：BM25、向量检索、混合检索、自动路由
- `Relations`：已落地关系模型、关系存储、显式迁移、低歧义关系 extraction / backfill 与一跳 query service
- `AI`：摘要、标签提取、Embedding、基础知识引用；R4 的实际 usage、reservation 和可选 price-card 控制均为内部 durable ledger
- `Application`：CLI、MCP 与外部 Wrapper 经 `KnowledgeApplication` / `pkv_kernel` 共享业务调用边界；归档在内部走 Q0 admission → Q1′ 内容提交 → Q2 AI 派生，Provider 与向量依赖仍按操作惰性创建
- `Testing`：已有单元、集成、黑盒、E2E 测试基础
- `Internal package`：可生成明确标记为 `INTERNAL TEST ONLY` 的 onedir/ZIP，并只在合成 `.data-test` 根执行仓库外 smoke

### 4.3 当前接口快照

当前已核验的交互面如下：

- `CLI` 核心命令：`archive` / `archive-text` / `search` / `show` / `list` / `tags` / `related` / `config` / `stats`
- `MCP Tool`：15 个（13 个只读 + 2 个写入）：`get_runtime_status` / `search_knowledge` / `get_entry` / `list_tags` / `list_entries` / `get_stats` / `archive_url` / `archive_text` / `get_related` / `query_subgraph` / `explain_relation` / `collect_evidence` / `find_bridges` / `timeline_of` / `contrast`
- `MCP Prompt`：3 个
- `MCP Resource`：9 个
- `pkv_kernel`：外部 Wrapper 唯一可导入的 Core API；S0/K1a 已冻结公开 API/版本能力握手/兼容性合同，K2 已建立配置 snapshot/reload 基线，K1b 已完成本地 wheel/source-free clean-install 的内部验证。R1→R4 的运行时强化已通过最终默认隔离全量回归；R4 仍不是公开 rebuild API，以上均不构成 PyPI、安装器或 release 资格。

默认自动化继续保持离线：只使用 `.data-test` 隔离根、合成数据与可控 mock；不连接真实 Provider，不读取真实 API key 或真实 Vault。W3 已交付、W4 已使用外置 deterministic loopback harness 完成 Chat Artifact E2E；harness/fake provider 不进入 release payload。

## 6. 当前关键缺口

当前系统已具备检索型 MCP、最小推理接口、固定离线引用契约和 Phase C
最小评测闭环；三个高阶探索 Tool 已按 `partial-v1` 交付，但仍诚实声明
`implementation_level=partial`，没有升级为 full implementation。

主要缺口如下：

- 关系层已经补上最小 extraction / backfill / 一跳 query，并新增内部多跳子图遍历、最小关系解释、chunk-aware 证据聚合，以及桥接/时间线/对比的 partial implementation；但这些高阶能力仍未形成完整闭环
- `get_related` 仍以向量相似度近邻为主，不等于关系探索
- `collect_evidence` 当前已支持 chunk-aware 路径、稳定 chunk locator 与文档级兼容路径；真实库样本覆盖与更完整的验收口径仍待收口
- `find_bridges` 当前已在显式关系子图与 tags/标题/摘要重合之外，引入局部图桥接信号（断开邻居对、深度跨度）并返回逐跳 `evidence_path`，但不代表完整语义桥接
- `timeline_of` 当前会优先使用 `event_time > published_at > archived_at` 的结构化真实时间字段，并显式返回 source 与时间字段 locator，但不代表正文中的真实事件时间
- `timeline_of` 当前在多时间源并列主导时会把 `inferred_time_field` 返回为 `mixed`，用于避免单一高优先级字段导致整体偏乐观
- `contrast` 当前已在检索候选、tags、摘要与稳定对比维度结构之外，引入跨主题显式关系路径、`relation_graph_signal` 与候选—来源 provenance，但不代表完整语义对比
- 已建立并验收 Phase C 最小离线评测闭环：16 条固定任务通过真实 FastMCP
  `list_tools` / `call_tool` / `read_resource` 执行，当前 fresh run 为 151/151 checks
  （119 项版本化声明式检查 + 32 项自动公开 envelope 检查）、`overall=1.0`、
  全部维度 `1.0`、0 failed、`targets_met=true`。
- 当前独立 baseline proposals 的 Tool 选择/参数/结果、chunk 相关性与
  partial/degraded 可观察性及可引用性均通过，详见
  `docs/operations/MCP最小评测基线-2026-07-29.md`。
- Phase B citation 合同已完成，当前采用 `threshold_enforced` 策略：固定
  报告 schema、独立 gold/proposals、119 项声明式检查、32 项自动公开 envelope 检查与现有阈值；CLI
  `--enforce-thresholds` 将阈值结果升级为退出码门禁。
- R3.1 已收口运行时日志的 lease-owned 写入、任务/fence 私有 Q0 temporary-image workspace、显式 Config/layout 向量写入的 containment + lease，以及历史维护入口的 fail-closed fence；这仍不应被表述为“所有文件系统写入均已串行化”。R4 的 public rebuild adapter、自动清理和公开 rollback 同样仍属未来工作；R4 内部 Q0→Q1′→Q2 已完成 source acceptance，但没有被提升为 daemon 或公共 resume/rebuild 能力。

## 7. 当前主战场

离线基线收口后的工作顺序是：

1. M13 W1/W2/W3 已完成；W4 Artifact E2E 已给出拆分前 candidate 的历史功能证据。候选继续保持 hold，当前不安排合规收口或正式发布。
2. 后 M13 的 P1-A 已收敛 CLI/MCP 与外部 Wrapper 到 `KnowledgeApplication` / `pkv_kernel`，P1-C 已完整剥离 GUI；2026-08-18 的 headless 默认离线重测为 `2947 passed, 21 skipped, 219 deselected`。这不等于发布，也不改变当前默认数据根或安装拓扑。
3. S0/K1a 已冻结 `pkv_kernel` 的公开 API、版本/能力握手、兼容与废弃合同，K2 已建立 Kernel 配置 snapshot/reload 基线；K1b 已完成本地 wheel/source-free clean-install 内部验证。外部 Wrapper 不得依赖相邻 checkout 或 `src.*`，这些结论不授予发布或 PyPI 权限。
4. R1 配置/布局 → R2 生命周期 → R3 受支持业务/数据写入的 lease/审计 → R4 Q0→Q1′→Q2 自动 AI lifecycle 已通过定向隔离回归与真实 CLI/MCP source blackbox。R3 不宣称所有文件系统写入已串行化；R4 目前仍不提供 Kernel、CLI 或 MCP 的公共重建接口。
5. R3.1 writer/path hardening 已完成；实际需要时的 R4 public rebuild adapter 是独立 P1 gate。该 gate 收口后，才把现有证据与关系能力收束为可追溯知识成果。高阶探索 Tool 的 full 语义按真实场景逐个补强，不能抹去现有 partial 边界。
6. `pkv-GUI` 的 GUI 封包、桌面 smoke、生命周期与升级策略在独立仓库演进；Core 只维护其公开 API、版本握手和 GUI-free 门禁。
7. Node/Docker 仍未实现且必须等到后台任务、并发写入或资源复用的真实需求出现后才进入开发。
8. 在 U1/G8 与 FT5 交付后，另行规划用户授权的真实快照验证。

M13 是离线基线之后已完成的功能验证阶段，不代表真实数据已经验收，也不解除真实快照前置阻塞。

W1 当前事实（2026-08-07）：

- CLI、MCP 与外部 Wrapper 通过同一个 runtime bootstrap 解析只读 bundled resources 和单一用户数据根
- Markdown 主存储、SQLite/FTS/tags/chunks 必需索引和 Vector 辅助索引具有显式跨存储终态；失败不再被 adapter 伪装为空结果或完整成功
- operation journal v3 使用文件 identity + SHA-256；SQLite `storage_operation_commits` 与业务投影在同一事务提交，commit-after-raise 只按 operation-bound proof 对账
- Vector index/metadata 由持久 pair marker 保护，启动会回滚可证明的中断发布；未知替换保留现场并 fail-closed
- Vault 文件读写、删除、预览、证据读取和关系回填统一做 canonical containment，并拒绝链接、硬链接、same-inode 内容漂移和不可判定路径
- 只有完全不存在的数据库是 fresh；损坏、缺版本表、链/表漂移、旧版和未来版均 fail-closed，Developer Preview 不隐式升级历史库；当前 schema 为 `1.2.6`（12 个迁移）

- 独立 SubAgent 最终复审未发现确定性 P0/P1；非协作 ABA、Windows 掉电持久序及历史原地升级 WAL/列级 drift 为明确后置边界
- 冻结后离线验收为 unit `1583 passed, 19 skipped`、integration/blackbox/e2e `277 passed, 9 deselected`；未读取或改写真实 `.data/`
