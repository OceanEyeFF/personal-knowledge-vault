# 技术选型

> Personal Knowledge Vault - Technology Stack & Strategy
> 面向当前实现与下一阶段关系层演进的技术基线

**文档版本**: v2.1
**创建日期**: 2026-01-27
**最后更新**: 2026-08-21

---

## 1. 选型原则

PKV 的技术选型遵循以下原则：

1. **本地优先**
2. **低部署复杂度**
3. **数据主权优先**
4. **可重建索引**
5. **服务 AI Agent 的能力优先于花哨界面**
6. **为关系层和高阶 MCP 预留演进空间**

---

## 2. 为什么选择 Markdown + YAML Front Matter

### 2.1 核心判断

PKV 的主存储选择不是数据库，而是：

**Markdown + YAML Front Matter**

原因很直接：

- 人可读
- 可导出
- 可迁移
- 可版本控制
- 可被通用编辑器直接查看
- 不会因数据库损坏而失去核心知识内容

### 2.2 方案比较

| 方案 | 结论 |
|------|------|
| YAML Front Matter | 当前最佳平衡方案 |
| JSON 文件 | 机器友好，但人工维护体验一般 |
| TOML Front Matter | 可用，但生态和习惯不如 YAML |
| 纯数据库主存储 | 不符合 PKV 的长期数据主权目标 |

### 2.3 最终结论

主存储：

- Markdown 正文
- YAML Front Matter 元数据

辅助层：

- SQLite
- hnswlib

这意味着 PKV 的技术底座不是“数据库驱动文档系统”，而是“文件驱动、索引辅助”的知识系统。

## 3. 当前核心技术栈

### 3.1 语言与运行时

| 技术层 | 当前选型 | 说明 |
|--------|---------|------|
| 编程语言 | Python 3.11+ | AI 生态成熟，类型提示与异步能力可接受 |
| 环境管理 | Conda / venv | 本地开发和部署成本低 |

### 3.2 本地存储与索引

| 技术层 | 当前选型 | 说明 |
|--------|---------|------|
| 主存储 | Markdown + YAML | 长期事实源 |
| 元数据与全文索引 | SQLite + FTS5 | 零配置、本地优先 |
| 中文分词 | jieba | 配合 FTS5 使用 |
| 向量索引 | hnswlib | 本地 ANN 检索 |
| 路径解析 | 不可变 `Config` + `RuntimeLayout` | 将 Vault、SQLite、向量和日志绑定到同一有效 data root |

### 3.3 交互入口

| 技术层 | 当前选型 | 说明 |
|--------|---------|------|
| CLI | Click + Rich | 命令行与控制台输出 |
| MCP | 官方 MCP Python SDK + FastMCP | M13 仅发布 stdio；HTTP/Bearer 后置 |
| 外部 GUI Wrapper | `pkv-GUI`（独立技术栈） | 独立仓库；核心仅公开 `pkv_kernel` 接口，不携带 GUI 依赖 |

### 3.4 AI 能力

| 技术层 | 当前选型 | 说明 |
|--------|---------|------|
| 摘要 / 标签 | DeepSeek | 成本低，适合高频使用 |
| Embedding | OpenAI-compatible `text-embedding-3-small` | 当前向量化基线；由同一 `Config` snapshot 的 `ai.embedding.*` 决定，模型/维度与向量索引绑定，切换需重建索引并重算 Embedding |
| Provider HTTP | OpenAI SDK / httpx | 只用于显式配置的 LLM/Embedding；默认自动化离线 |

业务配置和数据路径是两种不同的状态：

- bundled `config/config.yaml` 与唯一可编辑的
  `%USERPROFILE%\\.pkv\\config.yaml` 合并为不可变 `Config` snapshot。
- 有效 data root 由 `PKV_DATA_ROOT` → 用户配置 `storage.data_root` →
  `%USERPROFILE%\\.pkv\\data` 选择；Vault、数据库、向量和日志子路径只从该
  snapshot 的 `RuntimeLayout` 派生。
- `<data-root>/config/local.yaml` 是 PKV 写入的无密钥 runtime snapshot，用于
  runtime/数据库/Embedding 合同校验，绝不是 Provider 或业务配置层。

### 3.5 内容处理

| 功能 | 当前选型 | 说明 |
|------|---------|------|
| 网页抓取 | `urllib3>=2.2,<3` + DNS-pinned `SafeFetcher` | 固定验证过的 IP，保持 Host/SNI/证书 hostname；每跳 redirect 与子资源重校验 SSRF |
| 正文提取 | Readability / lxml 路线 | 去广告和正文提取 |
| Markdown 转换 | html2text | 将网页正文转为 Markdown |

## 4. 为什么不是更重的后端方案

### 4.1 不采用 PostgreSQL / pgvector 作为当前主线

这类方案并非绝对错误，但不适合作为 PKV 当前主线基础设施：

- 部署复杂度更高
- 与“本地优先、低依赖、可长期维护”的目标不完全一致
- 当前数据规模和单机场景下收益不明显

因此当前事实是：

- 不以 PostgreSQL 为当前实现基线
- 若未来出现明显规模或协作需求，再单独评估

### 4.2 不引入任务队列作为当前主线

当前项目并不需要 `Celery + Redis` 这类重型异步基础设施作为核心前提。

原因：

- 主要运行场景是本地
- 当前工作流复杂度仍可由现有架构承载
- 引入额外服务会显著提高维护成本

## 5. 检索策略选型

### 5.1 核心判断

BM25 和向量检索不是简单的“粗排 + 精排”流水线关系，而是两类互补工具：

- BM25 适合精确命中
- 向量检索适合语义召回
- 混合检索适合平衡效果与成本

### 5.2 当前策略

当前系统保留三类检索路径：

- BM25
- Vector
- Hybrid

由 `QueryRouter` 做自动路由。

### 5.3 为什么这样设计

- 避免一切查询都走高成本语义路径
- 保留专有名词、代码符号、短查询的精确性
- 在语义需求场景下提供足够表达能力

### 5.4 当前不足

当前检索体系解决的是“找到相关内容”，还没有真正解决：

- 内容之间为什么相关
- 如何从 A 走到 B
- 如何返回证据链而不是单条命中

这也是下一阶段关系层要承接的问题。

## 6. MCP 技术选型判断

### 6.1 当前判断

MCP 已经不是“以后再说”的扩展能力，而是当前一等技术面。

采用 MCP 的原因：

- 可以让 AI Agent 直接调用知识库
- 可以把 PKV 从“被动资料库”推进为“可操作知识环境”
- 比单纯依赖 GUI 更符合项目的 AI-First 定位

### 6.2 当前能力边界

当前 MCP 已经支持：

- 搜索
- 详情读取
- 列表浏览
- 归档
- 基础关联推荐

但从技术选型视角看，下一阶段还缺：

- 面向关系层的查询接口
- 面向证据链的返回结构
- 面向多跳探索的 Tool 设计

---

## 7. GUI 技术选型判断

### 7.1 为什么保留 GUI

外部 GUI Wrapper 有现实价值：

- 浏览和检查更方便
- 归档状态和系统状态更可见
- 审核和调试体验更直观

### 7.2 为什么 GUI 不属于核心仓库主战场

因为 PKV 当前真正的差异化更接近：

- MCP 能力
- 知识关系层
- 多跳探索
- 证据聚合

所以 GUI 的技术选型不再进入核心依赖/封包闭包；它在独立仓库中作为稳定、可维护、足够好用的 Kernel Wrapper 演进。

### 7.3 当前结论

- 核心仓库不再保留 PySide6/qasync 或 `pkv-gui.exe`；`pkv-GUI` 独立管理其桌面技术栈
- 不围绕 GUI 扩张定义核心项目

## 8. 数据模型与关系层预留

### 8.1 当前事实

当前重点数据模型包括：

- 知识条目元数据
- Markdown 文件路径
- 检索索引信息
- 审核与历史相关数据

### 8.2 下一阶段预留

为关系层与高阶 MCP 预留的方向包括：

- 关系类型枚举
- 关系来源标记（显式 / 结构 / 语义 / 工作流）
- 路径解释所需字段
- 证据包返回结构

### 8.3 当前建议

在关系层未明确前，不建议直接引入重量级图数据库。

优先路径应是：

1. 先定义关系模型
2. 再评估基于现有 SQLite / 辅助索引是否足够
3. 只有在现有方案明显不足时，再考虑图数据库或外部关系引擎

---

## 9. 当前不推荐的技术扩张

当前不建议优先引入：

- PostgreSQL / pgvector 作为主线基础设施
- Celery + Redis 作为主线异步架构
- 图数据库作为默认依赖
- 为 GUI 强行引入更复杂前端栈

原因不是这些技术不好，而是它们会在当前阶段提高复杂度，却不一定提高核心价值。

---

## 10. 一句话总结

PKV 当前技术选型的本质，是用 **Markdown + SQLite + hnswlib + Workflow + MCP** 构建一个可长期维护、可被 AI 调用、并且能继续演化到关系推理层的本地知识底座。
