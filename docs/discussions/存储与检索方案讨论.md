## 背景与动机

在 [技术选型](./技术选型.md) 文档中，PKV 最初选定了 PostgreSQL + pgvector 作为辅助存储方案。在参考 [VCPToolBox](https://github.com/lioensky/VCPToolBox) 项目后（见 [Inspired By VCP](./Inspired%20By%20VCP.md)），提出了向 SQLite + 轻量向量索引转型的可能性。

本文档记录相关技术讨论过程、利弊分析和决策依据。

## 检索方案讨论

### 核心共识：BM25 和向量检索是两个维度

BM25（稀疏检索）和向量检索（稠密检索）**不是粗排→精排的流水线关系**，而是**两种不同维度的工具**：

| 维度 | BM25（关键词精确匹配） | 向量检索（语义理解） |
|------|----------------------|-------------------|
| 表示方式 | 词频统计（TF-IDF 变体） | Embedding 稠密向量 |
| 匹配方式 | 关键词精确匹配 | 语义相似度计算 |
| 擅长场景 | "找包含 useState 的笔记" | "React 状态管理相关" |
| 优势 | 快速、可解释、精确匹配强、零成本 | 语义理解、同义词处理 |
| 劣势 | 不理解语义 | 需要模型、计算开销大 |

### 接口设计原则：PKV 提供能力，AI 前端决策

PKV 的定位是**能力提供者**，不负责智能决策。具体调用策略由外部 AI 前端（Claude Code、Codex 等）自行决定。

```
调用方（决策层）                     PKV（能力层）
═══════════════                     ═══════════════
Claude Code / Codex / 内置AI        暴露原子检索接口
      │                                  │
      └── 根据用户意图自行选择 ──────→   ├── /search/bm25
          调用哪些接口、如何组合          ├── /search/vector
                                        ├── /search/chunk-vector
                                        ├── /search/structured
                                        └── /search/tags
```

### 归档时 vs 查询时的职责划分

| 阶段 | 决策内容 | 决策者 |
|------|---------|--------|
| **归档时** | 该内容**支持**哪些检索方式 | PKV 自身 |
| **查询时** | 本次查询**使用**哪种检索方式 | AI 前端 |

**归档时的索引策略**（非排他性）：
- 所有内容：建 BM25 全文索引（零成本）
- 所有内容：生成文档级 embedding（成本低）
- 长文本（>5000字）：额外做分块 embedding
- 视频内容：建时间轴结构化索引

### 标签系统：独立的第二检索维度

标签检索独立于文本检索，作为并行的检索维度：

```
维度1：文本检索
  ├── BM25（关键词精确匹配）
  ├── 向量（语义相似度）
  ├── 分块向量（长文本语义定位）
  └── 结构化（视频时间轴等）

维度2：标签检索
  ├── 核心标签匹配（AI 推荐 + AI 整理，强制召回）
  ├── 推断标签匹配（AI 自动生成，加权召回）
  └── 语义组展开（AI 动态学习，关联召回）
```

查询时两个维度可自由组合，例如：核心标签"分布式系统" + 语义搜索"一致性保证"。

### 可替换算法模块接口

VCP 的残差金字塔等高级 RAG 算法**保留但不实现**，预留可插拔接口，未来作为可替换算法模块接入。

## 存储方案讨论：SQLite vs PostgreSQL

### 前提：PKV 的存储架构

```
主存储：Markdown + YAML Front Matter（数据主权，不可动摇）
辅助存储：数据库（只负责索引加速和复杂查询）
                ↑
       辅助存储坏了可以从 Markdown 文件重建
```

因此讨论的焦点是：**作为辅助存储，应该选 PostgreSQL 还是 SQLite？**

---

### SQLite 方案

#### 优势

| 优势 | 说明 |
|------|------|
| **零配置部署** | 无需安装和维护独立数据库服务 |
| **单文件存储** | 复制文件即完成备份/迁移 |
| **依赖最小化** | Python 标准库内置 sqlite3 |
| **匹配"辅助存储"定位** | 数据库只是缓存索引，轻量方案更合理 |
| **重建成本低** | 损坏后删掉重建即可（主数据在 Markdown） |
| **10年可维护性** | SQLite 是世界上部署最广的数据库，格式极度稳定 |
| **符合 PKV 核心原则** | 本地优先、简洁优先、依赖最小化 |

#### 困难点与风险（原始评估）

> ⚠️ 以下为最初评估。经过深入调研后，多数困难点已找到解决路径，详见下方"方案3"。

| 困难点 | 详情 | 原始评估 | 当前状态 |
|--------|------|---------|---------|
| **向量检索：sqlite-vec 只有暴力搜索** | 当前 v0.1.0 没有 ANN 索引（HNSW/IVF），25万条记录已出现性能问题 | 🔴 高 | ✅ 已解决：使用独立 hnswlib 替代 |
| **向量检索：sqlite-vec 功能缺失** | 不支持 UPSERT，LEFT JOIN 与 MATCH 配合有问题 | 🟡 中 | ✅ 已解决：不使用 sqlite-vec |
| **向量检索：平台兼容性** | sqlite-vec 在 Windows/ARM 安装有报告困难 | 🟡 中 | ✅ 已解决：hnswlib 有成熟 pip wheel |
| **中文 BM25：FTS5 不支持 CJK** | 默认 unicode61 tokenizer 无法处理中文分词 | 🔴 高 | ✅ 已解决：jieba Python 层预分词后写入 FTS5 |
| **中文 BM25：需要 C 扩展** | [wangfenjin/simple](https://github.com/wangfenjin/simple) 需要编译 C 扩展 | 🟡 中 | ✅ 已绕过：jieba 是纯 Python，无需 C 扩展 |
| **混合检索融合** | 无现成框架，需要自己编写融合逻辑 | 🟡 中 | 🟡 仍需自行编写，但有参考实现 |

#### 向量检索替代方案对比

| 方案 | 特点 | 成熟度 | 风险 | 推荐度 |
|------|------|--------|------|--------|
| **sqlite-vec** | 纯 C、零依赖、6.7k star，但只有暴力搜索 | ⭐⭐⭐ | ANN 未实现，25万条变慢 | 🟡 观望 |
| **vectorlite** | 使用 hnswlib，比 sqlite-vss 快 10-40x | ⭐⭐⭐ | 社区较小（~340 star） | 🟡 可选 |
| **独立 hnswlib** | 成熟的 HNSW 实现，5.1k star，`pip install hnswlib` | ⭐⭐⭐⭐ | 需自行管理索引文件 | ✅ **推荐** |
| **独立 Faiss** | Meta 出品，GPU 支持，批量操作强 | ⭐⭐⭐⭐ | 较重，单次查询不算快 | 🟡 偏重 |

#### 重要澄清：hnswlib 不存在"中文支持"问题

hnswlib 是纯粹的**数值向量索引库**，只接收 `float32` 数组，不接触文本内容，对语言完全无感知：

```
中文文本 → Embedding 模型（如 bge-zh / m3e-base） → 数值向量 → hnswlib
                ↑                                              ↑
          中文支持在这里决定                              只看到数字，不关心语言
```

因此"中文问题"只存在于两个地方：
1. **BM25 全文检索**：需要中文分词 → 用 jieba 在 Python 层解决
2. **Embedding 模型选择**：需要选支持中文的模型 → 与 hnswlib 无关

### PostgreSQL 方案

#### 优势

| 优势 | 说明 |
|------|------|
| **pgvector 成熟** | 原生支持 HNSW 索引，向量检索性能有保障 |
| **SQL 能力强** | 复杂过滤查询（如"最近一周的微信文章"）非常方便 |
| **中文全文搜索** | pg_jieba / zhparser 扩展成熟（但也需要额外安装） |
| **事务保证** | 完整 ACID 特性 |
| **统一存储** | 元数据 + 向量 + 全文索引一体化，无需管理多个索引文件 |
| **扩展路径清晰** | 数据量增长后可接入 Qdrant 等专业向量库 |

#### 缺点

| 缺点 | 说明 |
|------|------|
| **部署成本高** | 需要安装和维护 PostgreSQL 服务进程 |
| **与"辅助存储"定位不匹配** | 为独立主存储设计，对于只做索引缓存来说偏重 |
| **备份/迁移复杂** | 需要 pg_dump/pg_restore，不如复制文件直观 |
| **依赖较重** | psycopg2 + PostgreSQL 服务 + pgvector 扩展 |
| **本地优先体验差** | 启动项目前需要确保 PG 服务正在运行 |
| **中文扩展也需额外安装** | pg_jieba / zhparser 同样不是开箱即用 |

---

### 推荐方案：方案3（SQLite + 独立 hnswlib + jieba Python 层分词）

经过多轮讨论和调研，确定了一个兼顾轻量性和功能完整性的组合方案：

```
┌──────────────────────────────────────────────────────┐
│                  Python 应用层                         │
├──────────────────────────────────────────────────────┤
│                                                      │
│  jieba 分词（纯 Python，pip install jieba）            │
│  ├── 中文文本 → 分词 → 空格连接的关键词                │
│  └── 写入 FTS5 全文索引                               │
│                                                      │
│  Embedding 模型（如 bge-zh / m3e-base）               │
│  ├── 文本 → 稠密向量                                  │
│  └── 写入 hnswlib 索引                                │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│  SQLite（元数据 + FTS5）       hnswlib（向量 ANN）     │
│  ┌─────────────────────┐     ┌────────────────────┐  │
│  │ knowledge_items     │     │ doc_vectors.idx    │  │
│  │ content_chunks      │     │ chunk_vectors.idx  │  │
│  │ tags / tag_groups   │     │ (独立索引文件)      │  │
│  │ FTS5 全文索引        │     │ HNSW 算法          │  │
│  └─────────────────────┘     └────────────────────┘  │
│        pkv.db                    pkv_vectors/         │
│                                                      │
└──────────────────────────────────────────────────────┘
```

#### 方案3 如何解决各项问题

| 问题 | 解决方式 |
|------|---------|
| ANN 向量检索 | hnswlib 提供成熟的 HNSW 算法，百万级数据无压力 |
| 中文全文搜索 | jieba 在 Python 层分词后写入 FTS5，无需 C 扩展 |
| 元数据 + SQL 查询 | SQLite 原生能力，完全满足 |
| 标签检索 | SQLite 普通表 + SQL 查询 |
| 部署复杂度 | `pip install hnswlib jieba` 即可，零配置 |
| 文件管理 | 两个位置：`pkv.db`（SQLite）+ `pkv_vectors/`（hnswlib 索引） |

#### 方案3 的代价

| 代价 | 说明 | 是否可接受 |
|------|------|-----------|
| 管理两类文件 | SQLite 文件 + hnswlib 索引文件 | ✅ 可接受，都是本地文件 |
| 跨组件一致性 | SQLite 和 hnswlib 的数据需要自行保持同步 | ✅ 可接受，归档时统一写入 |
| 混合检索融合 | 需要自行编写 BM25 + 向量结果的融合逻辑 | ✅ 可接受，有参考实现 |

### 方案对比总览

| 维度 | 方案3：SQLite + hnswlib | PostgreSQL + pgvector |
|------|------------------------|----------------------|
| 部署复杂度 | ✅ `pip install` 即可 | ❌ 需安装+运行 PG 服务 |
| 依赖量 | ✅ 纯 Python + pip 包 | ❌ PG服务 + psycopg2 + pgvector |
| 备份/迁移 | ✅ 复制文件夹 | ❌ pg_dump / pg_restore |
| 向量 ANN 检索 | ✅ hnswlib HNSW（成熟） | ✅ pgvector HNSW（成熟） |
| 中文 BM25 | ✅ jieba + FTS5（纯 Python） | ⚠️ pg_jieba（需编译安装） |
| SQL 复杂查询 | ✅ SQLite SQL | ✅ PostgreSQL SQL（更强） |
| 并发性能 | ⚠️ WAL 模式够用（个人工具） | ✅ 强 |
| 统一存储 | ⚠️ 两类文件需同步 | ✅ 一体化 |
| 与 PKV 理念契合度 | ✅ 本地优先、依赖最小 | ⚠️ 偏重 |
| 数据库损坏恢复 | ✅ 删掉重建（主数据在 Markdown） | ⚠️ 需要备份恢复流程 |
| 10年维护性 | ✅ SQLite 格式极稳定 + hnswlib 算法成熟 | ⚠️ 需持续维护 PG 服务 |
| 扩展性 | ⚠️ 百万级以上需考虑 | ✅ 可接入专业向量库 |

## 已达成的共识

### 检索方案

- [x] BM25 和向量检索是两种不同维度的工具，不是粗排→精排关系
- [x] PKV 暴露原子检索接口，调用策略由 AI 前端决定
- [x] 归档时决定"支持哪些检索方式"，查询时决定"使用哪种方式"
- [x] 归档时所有内容都建 BM25 + 文档级向量索引，长文本额外分块
- [x] 标签系统作为独立的第二检索维度
- [x] 核心标签由 AI 辅助推荐 + AI 整理
- [x] 语义组由 AI 动态学习
- [x] 残差金字塔保留不实现，预留可插拔接口

### 存储方案

- [x] 主存储不变：Markdown + YAML Front Matter
- [x] 辅助数据库的定位：索引缓存，可从文件重建
- [x] 辅助存储倾向采用方案3：SQLite + 独立 hnswlib + jieba Python 层分词
- [x] hnswlib 不存在"中文支持"问题（它只处理数值向量，对语言无感知）
- [x] 中文 BM25 通过 jieba 在 Python 层预分词后写入 FTS5 解决，无需 C 扩展
- [x] **LanceDB 调研结论**：因中文全文搜索不支持，暂不采用，列入观察名单（详见 [LanceDB vs SQLite 调研](./存储与检索方案讨论2-LanceDB-vs-SQLite.md)）

### 2. Embedding 模型选型

需要选择支持中文的 Embedding 模型：

| 模型 | 特点 | 维度 |
|------|------|------|
| **bge-zh** (BAAI) | 中文优化，MTEB 榜单表现优秀 | 768 |
| **m3e-base** | 中文社区流行，轻量 | 768 |
| **text-embedding-3-small** (OpenAI) | 多语言，需要 API 调用 | 1536 |
