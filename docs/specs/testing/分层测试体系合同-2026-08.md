# 分层测试体系合同

**状态：内部测试架构目标；不是发布计划。** 机器可检查投影是
[`tests/contracts/test_topology.v1.yaml`](../../../tests/contracts/test_topology.v1.yaml)。

## 目的与边界

本合同把 Python 项目的“编译前/后”明确为**构建产物前**与**安装或解包产物后**：源码
白盒测试可以导入实现；产物黑盒测试只能使用已安装或已解包的公开接口。它补充、但不
修改历史 [`m13_test_lanes.v1.yaml`](../../../tests/contracts/m13_test_lanes.v1.yaml)。后者仍是
held M13 candidate 的历史治理合同，不能被本文件升级为 release 证据。

本合同只覆盖 Windows 上的内部、离线、合成数据验证。它不授权 PyPI、公开发布、安装器
资格、升级或回滚承诺、真实迁移、真实 Provider、真实 Vault、GUI 或 GUI 封包。其他操作
系统的实验不属于主线质量或产品平台证据。

```text
L0 隔离启动器
        │
        └─ L1 Windows 源码白盒
                 │
                 └─ L2 本地构建合同
                        │
                        ├─ L3 本地 wheel clean-install 黑盒
                        └─ L4 Windows INTERNAL TEST ONLY 包黑盒
```

源码层通过不代表产物层；任何产物通过也不代表 release。

## 证据分类

每一份测试报告都必须同时标注对象、revision/provenance、证据等级和决策，至少归入下列
一种类别，避免把不同时间线的“artifact”混为同一结论：

| 类别 | 对象 | 可证明的范围 |
| --- | --- | --- |
| `CURRENT_ARCHITECTURE` | 当前 headless Core 与 `pkv_kernel` 公共接口 | 架构和接口边界，不是封包或发布证明 |
| `CURRENT_RELEASE_DECISION` | 当前 held 决策 | 不发布的状态，不能从任何测试 green 推导为 release eligible |
| `HISTORICAL_PRE_SPLIT_W4_EVIDENCE` | GUI 拆分前的 held candidate | 历史对象当时的功能记录，不能证明当前 headless revision |
| `INTERNAL_SELF_TEST_ONLY` | 当前内部 onedir/ZIP smoke | 当前 CLI/MCP 的本地合成自测，不能替代 W4 或安装交付验证 |
| `INTERNAL_COMPATIBILITY_PROOF` | 本地 `pkv_kernel` clean-install wheel | Kernel 包的 source-free 使用边界，不能证明 EXE、CLI/MCP 或发布包 |
| `PLANNED_GATED` | 尚未取得完整证据的新 lane | 只表示计划，不能被描述为已通过 |

历史 held candidate、其 fixture、handoff 和 release contract 是冻结的历史材料；主线不得为了
让当前测试“变绿”而改写其 GUI、blocker 或 provenance。当前 headless artifact 若要形成新的
正式候选，必须另建身份、场景合同和 evidence registry。

## 共同隔离模型

每次自动化运行必须有独立运行根。`test-conda.ps1` 的标准布局为：

```text
<checkout>/.data-test/conda-<run-id>/<lane>/
  db/ vault/ vectors/ logs/ tmp/
```

其他受支持 launcher 也必须将每一项运行时路径置于同一 `.data-test` 运行根，且 lane 之间
不得共享可写数据。`scripts/run-test.ps1` 是 Windows 源码及受支持测试子进程的唯一默认
启动器。它在 Python、pytest 和产品导入前建立 base-only、离线环境；`DATA_DIR`、`DB_PATH`、
`VAULT_DIR`、`VECTOR_DIR`、`LOG_DIR` 与 `TMP_DIR` 必须全部落在同一测试根。报告只能写入
该根或显式受控的报告根。

以下对象属于用户区，自动化不得读取、比较或写入：

- `%USERPROFILE%\\.pkv\\config.yaml`；
- `%USERPROFILE%\\.pkv\\data` 及继承而来的有效 `PKV_DATA_ROOT`；
- `<effective-data-root>\\config\\local.yaml`；
- Provider key、代理凭据、真实 Vault、真实 URL 和真实迁移目标。

测试启动时应清理 Provider、proxy、`PYTHONPATH`/startup 与用户 pytest plugin 注入，并创建
合成 HOME、USERPROFILE、APPDATA、LOCALAPPDATA、TEMP。`PKV_DATA_ROOT` 与
`PKV_LOG_LEVEL` 仍是仅有的正式产品环境覆盖；测试的六个运行时路径变量仅用于
`PKV_TEST_OFFLINE=1` 的隔离注入，绝不是第二套用户配置。

这是一层 Python 进程和路径隔离，不是 OS sandbox；受信本地工具链、同权限测试代码、已安装
plugin 与非 Python Direct 命令仍须单独审查。

## 分层与执行责任

| 层 | 运行位置 | 可导入源码 | 核心证明 | 不能证明 |
| --- | --- | --- | --- | --- |
| L0 | Windows test launcher | 可 | 路径、profile、凭据、网络隔离 | 业务功能 |
| L1 | Windows 源码 | 可 | 单元、集成、故障注入、边界条件 | 已安装产物 |
| L2 | 本地构建 | 仅 builder | wheel/package payload、元数据、禁止 payload | clean-install 行为 |
| L3 | checkout 外 clean venv | 不可 | 本地 wheel 的 `pkv_kernel` 公开 API/能力握手 | CLI/MCP 封包或 release |
| L4 | checkout 外解包 Windows 子进程 | 不可 | INTERNAL TEST ONLY 的 CLI、BM25、MCP stdio smoke | 安装器、升级、release |

### L0 与 L1：隔离启动器和源码白盒

`scripts/test-conda.ps1 -Suite P0` 先验证默认收集合同，再运行完整离线源码套件；它是 Windows
源码兼容性预检，不包含封包构建，也不包含 MCP 覆盖率结论。`scripts/run-test.ps1` 的负向测试
必须持续证明：外部数据根、真实 profile、Provider 凭据和网络 canary 被 fail-closed。

`scripts/test-conda.ps1 -Suite MCP` 是独立的 L1 专项门禁。它通过同一启动器在新的
`.data-test/conda-<run-id>/mcp-coverage` 根运行 unit、integration、blackbox 与 E2E 的离线
MCP 用例，并以 `--cov=src.mcp --cov-fail-under=95` 收口。P0 green 不得被描述为 MCP coverage
green，反之亦然。

### L2：本地构建合同

`scripts/build-internal-package.ps1` 使用 `scripts/run-windows.ps1` 执行 builder，验证内部
onedir/ZIP payload、元数据和禁止内容。builder 是受信本地工具链阶段，不声称具备 L0 默认
离线启动器的完整环境清理保证；其后的合成 fixture 与外置产物 smoke 必须重新进入
`scripts/run-test.ps1` 隔离边界。

### L3：本地 wheel clean-install 黑盒

L3 从本地构建的 wheel 安装到 checkout 外的 clean venv，以隔离子进程调用 `pkv_kernel` 公共
接口和版本/能力握手；禁止 editable install、源码目录 cwd、`src.*` 导入、PyPI 下载。它只说明
本地 wheel 可被 clean-install 使用，不能证明 CLI、MCP 封包、安装器或 release。

### L4：Windows INTERNAL TEST ONLY 包黑盒

L4 从内部 ZIP 解包到 checkout 外工作目录，保留唯一 `.data-test/<run-id>/...` runtime 根，至少
验证 `pkv --help`、合成数据 BM25 搜索与 MCP stdio initialize。它只验证内部包的可运行性；不
验证用户安装、数据接管、迁移、升级、卸载或 GUI。

历史 held Artifact candidate 与当前 headless INTERNAL TEST ONLY lane 是两类独立证据。前者
必须保持 hold 和历史身份；不得把其旧场景、旧 payload 或旧结果回退为当前产物的替代证明。

## 执行与证据规则

每次新增或修改 lane 必须同时更新机器合同、对应 launcher、负向隔离回归与本规范；否则只能
标为规划，不能成为质量门禁。默认执行顺序是：L0/L1 P0、需要时独立 MCP coverage、L2 构建、
L3 wheel、L4 internal smoke；每个结果只对本层生效。

- 源码结果不能证明 installed wheel、internal artifact 或 release。
- 本地 wheel 结果不能证明 installer、release 或 PyPI publication。
- internal artifact 结果不能证明 release、installer qualification 或 upgrade compatibility。
- 历史 held candidate 不能证明当前 headless revision。

默认自动化始终使用 `.data-test`、合成 fixture、fake Provider 与离线 guard。真实数据或 live
流程只能走用户明确授权的独立流程，且不属于本合同的完成条件。
