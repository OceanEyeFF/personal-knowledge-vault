Embedding v2、ledger 3、grant 2 与 publish-ready proof 均属 W4，尚未实现。
W3 的组件证据与最终验收状态以

## 1. 范围与冻结原则

- 外部代码仍只导入 `pkv_kernel`；不增加公开 Store、Provider、lease、stage path 或配置注入。
- 新 v2 入口使用显式 `_v2` 名称和独立 DTO，允许在兼容 SDK 中增加，不能改变旧函数必填参数。
- v2 DTO 的新增字段不能通过将 v1 DTO 无条件扩充来假称兼容；新客户端须握手并调用 v2 名称。
- Outcome 操作仍为零 Provider；手动 rebuild 只允许新网络重建或原操作的本地发布/完成对齐。
- 所有 inspect/get/plan 是零写、零 lease、零网络。确认句柄只保留用户选择，只有 execute 才写。
- 以下代码块是冻结类型签名；Outcome 已在 W3 实现，manual rebuild v2 仍为 W4 目标。
  新增 DTO/函数在所属子模块 `__all__` 中逐项冻结；
  不新增第五个公开子模块。

公共标量约束：`Sha256` 为 64 位小写十六进制；正整数不接受 bool；bool 不接受字符串/整数。
Outcome 标识继续使用 `[a-z][a-z0-9_-]{0,95}`；manual operation/generation 标识沿用现有
产品生成格式，调用方只能原样传回，不自行生成或当作路径。日期为 `YYYY-MM-DD`，月为
`YYYY-MM`，timezone 为已验证 policy 的 IANA 名称。对象请求禁止额外字段；输出字段按本文
枚举，不传递内部异常、未知字段或任意 metadata。

## 2. Outcome v2

### 2.1 SDK 签名与公开类型

目标导入位置：`pkv_kernel.outcomes`。以下符号为兼容期新增，major 2 保持相同名称：

```python
@dataclass(frozen=True)
class ResearchBriefReviewConfirmation:
    outcome_id: str
    expected_revision: int
    content_sha256: str
    expected_input_revision: int

class ResearchBriefReturnReason(str, Enum):
    NEEDS_REVISION = "needs_revision"
    INSUFFICIENT_EVIDENCE = "insufficient_evidence"
    OTHER = "other"

def get_outcome_v2(
    topic_id: str, *, kernel: KnowledgeKernel | None = None,
) -> OutcomeBundleV2: ...

def get_research_brief_v2(
    *, topic_id: str | None = None, outcome_id: str | None = None,
    kernel: KnowledgeKernel | None = None,
) -> ResearchBriefRecordV2 | None: ...

def render_research_brief_v2(
    *, topic_id: str, kernel: KnowledgeKernel | None = None,
) -> ResearchBriefRecordV2: ...

def approve_research_brief_v2(
    *, confirmation: ResearchBriefReviewConfirmation,
    kernel: KnowledgeKernel | None = None,
) -> ResearchBriefReviewResultV2: ...

def return_research_brief_v2(
    *, confirmation: ResearchBriefReviewConfirmation,
    reason_code: ResearchBriefReturnReason | str,
    kernel: KnowledgeKernel | None = None,
) -> ResearchBriefReviewResultV2: ...
```

`get_research_brief_v2` 必须且只能提供一个 selector。不存在的合法 selector 返回 `None`；
`get_outcome_v2` 的 Topic 不存在返回 `outcome_not_found`。review 通过 outcome_id 定位，
不再接收 topic_id，也不由服务端补齐确认字段。确认 DTO 可由客户端从已展示的结果构造，
不是可绕过校验的授权凭据；构造/解析阶段只校验形状，提交阶段仍复核持久事实。

`ResearchBriefRecordV2` 是不可变值对象，`to_dict()` 字段冻结如下：

| 字段 | 类型/语义 |
| --- | --- |
| `schema` | 固定 `pkv.outcome.brief.v2` |
| `outcome_id, topic_id` | opaque 标识 |
| `outcome_type` | 固定 `research_brief` |
| `revision, content_sha256` | 当前已提交 pointer 的正整数版本与字节摘要 |
| `state, effective_state` | 既有 OutcomeState；前者持久值，后者复核后的可见值 |
| `markdown_relative_path` | 既有安全相对投影引用，不是任意文件读权限 |
| `projection_state` | `current / stale / unavailable` |
| `publication_id` | Sha256 或 null；历史未绑定行允许 null |
| `rendered_input_revision, rendered_input_digest` | 正整数/Sha256 或 null；必须同时有值或同时 null |
| `current_input_revision, current_input_digest` | 本次一致读取的 Topic 输入绑定 |
| `render_contract_version` | 该 pointer 的持久 renderer 合同版本；legacy_unverified 为 null |
| `current_render_contract_version` | 本次一致读取的 Topic renderer 合同版本 |
| `binding_state` | `verified / legacy_unverified` |
| `review_confirmation` | 上述四元组或 null；仅 binding、input、projection 可验证且状态允许 review 时提供 |
| `created_at, updated_at` | 既有持久时间；不进入 input digest |

`review_confirmation.expected_input_revision` 必须等于 rendered 与 current input revision；
绝不能将当前 input 代填到未验证的历史 brief。外部 source 漂移使 effective state 降级并使
review_confirmation 为 null。已批准但仍完整匹配的版本可提供确认以便精确重放或退回；
returned 可提供同版本确认供相同退回动作幂等查询，不能据此再批准。

`OutcomeBundleV2` 包含 `schema="pkv.outcome.bundle.v2"`、`topic`、`evidence`、`claims`、
`brief`。evidence/claims 沿用 v1 body-free 字段；topic 保留 v1 字段并增加稳定 outcome_id、
input_revision、input_digest、render_contract_version；brief 是上述 v2 DTO 或 null。
`ResearchBriefReviewResultV2` 仅包含 `schema="pkv.outcome.review-result.v2"`、`brief`、
`review_receipt_id`（opaque）、`idempotent`（bool）。所有值对象均提供 `to_dict()`。

### 2.2 review 事务、退回原因与重放

顺序固定为：解析校验 → root writer lease → source/projection 复核 → 同一 SQLite 事务内
复核 pointer、四元组、Topic/brief 输入绑定及状态 → 写 review state 与 receipt → commit。
pointer/input/state 校验与 receipt 不得分为两个 commit。Provider、render、输入修改均不属于 review。

| 当前 effective state | approve | return |
| --- | --- | --- |
| `awaiting_review` | 校验完整后提交 approved | 校验完整后提交 returned |
| `approved` | 同元组、同 approve receipt 幂等返回 | 提交 returned，记录 reason_code |
| `returned` | `outcome_state_conflict`；须显式 render 新 revision | 同元组、同 reason_code、同 return receipt 幂等返回 |
| `draft / needs_review` | `outcome_approval_blocked` | `outcome_approval_blocked` |

reason_code 为上述三值之一且必填；不接收自由文本 reason，不保存正文、路径或 URL。
approve receipt 的 reason_code 为 null。不同 reason 的重复 return 为 state conflict，不修改旧 receipt。
精确重放仅在当前仍是该元组与目标状态时成功；旧 approve 不能撤销后来的 return，新输入/新版本
不能沿用旧 receipt。审计可延迟完成，但成功 receipt/状态不得因此被回滚或要求重新批准。

普通 render 使用持久 render_contract_version，不能因软件升级静默更换 renderer；无法支持时
返回 `outcome_render_contract_unsupported`，进入独立受控迁移/重新生成流程。
字节只由已持久化的规范输入生成；外部 source/effective 状态只作为发布和 review 的复核门禁，
不得注入同一 input digest 的渲染字节。需要反映外部变化时，先经显式输入 mutation 推进 binding。

## 3. Manual rebuild v2

本节为 W4 冻结目标，当前 SDK 不提供这些 v2 入口或 `kernel.embedding-rebuild.v2` 能力；
不得从 W3 的 Outcome v2 实现推断本节已可用。

### 3.1 SDK 签名与 opaque handles

目标导入位置：`pkv_kernel.embedding`。已有 v1 名称保留；新增完整 v2 链如下：

```python
def inspect_embedding_rebuild_v2(
    config: Config | None = None,
) -> EmbeddingRebuildInspectionV2: ...
def plan_embedding_rebuild_v2(
    inspection: EmbeddingRebuildInspectionV2, *, force: bool = False,
) -> EmbeddingRebuildPlanV2: ...
def confirm_embedding_rebuild_v2(
    plan: EmbeddingRebuildPlanV2, *, approved: bool = True,
    allow_network: bool = False,
) -> EmbeddingRebuildConfirmationV2: ...
def execute_embedding_rebuild_v2(
    plan: EmbeddingRebuildPlanV2,
    confirmation: EmbeddingRebuildConfirmationV2 | None = None,
) -> EmbeddingRebuildExecutionV2: ...

def inspect_embedding_operation_v2(
    operation_id: str, *, config: Config | None = None,
) -> EmbeddingOperationInspectionV2: ...
def plan_embedding_publication_v2(
    inspection: EmbeddingOperationInspectionV2,
) -> EmbeddingPublicationPlanV2: ...
def confirm_embedding_publication_v2(
    plan: EmbeddingPublicationPlanV2, *, approved: bool = True,
) -> EmbeddingPublicationConfirmationV2: ...
def execute_embedding_publication_v2(
    plan: EmbeddingPublicationPlanV2,
    confirmation: EmbeddingPublicationConfirmationV2 | None = None,
) -> EmbeddingRebuildExecutionV2: ...
```

上述八个函数返回的七个类型均为 façade-only、process-local opaque handles；禁止直接构造或由 JSON
反序列化为执行能力。公开属性为各 DTO 中的安全字段，`to_dict()` 返回独立展示副本。
CLI/MCP 跨进程提交 plan_id 时在当前 Config 重新 inspect/plan，精确比对后才创建确认句柄；
不依赖服务端缓存。缺确认、不同 plan 的确认或将 rebuild/publication 句柄混用均拒绝。

### 3.2 展示字段与 identity

所有 DTO 均有 schema；依次为 `pkv.embedding.inspection.v2`、`pkv.embedding.plan.v2`、
`pkv.embedding.confirmation.v2`、`pkv.embedding.execution.v2`、
`pkv.embedding.operation.v2`、`pkv.embedding.publication-plan.v2`、
`pkv.embedding.publication-confirmation.v2`。下列字段为封闭形状：

| DTO | 字段（除 schema） |
| --- | --- |
| rebuild inspection | `index`（state/source_digest/source_count/chunk_count/active_generation_id/previous_generation_id/active_manifest_sha256/contract/issues）、`data_root_identity_sha256`、`runtime_snapshot_sha256`、`policy`、`budget_check_period`、`ledger_schema_version`、`ledger_upgrade` |
| rebuild plan | `plan_id`、`action="rebuild"`、`force`、`inspection`、`estimated_embedding_tokens`、`requires_confirmation=true`、`requires_network=true` |
| rebuild confirmation | `plan_id`、`approved`、`allow_network` |
| operation inspection | `operation_id`、`effective_state`、`provider_effect`、`generation_id`、`original_plan_id`、`data_root_identity_sha256`、`runtime_snapshot_sha256`、`proof_valid`、`proof_sha256`、`reservation`、`local_estimate`、`provider_usage`、`publication_committed`、`ledger_completion_pending`、`audit_completion_pending`、`ledger_schema_version`、`ledger_upgrade`、`issues` |
| publication plan | `plan_id`、`action`（`publish_only / reconcile_completion`）、`operation_id`、`generation_id`、`operation_inspection`、`ledger_upgrade`、`requires_confirmation=true`、`requires_network=false`、`creates_reservation=false` |
| publication confirmation | `plan_id`、`operation_id`、`approved` |
| execution | `operation_id`、`generation_id`、`previous_generation_id`、`status="ready"`、`provider_called`、`publication_committed=true`、`ledger_completion_pending`、`audit_completion_pending`、`issues` |

index.contract 包含 provider/model/dimension/endpoint_fingerprint，不包含 endpoint 原文。
policy 包含 enabled/authorization_mode/timezone/daily_embedding_token_limit/monthly_embedding_token_limit/
fingerprint；均为已经验证的独立 manual policy。budget_check_period 包含 timezone/local_day/local_month。
reservation 为 null 或 {state,timezone,local_day,local_month,reserved_tokens,settled_tokens}；
usage 为 null 或既有 TokenUsage 的 body-free 数值/source 字段，未知值保持 null，不补零。
issues 为本合同第 4 节的稳定 issue 数组；generation/manifest/proof/previous 字段不存在时为 null。
ledger_schema_version 为 1/2/3，文件尚不存在时为 null。ledger_upgrade 为 null 或精确对象
`{from_schema:1|2,to_schema:3,source_sha256,operation_count,blocking_operation_count}`；两项计数
为非负整数，source_sha256 是已严格验证的旧 ledger 原始字节摘要。inspection 只读分类并展示
此影响，不写升级文件。未知版本、坏记录不能伪装为 null/空账本。

effective_state 枚举：`processing / awaiting_publish / activation_intent / completed / failed /
budget_paused / repair_required`。provider_effect 枚举：`not_started / completed / unknown`；
它表示调用进展，不表示 Provider 报告了准确用量。valid proof 才能从未完成记录推导
provider_effect=completed 和 effective_state=awaiting_publish；pointer 提交事实与验证通过的
已完成账本可证明 effective_state=completed。legacy completed 没有 proof 时允许保留
completed 终态和费用事实，但 provider_effect=unknown、proof_valid=false，不能据此重新发布。
开始调用但尚未完整封存时对外保持 unknown；不凭存活 PID、过期时间或一条 processing 行猜测。
proof_valid=false 时 proof_sha256=null，
不暴露未经验证摘要、私有 seal、grant/fence、stage 路径或 artifact 文件列表。

新网络 plan identity 的 canonical 材料固定为 W0 的 root/snapshot、source/count、pointer/
manifest、Embedding contract、policy fingerprint、force、action/schema 和 budget_check_period；
material replay key 排除 force 与 budget_check_period。snapshot 摘要只来自经过无密钥验证的
runtime snapshot，绝不散列秘密用户配置供公开验证。root 身份算法沿用 Runtime canonical identity。
publication plan 另绑定原 operation/public plan、完整 proof 摘要、当前 root/snapshot/source/
contract/policy/pointer 与 action；不加入新预算期间，不产生第二次网络 reservation。
operation DTO 的 original_plan_id 始终是原 `public_plan_id`，绝不是带进程私有 HMAC 的 Core plan_id。

hash 编码采用[迁移合同第 2 节](../database/生命周期一致性迁移冻结方案-2026-10.md)的
`SHA256(UTF8(domain) || 0x00 || canonical_json(payload))`，不复用 v1 未分域算法。
以下映射中的键为精确拼写，省略值以 null 表示，不省略键；计数为非负整数：

```text
contract_sha256:
  domain = pkv.embedding.contract.v2
  payload = {provider, model, dimension, endpoint_fingerprint}

material:
  {identity_schema:"pkv.embedding.transition.v2",
   data_root_identity_sha256, runtime_snapshot_sha256,
   index_state,
   source:{digest, document_count, chunk_count},
   pointer:{active_generation_id, previous_generation_id, active_manifest_sha256},
   contract_sha256, policy_fingerprint}

material replay key:
  domain = pkv.embedding.transition.v2
  payload = material

new network plan_id:
  domain = pkv.embedding.rebuild-plan.v2
  payload = {action:"rebuild", material, force, ledger_upgrade,
             budget_check_period:{timezone,local_day,local_month}}

publication plan_id:
  domain = pkv.embedding.publication-plan.v2
  payload = {action, operation_id, original_public_plan_id, ledger_upgrade,
             proof_sha256, generation_id, material,
             publication_committed, ledger_completion_pending, audit_completion_pending}
```

contract 的四个值来自同一 validated Embedding contract；endpoint_fingerprint 沿用该合同的
无凭据 endpoint 摘要，不重新散列 credential。material.source.digest 为捕获 source 摘要，
其余来源计数与 inspection 对齐；policy_fingerprint 为独立 manual policy 的既有稳定指纹。
material 中不含估算/用量、当前时间、issues、私有 Config HMAC、stage path 或 owner fence。
publication material 是本次只读复核的当前材料；原 operation 绑定仍须单独验证，当前计划
不能替旧 stage 消除 source/contract/root 漂移。reconcile_completion 允许 proof_sha256=null
但必须有可验证的已提交 pointer/完成事实；这不授权以缺 proof 的 stage 再次发布。

### 3.3 旧账本的显式升级

v2 inspect 支持严格只读解析 legacy ledger 1/2，按持久合同分类；目标 mutation 使用 ledger 3。
ledger_upgrade 摘要进入新网络或 publication plan 的确认 identity，不进入 material replay key。
legacy 未终结操作或未结算的未知外部影响仍阻断新网络计划并显示 repair_required，不能通过
先升级改名绕过。已完整结算的 legacy completed/failed 不因 provider_effect=unknown 单独
形成整根围栏；它们保留历史事实，新工作仍须独立明确确认。
可执行计划必须完整展示升级影响，确认后在 A 的 root lease 内重新验证 source_sha256 和所有
记录，原子升级后才预留新预算或继续发布。升级本身不调用 Provider，不改变原费用或 pointer；
后续预算拒绝仍可保留已明确授权的升级事实。只读调用和 confirm 不执行升级。

升级后的 SDK 中，v1 rebuild façade 面对空账本可在已确认执行时创建 ledger 3，面对已是 v3 的
账本使用共同 Core；因此 v1 的 D pending 规则可达。面对 legacy 1/2，旧 v1 mutation 返回
`embedding_ledger_upgrade_required`，不能在旧计划未展示升级影响时自动迁移，须改用 v2
计划/确认。旧二进制不认识 ledger 3 时继续按未来 schema 拒绝，不把 schema 3 改写回 2。

### 3.4 A/D 争锁与继续发布

A 争锁返回 `write_busy`，零 operation/reservation/Provider/stage；不能返回可重入 operation_id。
C 在窄 stage grant 内合法封存完整 proof 后，D 争锁返回下列明确 pending 错误：

```json
{
  "code": "embedding_publication_pending",
  "stage": "embedding_publication",
  "recoverable": true,
  "details": {
    "operation_id": "<opaque>",
    "effective_state": "awaiting_publish",
    "provider_effect": "completed",
    "publish_only_required": true
  }
}
```

该错误终止本次请求，但不声称 operation 终态或 READY。SDK 抛 `PKVRuntimeError`；CLI/MCP
保留以上安全 details。D 无 lease 时仅凭 proof 投影状态，不写 ledger/snapshot/audit。
publish-only execute 再争锁时返回同一 pending 错误；在初始 network A 发生的普通争锁仍为 write_busy。
此项 A/D 错误分类修正由共同 Core 实施，既有 `execute_embedding_rebuild` 及其 v1 adapter
也须透传 pending code/details：函数签名、异常基类及成功语义不变，仅补齐已经发生的费用/
待发布事实。v1 不因此获得 lookup/publish 入口；继续发布须协商 v2。R-02 红测试可继续调用
既有入口验证该修正，不能仅实现新入口却让旧入口继续丢失已发生工作的身份。

客户端明确 inspect 原 operation → plan → 审阅 → confirm → publication execute。执行取得 lease
后核验完整 proof/artifacts/原授权、当前输入和 pointer；合法 sealed stage 可以在旧 grant 过期后
由新 publish grant 采用，旧 grant 不恢复写权限。新 lease 内 reconcile reservation/usage，
不创建 Provider、不重复预留或结算。provider_called 在此执行结果恒为 false。

pointer 已指向该 operation 的 generation 时，inspect 投影 completed；仅 ledger/audit pending
时可生成 action=reconcile_completion 的计划，execute 只对齐持久事实，不重复 CAS/Provider。
完全完成且无 pending 的 operation 不生成可执行计划，返回 `embedding_operation_completed`；
客户端以 inspect 读取成功事实。它不被转换为 force rebuild。

stage/source/contract/pointer 漂移返回 runtime_plan_stale 或 repair_required，按迁移合同保留
已发生费用事实；未知 Provider effect、旧 ledger 无 proof 的 processing 不自动转为可重试。
新的网络 attempt 必须重新 inspect/plan/confirm 并经过当期日/月预算。零 effect/零 reservation
的 budget_paused 不永久占用 replay；active/awaiting_publish 操作跨期仍不能重复调用 Provider。

## 4. 错误与 adapter envelope

`PKVRuntimeError` 增加可选 `details: Mapping[str, object] | None = None`，默认 None；
`to_dict()` 仅在有批准的安全字段时包含 details。既有 constructor 参数和旧错误形状保持兼容。
details 不是任意 exception/context 序列化出口；本合同仅批准 pending 的四字段，以及
operation 冲突/完成的 `{operation_id,effective_state}`。未知字段拒绝投影。

| code | 触发条件/行为 |
| --- | --- |
| `outcome_invalid` | DTO、selector、reason、数字/哈希格式无效；无业务写 |
| `outcome_not_found` | review/render 对象不存在 |
| `outcome_state_conflict` | 四元组/input/pointer 不匹配、returned 后 approve、不同 reason 重放 |
| `outcome_approval_blocked` | legacy_unverified、不可审阅状态或不完整/不可用投影 |
| `outcome_evidence_stale` | 外部 evidence 绑定漂移；不代换证据 |
| `outcome_render_contract_unsupported`（新增） | 无法使用持久 renderer 版本 |
| `outcome_review_confirmation_required`（新增） | major 2 旧无版本 approve/return stub 拒绝 |
| `confirmation_required` | rebuild/publication 缺 approved 或确认；零 Provider |
| `runtime_plan_stale` | plan/root/snapshot/period/source/contract 漂移 |
| `embedding_rebuild_authorization_required` | 新网络执行缺 allow_network 或 policy 授权 |
| `embedding_budget_paused` | A 当期预算不足；零 Provider，不消费 replay 资格 |
| `write_busy` | 无已封存工作时获取 writer lease 失败 |
| `embedding_publication_pending`（新增） | 完整 proof 的操作未取得发布 lease；必须返回四字段 details |
| `embedding_operation_not_found`（新增） | 当前根不存在该 manual operation；不搜索其他根 |
| `embedding_operation_completed`（新增） | 已完成且无待对齐事实；拒绝新的执行计划 |
| `embedding_ledger_upgrade_required`（新增） | v1 mutation 遇到 legacy ledger 1/2；须经 v2 展示升级影响并明确确认 |
| `embedding_processing` | 同 material transition 活跃且无完整 proof，不重调 Provider |
| `repair_required` | proof/ledger 完整性不确定、未结算的未知外部影响、旧未终结操作缺有效 proof 或无法安全发布；已完整结算的历史终态不因 effect=unknown 单独触发 |
| `database_upgrade_required` | Outcome v2 所需持久字段未升级；不在 read/review 中迁移 |

新增错误的 enum 成员采用上述 code 的大写形式。既有安全路径/I/O/schema 错误沿用当前稳定 code，
不吞并为 not_found。review state conflict 的 recoverable=true 表示须重新审阅，不是许可自动重放；
unsupported renderer/repair_required 只能进入独立维护流程。所有 message 由 adapter 稳定映射，
不回显用户参数或异常原文。

v2 CLI 与 MCP 使用同一 body-free envelope：
`{schema:"pkv.lifecycle-response.v2",status:"success"|"error",terminal:"success"|"error",
operation:string,result:DTO|null,issues:Issue[]}`。Issue 为 code/message/stage/recoverable，以及
上述可选 details。success 时 issues 可包含 completion-pending 警告；READY 只在 pointer 已提交后
返回。pending 是 error，result=null，details 仍完整保留。CLI success 写 stdout、exit 0；业务错误
写 stderr、exit 1；Click 语法/类型错误 exit 2 且不加载 runtime。MCP 保留相同结构化 content，
不把 pending 输出为空结果；是否为 operation 终态只看 effective_state，不能从 terminal 推断。

## 5. CLI 与 MCP 映射

兼容期新增以下显式名称；major 2 继续使用同名，避免切换时再引入第二套 v2 方言。
CLI 任意深度帮助/语法检查都先于 runtime；业务 gate 仅在叶子执行。MCP 仍仅 stdio。
当前 W3 已实现表中的五项 Outcome 映射；Embedding 映射继续作为 W4 目标冻结。

| SDK 操作 | CLI | MCP Tool（参数） |
| --- | --- | --- |
| get_outcome_v2 | `outcome get-v2 TOPIC_ID` | `get_outcome_v2(topic_id)` |
| get_research_brief_v2 | `outcome brief-v2 --topic-id ID` 或 `--outcome-id ID` | `get_outcome_research_brief_v2(topic_id=null,outcome_id=null)` |
| render_research_brief_v2 | `outcome render-v2 TOPIC_ID` | `render_outcome_research_brief_v2(topic_id)` |
| approve_research_brief_v2 | `outcome approve-v2 OUTCOME_ID --expected-revision N --content-sha256 H --expected-input-revision N` | `approve_outcome_research_brief_v2(outcome_id,expected_revision,content_sha256,expected_input_revision)` |
| return_research_brief_v2 | 上述 approve-v2 改为 `return-v2`，增加必填 `--reason-code CODE` | `return_outcome_research_brief_v2(同四元组,reason_code)` |
| inspect_embedding_rebuild_v2 | `embedding inspect-v2` | `inspect_embedding_rebuild_v2()` |
| plan_embedding_rebuild_v2 | `embedding rebuild-v2 [--force]` | `plan_embedding_rebuild_v2(force=false)` |
| execute_embedding_rebuild_v2 | `embedding rebuild-v2 [--force] --apply --confirm PLAN_ID --allow-network` | `execute_embedding_rebuild_v2(plan_id,approved=false,allow_network=false,force=false)` |
| inspect_embedding_operation_v2 | `embedding operation-v2 OPERATION_ID` | `inspect_embedding_operation_v2(operation_id)` |
| plan_embedding_publication_v2 | `embedding publish-v2 OPERATION_ID` | `plan_embedding_publication_v2(operation_id)` |
| execute_embedding_publication_v2 | `embedding publish-v2 OPERATION_ID --apply --confirm PLAN_ID` | `execute_embedding_publication_v2(operation_id,plan_id,approved=false)` |

每个 MCP 参数的 scalar 类型与 SDK 相同；未知字段/缺必填/错误 bool 不可转型。get/inspect/plan
Tools 的 readOnlyHint=true，其余为 false。CLI --apply 代表 approved=true，但必须同时有当前
plan_id；只带 --confirm/--allow-network 时拒绝。publish 命令和 Tool 不提供 allow_network/force，
传入为语法错误，不能自动退化为网络 rebuild。SDK confirm 的批准默认值不代表 adapter 可替用户批准；
Tool approved 默认为 false。所有 root/config 仍由受管理入口选择，协议不接受任意路径。

v2 envelope.operation 固定使用对应 MCP Tool 名称（CLI 亦然），因此不携带用户标识。
兼容阶段旧 outcome approve/return 与旧 MCP 两个无版本 Tool 发出弃用提示但保持原签名；
major 2 中它们保留为明确拒绝的 stub，返回 outcome_review_confirmation_required。不能读取
latest 后补齐元组，不将 topic_id 当作 outcome_id，不提供“自动迁移调用”的旁路。
这些 stub 在拒绝前不 bootstrap、不取 lease、不读写业务数据。

## 6. major / capability 迁移与退出条件

兼容版本新增 `require_kernel_compatibility(..., required_api_major: int | None = None)`：
在 API-major-1 中 None 保留旧行为，显式非 1 拒绝；major 2 中 None 或非 2 均在握手阶段抛
`KernelCompatibilityError`，数据根不被打开。包根函数与 `pkv_kernel.contracts` 的对应函数
保持同一参数含义（后者既有 sdk_version 首参数不变）。required_capabilities 继续精确校验。

| 阶段 | 必须交付的兼容事实 | 不能声称 |
| --- | --- | --- |
| W1（历史冻结） | 本文签名/DTO/错误与迁移 schema 冻结；冻结时 major、版本、registry 均未改 | 文档冻结等于 v2 可调用、旧 review 已安全 |
| W3 Outcome 兼容准备（当前） | SDK `0.9.0` / API `1.0.0` 已实现独立 Outcome v2；旧符号保留并发出含替代 *_v2 名称与移除 major 的 DeprecationWarning；验收证据见 W3 实施记录 | 新入口已消除旧调用缺陷、R-04 已关闭、Embedding v2 已可用或已正式发布 |
| W4 Embedding 兼容准备（待实施） | 在兼容 SDK 中实现本合同的 Embedding v2 公开流程、ledger/grant 迁移与相应测试 | 仅有冻结文档或 Outcome v2 等于完成本阶段 |
| W5 major 2 切换 | KERNEL_API_VERSION=2.0.0；声明 `kernel.traceable-outcomes.v2` 与 `kernel.embedding-rebuild.v2`；旧无版本 review 拒绝；客户端显式 required_api_major=2 | major 1 旧 Wrapper 可猜测兼容或导入 src.* 回退 |

兼容期可以提前暴露已完整实现且通过验收的 v2 capability，但不得对尚缺公开流程的半成品声明。
major 2 不再声明上述两个 v1 capability；其他未改变语义的能力继续保留其原标识。SDK build
版本在实际版本交付时按仓库版本流程分配，不能把文档冻结当作版本发行。

OC-10a 在 W3 验证新旧符号并存、警告、exact review 和客户端迁移准备；ER 在 W4 验证
publish-only 与完整错误投影。OC-10b / SDK-01 在 W5 验证真实 major 切换、旧调用/stub/握手拒绝、
CLI/MCP 同步迁移和 installed SDK 公共边界。只有 W5 证据齐全才关闭 R-04。
迁移对旧数据的证明和费用保留规则以持久化合同为准，不由 v2 read/plan 隐式执行。
