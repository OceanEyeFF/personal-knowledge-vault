## 设计理念

### 核心原则

使用 YAML Front Matter 作为文档元数据的主要存储方式，实现：

1. **人工友好**: 可以直接在任何文本编辑器中查看和修改
2. **工具兼容**: Obsidian、VSCode、Typora 等都原生支持 YAML Front Matter
3. **快速访问**: 无需查询数据库，直接读取文件头即可获取元数据
4. **版本控制**: 元数据和内容一起进行 Git 版本管理，历史可追溯

### 为什么选择 YAML Front Matter？

**对比其他方案**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **JSON 文件** | 标准格式、解析简单 | ❌ 不支持注释、人工编辑不友好 |
| **TOML Front Matter** | 类型安全、语法清晰 | ❌ 生态支持少、多行字符串麻烦 |
| **YAML Front Matter** ✅ | ✅ 人类可读性强<br>✅ 工具生态完善<br>✅ 支持多行字符串<br>✅ Markdown 社区标准 | 缩进敏感（但编辑器都有支持） |
| **纯数据库存储** | 查询性能好 | ❌ 数据锁定、导出困难<br>❌ 无法离线访问 |

**YAML Front Matter 的独特优势**：
- 📝 **编辑器友好**: 所有 Markdown 编辑器原生支持
- 🔍 **快速预览**: 打开文件即可看到元数据，无需额外工具
- 🌐 **生态丰富**: Obsidian、Jekyll、Hugo、VuePress 等都使用这个标准
- 🔄 **人机协作**: AI 生成，人工调整，双向编辑流畅

## Markdown Front Matter 标准

### 标准模板

```yaml
---
# === 基础元数据 ===
title: "文章标题"
source_type: "wechat"  # wechat/zhihu/bilibili/pdf/personal
source_url: "https://mp.weixin.qq.com/xxx"
archived_at: "2026-01-27 20:00:00"

# === 内容分析 ===
tags: ["技术", "AI", "知识管理"]
keywords: ["RAG", "向量检索", "BM25"]
abstract: "这是一篇关于智能检索策略的文章，探讨了混合检索的优势..."

# === 多层次摘要 ===
summary_one_sentence: "混合检索策略比纯向量方案节省85%成本"
summary_100_words: |
  本文详细介绍了智能混合检索策略，包括BM25关键词检索、
  向量语义检索、以及两者的混合方案。通过对比分析，
  证明混合策略在保证检索质量的同时，能够显著降低成本。

# === 检索配置 ===
search_strategy: "keyword"  # keyword/hybrid/vector/structured
word_count: 1500

# === 关联信息（可选）===
related_docs:
  - "docs/web-archives/zhihu/相关文章.md"
  - "docs/books/某本书/chapter1.md"
children:
  - "docs/books/某本书/chapter2.md"
version_of: "docs/books/某本书/chapter1-v1.md"

# === 个人标注（可选）===
reading_status: "已读"
rating: 5
notes: "这篇文章的检索策略部分特别有启发"
---

# 文章正文从这里开始...
```

### 字段详细说明

#### 基础元数据（必填）

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `title` | string | ✅ | 文档标题 | "AI驱动的知识管理系统" |
| `source_type` | enum | ✅ | 来源类型 | wechat / zhihu / bilibili / pdf / personal |
| `source_url` | string | ⭕ | 原始链接（非个人内容必填） | "https://mp.weixin.qq.com/xxx" |
| `archived_at` | datetime | ✅ | 归档时间 | "2026-01-27 20:00:00" |

#### 内容分析（必填）

| 字段 | 类型 | 必填 | 说明 | 示例 |
|------|------|------|------|------|
| `tags` | array | ✅ | 内容标签（3-5个） | ["技术", "AI", "知识管理"] |
| `keywords` | array | ✅ | 关键词（5-10个） | ["RAG", "向量检索", "BM25"] |
| `abstract` | string | ✅ | 内容摘要（100-200字） | "这是一篇关于..." |

#### 多层次摘要（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `summary_one_sentence` | string | ✅ | 一句话总结（< 50字） |
| `summary_100_words` | string | ✅ | 100字摘要（可多行） |

**设计理由**：
- 快速浏览时看一句话总结
- 详细了解时看100字摘要
- 完整内容在正文中

#### 检索配置（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `search_strategy` | enum | ✅ | keyword / hybrid / vector / structured |
| `word_count` | number | ✅ | 字数统计（用于策略判断） |

#### 关联信息（可选）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `related_docs` | array | ⭕ | 显式相关文档相对路径列表 |
| `children` | array | ⭕ | 子文档相对路径列表；当前映射为 `parent_of` |
| `version_of` | string | ⭕ | 当前文档的版本基线相对路径；当前映射为 `version_of` |

**关系字段约束**：
- `related_docs` / `children` 都是 `list[str]`
- `version_of` 是单个 `str`
- 三者当前都只接受 vault 内相对路径字符串
- 自动关系回填当前只消费这三个显式结构字段，不消费别名字段或 URL
- `children` / `version_of` 当前属于原始 Front Matter 扩展字段，关系层会直接解析，但 `Entry` dataclass 尚未内建它们

#### 个人标注（可选）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `reading_status` | string | ⭕ | 已读 / 待读 / 在读 |
| `rating` | number | ⭕ | 个人评分（1-5） |
| `notes` | string | ⭕ | 个人笔记（可多行） |

## 双重存储策略

### 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                 Markdown 文件（主要）                     │
│  ─────────────────────────────────────────────────────  │
│  • YAML Front Matter 存储完整元数据                      │
│  • 人工编辑友好                                          │
│  • Git 版本控制                                          │
│  • 工具生态兼容（Obsidian/VSCode）                       │
│  • 数据主权：所有信息都在文件中                           │
└─────────────────────────────────────────────────────────┘
                          ↕ 同步
┌─────────────────────────────────────────────────────────┐
│              SQLite 索引 + hnswlib 向量层（辅助）         │
│  ─────────────────────────────────────────────────────  │
│  • 冗余存储关键字段（快速查询）                          │
│  • SQLite 负责元数据与 FTS5 全文索引                     │
│  • hnswlib 负责文档/分块 embedding                       │
│  • 提供复杂 SQL 查询能力                                 │
└─────────────────────────────────────────────────────────┘
```

### 存储原则

**Markdown 为主，SQLite + hnswlib 为辅**

- **主存储**: Markdown 文件（YAML Front Matter + 正文）
  - 所有元数据和内容都在这里
  - 即使数据库丢失，也不会丢失任何信息
  - 可以随时从 Markdown 文件重建数据库

- **辅助存储**: SQLite 索引数据库 + hnswlib 向量索引
  - SQLite 存储关键字段冗余副本、FTS5 索引与查询所需结构
  - hnswlib 独立存储文档级 / 分块级 embedding
  - 是性能优化手段，而非数据主体

### 同步机制

#### 写入流程

```
1. AI 分析内容 → 生成元数据（tags, keywords, summary等）
    ↓
2. 构建 `Entry`
   → 组织 YAML Front Matter 对应字段
   → 准备正文内容
    ↓
3. `MarkdownStore.save()`
   → 写入 Vault 中的 Markdown 文件
   → 产出 `file_path`
    ↓
4. `SQLiteStore.insert_entry()`
   → 写入 `knowledge_items`
   → 建立 SQLite / FTS5 可查询副本
    ↓
5. （可选）`VectorStore`
   → 生成文档向量与分块向量
   → 长文同时写入 `content_chunks`
```

#### 读取流程

**场景1：快速访问单个文档**
```
用户打开文件
  ↓
直接读取 Markdown 文件
  ↓
解析 YAML Front Matter
  ↓
展示元数据 + 正文
```
**优势**: 无需数据库，离线可用，速度极快

**场景2：复杂查询**
```
用户执行查询（如"最近一周的微信文章"）
  ↓
SQLite / FTS5 查询
  ↓
返回文件路径列表
  ↓
读取对应 Markdown 文件
  ↓
展示结果
```
**优势**: 强大的过滤、聚合、排序能力

#### 手动编辑同步

```
1. 用户在编辑器中修改 YAML Front Matter
    ↓
2. 当前代码不会自动监听文件变化
    ↓
3. 如需刷新 SQLite / 向量 / 关系索引，需要显式执行对应重建或回填流程
    ↓
```

**冲突处理**：
- Markdown 文件的修改时间 > 数据库记录 → 以文件为准
- 当前仓库未提供 `watchdog` 自动同步、`sync_log` 表、`/kb:sync-check` 或 `/kb:rebuild-db` 命令
- 关系边刷新需走显式回填流程，当前关系层合同见 `docs/specs/interfaces/Relations接口规范.md`

### 设计优势

1. **真正的数据主权**: 所有元数据都在 Markdown 中，随时导出，永不锁定
2. **编辑器友好**: 任何支持 Markdown 的编辑器都能查看和编辑
3. **零依赖访问**: 即使没有数据库，也能通过文件系统访问所有信息
4. **灵活扩展**: 可以随时在 YAML 中添加自定义字段，无需改数据库 Schema
5. **工具生态**: 兼容 Obsidian 插件、VSCode 扩展、Jekyll/Hugo 等现有工具
6. **容灾恢复**: 数据库损坏？从 Markdown 重建。文件丢失？Git 恢复

## 文件命名规范

### 基本原则

- **唯一性**: 同一来源类型下，文件名不重复
- **可读性**: 文件名直接反映内容主题
- **兼容性**: 避免特殊字符，确保跨平台兼容

### 命名规则

```
{标题}-{日期后缀}.md
```

**示例**：
```
AI驱动的知识管理系统.md
AI驱动的知识管理系统-20260127.md  （同名时加日期后缀）
```

### 特殊字符处理

**替换规则**：
- `/` → `-`（路径分隔符）
- `?` → `？`（全角问号）
- `:` → `：`（全角冒号）
- `*` → `×`（乘号）
- `"` → `'`（单引号）
- `<` `>` `|` → 删除

**Python 实现参考**：
```python
def sanitize_filename(title: str) -> str:
    replacements = {
        '/': '-',
        '?': '？',
        ':': '：',
        '*': '×',
        '"': "'",
    }
    for old, new in replacements.items():
        title = title.replace(old, new)

    # 移除非法字符
    title = re.sub(r'[<>|]', '', title)

    # 限制长度
    return title[:100]
```

## 目录结构规范

### 内容目录设计

```
docs/
├── books/                      # 书籍
│   ├── 技术类/
│   │   ├── 深入理解计算机系统/
│   │   │   ├── chapter1.md
│   │   │   └── chapter2.md
│   │   └── Python高级编程.md
│   └── 非技术类/
│
├── web-archives/               # 网页归档
│   ├── wechat/                 # 微信公众号
│   │   ├── 文章标题1.md
│   │   └── 文章标题2.md
│   ├── zhihu/                  # 知乎
│   │   ├── 问题-回答标题.md
│   │   └── 专栏文章标题.md
│   └── bilibili/               # B站视频
│       ├── 视频标题.md
│       └── attachments/        # 附件（封面、音频等）
│
└── experiences/                # 个人经历
    ├── 项目总结/
    ├── 学习笔记/
    └── 思考记录/
```

### 目录层级原则

- **最多三级**: `docs/{类型}/{分类}/{文件}` 或 `docs/{类型}/{文件}`
- **按来源分类**: 不同内容来源在不同目录（wechat / zhihu / bilibili）
- **扁平优先**: 避免过深嵌套，除非内容确实需要分层（如书籍章节）

### 附件存储

```
web-archives/
└── bilibili/
    ├── 视频标题.md              # 主文档
    └── attachments/
        └── 视频标题/            # 与主文档同名的附件目录
            ├── cover.jpg        # 封面
            ├── audio.mp3        # 音频
            └── comments.json    # 评论数据
```

**原则**：
- 附件与主文档名称关联
- 大型附件（视频、音频）可选择性存储
- 元数据指向附件相对路径
