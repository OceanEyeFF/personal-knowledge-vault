本文是[生命周期一致性修复计划](../../overview/生命周期一致性修复设计与分阶段计划-2026-10.md)

## 1. 三种独立版本

| 存储 | 当前事实 | 冻结目标 | 实施阶段 |
| --- | --- | --- | --- |

## 2. 统一编码与 identity

本节新哈希使用 `SHA256(UTF8(domain) || 0x00 || canonical_json(payload))`，输出小写 64 位
十六进制。canonical JSON 固定为 UTF-8、无 BOM、无结尾换行、对象键按 Unicode code point
排序、紧凑分隔符、字符串不转义非 ASCII、只允许有限整数/字符串/布尔/null/数组/对象；
禁止浮点、重复 key、非有限值和未声明字段。文本先经现有 Outcome 文本规范化与隐私校验，
此编码不额外进行 Unicode NFC/NFKC 转换。数组按下文指定排序，不以运行时遍历顺序为准。
整数不接受 bool，revision 范围为 `1..9223372036854775807`，到上限明确拒绝，不回绕。

原有摘要继续保留其语义：`content_sha256` / manifest / artifact hash 是原始文件字节 SHA-256；
`runtime_snapshot_sha256` 是通过无密钥验证的 snapshot 原始字节 SHA-256；根摘要沿用当前
`SHA256(config.data_root_identity.encode('utf-8'))`，不把根路径原文放进 public DTO。
新 domain hash 不应静默替换这些既有摘要。

`contract_sha256` 固定使用 domain `pkv.embedding.contract.v2`，payload 精确为
`{provider,model,dimension,endpoint_fingerprint}`。network plan、material replay、publication
plan 的 domain 和 canonical payload 以 v2 接口冻结合同第 3.2 节为唯一权威，使用本节编码；
ledger/grant/proof 不另行重命名字段或再算一套 contract hash。

### 2.1 Outcome 输入摘要

`input_digest` domain 为 `pkv.outcome.input.v1`，payload 的所有键如下：

| 键 | 规范值 |
| --- | --- |
| `input_revision` | Topic 新的完整输入版本 |
| `render_contract_version` | 初始冻结值 `research-brief.v2` |
| `topic` | `topic_id,outcome_id,title,question,state,revision`；最后一项仍是已有 Topic 自身 revision |
| `evidence` | 按 `(ordinal,evidence_id)` 排序；每项 `evidence_id,ordinal,locator,locator_kind,source_revision_sha256,acquisition_method,retrieval_status,recorded_state,limitation_codes` |
| `claims` | 按 `(ordinal,claim_id)` 排序；每项 `claim_id,ordinal,statement,state,revision,limitation_codes,evidence_links` |

`limitation_codes` 去重后按 ASCII 排序。`evidence_links` 每项仅
`evidence_id,polarity`，按 evidence_id 排序；关系删除由同一输入事务处理。
locator 使用已规范化的 public `pkv://` 值。时间戳、next ordinal、审阅状态、文件健康状态、
临时观察结果、source 正文、路径及 Provider 材料不进入摘要。

renderer 只能消费这份持久输入、candidate revision 和 outcome_id；固定渲染合同必须保证相同
输入输出相同 Markdown 字节（UTF-8、LF、一个结尾 LF）。source revalidation 是独立发布/审批
门禁，不得把即时观察到的 effective state 塞进同一 input digest 的渲染字节。需改变持久
Evidence/Claim 状态时先完成显式输入 mutation，再重新 render；render/read 不自行推进输入。
升级后没有 Topic 所绑定 renderer 时返回 `outcome_render_contract_unsupported`，不改 digest。

### 2.2 publication 与 review receipt

`publication_id` domain 为 `pkv.outcome.publication.v1`，payload 精确为
`{outcome_id,candidate_revision,input_digest}`。新文件固定在
`outcomes/topic-<topic_id>/<outcome_id>-r<revision:04d>-p<publication_id>.md`；
超过四位的 revision 不截断，使用完整 64 位 publication hash，不使用短 hash。
路径完全由经过校验的 ID 派生，不接受调用者路径。旧 pointer 的文件名保留原样。

`receipt_id` domain 为 `pkv.outcome.review.v1`，payload 精确为
`{outcome_id,expected_revision,content_sha256,expected_input_revision,action,reason_code}`。
approve 的 reason 为 null；return 的 reason 必须是 `needs_revision`、`insufficient_evidence`
或 `other` 之一。receipt 无自由文本，不含用户身份猜测、正文或环境信息。

## 3. SQLite 1.2.8 物理模型

014 保留现有五张表及其字段意义。重建 `outcome_topics`、`outcome_briefs` 以获得完整约束，
其余三张表的列、行与原有 FK 语义保持。增加 `outcome_review_receipts`。表名不带 API 版本。
标为 SHA 的列同时要求 TEXT、长度 64 且只含 `[0-9a-f]`；不只检查长度。

### 3.1 outcome_topics

| 新列 | SQL 类型及约束 | 写入规则 |
| --- | --- | --- |
| `outcome_id` | TEXT NOT NULL UNIQUE，现有 opaque ID 校验 | 创建 Topic 的同一事务分配 `outcome-<uuid4hex>`；从不作为“已生成”的证据 |
| `input_revision` | INTEGER NOT NULL CHECK >=1 | 创建/迁移为 1；实际输入 mutation 恰好加一；no-op/失败/render/review 不增加 |
| `input_digest` | TEXT NOT NULL，SHA | 由第 2.1 节在输入事务中计算 |
| `render_contract_version` | TEXT NOT NULL | 初始 `research-brief.v2`；只允许显式输入合同迁移修改 |

新增 `UNIQUE(topic_id,outcome_id)` 供 brief 复合外键引用。`revision` 保持 Topic 自身字段修订
语义，不重命名为 input_revision；Evidence/Claim 变更也推进 input_revision，但不伪造 Topic
文本 revision。删除 Topic 的既有级联范围包含其 receipts。

### 3.2 outcome_briefs

保留 `outcome_id` 主键、`topic_id` 唯一和既有 pointer/state/revision；以复合外键
`(topic_id,outcome_id) → outcome_topics(topic_id,outcome_id)` 防止身份串联。新列为：

| 新列 | SQL 类型及约束 | 规则 |
| --- | --- | --- |
| `binding_state` | TEXT NOT NULL CHECK IN (`verified`,`legacy_unverified`) | 新发布必须 verified；迁移旧行一律 legacy_unverified |
| `publication_id` | TEXT NULL UNIQUE，非空时为 SHA | 与已提交 pointer 一起写入；旧行 NULL |
| `rendered_input_revision` | INTEGER NULL，非空时 >=1 | 被发布输入版本；旧行 NULL |
| `rendered_input_digest` | TEXT NULL，非空时为 SHA | 被发布输入摘要；旧行 NULL |
| `render_contract_version` | TEXT NULL | 被发布 renderer 合同；旧行 NULL |

CHECK 固定两种合法组合：verified 时以上四项全部非 NULL；legacy_unverified 时四项全部
NULL。不从文件名或当前 Topic 猜测历史 publication/binding。旧 `state` 原值保留，包括
approved/returned；旧行的 effective state 一律 needs_review，审批返回
`outcome_approval_blocked`。仅新 render 的 pointer commit 把 binding_state 变为 verified。

`revision` 只在新 pointer 成功提交时加一。CAS 比较捕获时的旧 pointer 全元组
`(outcome_id,revision,markdown_relative_path,content_sha256,publication_id)`，首次为 absent，
并比较当前 Topic `(input_revision,input_digest,render_contract_version)`。CAS 失败不回退
竞争者 pointer；文件仅在没有被当前已提交 pointer 引用时属于 orphan。旧 revision 的文件
继续保留，但本阶段不新增可公开遍历历史全文的 API。

### 3.3 outcome_review_receipts

| 列 | 类型/约束 |
| --- | --- |
| `receipt_id` | TEXT PRIMARY KEY，SHA |
| `outcome_id` | TEXT NOT NULL，FK → outcome_topics(outcome_id) ON DELETE CASCADE |
| `expected_revision` | INTEGER NOT NULL CHECK >=1 |
| `content_sha256` | TEXT NOT NULL，SHA |
| `expected_input_revision` | INTEGER NOT NULL CHECK >=1 |
| `action` | TEXT NOT NULL CHECK IN (`approve`,`return`) |
| `reason_code` | TEXT NULL；approve 必须 NULL，return 必须为第 2.2 节三值之一 |
| `result_state` | TEXT NOT NULL；approve 必须 approved，return 必须 returned |
| `created_at` | TEXT NOT NULL，UTC RFC3339 毫秒时间，仅记账，不进入 receipt hash |

增加 `UNIQUE(outcome_id,expected_revision,action)` 与
`INDEX(outcome_id,expected_revision)`。receipt append-only；它不通过 FK 绑到会更新的 brief
revision，不因生成下一版而失去前版审阅证据。014 不为历史审批合成 receipt。

review 在 writer lease 内复核来源和投影，并在同一连接的一个事务中检验四元组、current /
rendered input、binding_state 和状态转移；CAS 更新 state 与 INSERT receipt 一起提交。
允许 awaiting_review→approved、awaiting_review→returned、approved→returned；returned
对该 revision 终止。相同元组/action/reason 且当前仍为目标状态时返回原 receipt；重放旧
approve 不会撤销后来 return。reason 不同、元组失配或状态不允许均为 outcome_state_conflict，
不新增 receipt、不更新 state。审计文件是外部旁证，不代替 SQLite receipt 原子性。

### 3.4 输入 mutation 的唯一 commit

同一个 SQLite transaction 完成输入行/边修改、input_revision +1、digest 更新及已有
brief.state=needs_review。no-op 由规范化后的完整持久值比较决定，不因 UPDATE 匹配行数
非零而推进版本。删除 Evidence 与级联边也只推进一次。事务失败不能仅回滚失效标记。
reader 使用一个显式 read transaction 捕获整份 bundle；同一时刻的 input binding、pointer
和 receipts 不允许由多次 autocommit SELECT 拼接。

## 4. 014 升级步骤与失败边界

升级仅接受通过旧结构验证的 1.2.7（或已验证历史链先到达 1.2.7）。014 的 DDL 与受版本控制
的 body-free backfill hook 共同组成一次迁移，不能让纯 SQL 的 schema_version INSERT 提前
宣告完成。迁移清单必须同时绑定 SQL 与 hook 的内容摘要；canonical hash 逻辑复用产品合同
实现，测试不能另写一个宽松算法代替。具体实现留 W3，本节没有可执行迁移脚本。

1. 只读 inspect 检查版本链、FK、原有行约束、安全文件身份，捕获数据库指纹；显式 migration
   plan 展示 014、未知历史绑定数量及没有正文/向量改动，绑定 schema/代码迁移清单摘要。
2. 获得确认、备份要求满足后，在 root writer lease 和现有 publication lock 下复制到同目录
   private work database。旧 DB 及其 Markdown 文件此时不修改。
3. 仅 work connection 在事务外禁用 FK enforcement；`BEGIN IMMEDIATE` 后创建带完整目标
   约束的临时 topics/briefs 表（其 FK 最终目标名仍为 outcome_topics），复制 rows，删除旧
   briefs/topics，重命名新表，重建原 indexes，创建 receipts。其余 Evidence/Claim/边不变。
4. Topic 已有 brief 时保留其 outcome_id；无 brief 时在本迁移事务生成并持久预留新 ID。
   所有 Topic input_revision=1、render_contract_version=research-brief.v2，按当前持久输入
   计算新 input_digest。它只声明迁移后的当前输入，绝不证明历史 brief 曾使用这些输入。
5. 旧 brief 全部 legacy_unverified，保留 state、revision、pointer、content SHA 与原时间戳；
   binding/publication 四列 NULL。无新 receipt，不重写 Markdown，不读 source 正文猜绑定。
6. 验证所有目标约束、FK、数据行/边/ID 保真、input digest、未改投影字节，最后在同一 work
   transaction 写入 schema_version 1.2.8 并 COMMIT。重新启用 FK，执行 foreign_key_check、
   integrity_check 和完整版本结构校验。不得在原数据库上暂时禁用 FK。
7. 复核原 DB 指纹未变和 work file 身份后沿用现有原子发布替换。发布前任何失败保留原 DB；
   发布后响应中断以重新 inspect 的 1.2.8 + 结构/摘要证明为完成判据，不重跑 014 或回滚旧文件。

重复执行已完成 014 必须为经结构验证的 no-op；同版本但缺列/receipt table/约束不能当作成功，
返回 repair_required。未来软件不得在普通 read/render/review 中建列或回填；旧 schema 返回
database_upgrade_required。旧软件打开比自身已知版本更新的 schema 必须拒绝写；W5 混合版本
验收未通过前不允许关闭兼容问题。没有 inplace downgrade；失败前保持原库，成功后恢复旧库
须另有完整 lifecycle/数据损失评估，本 W1 不定义用户可直接执行的恢复命令。

## 5. manual rebuild ledger v3

继续使用 `runtime/embedding-rebuild-ledger.json`。顶层精确为
`{schema_version:3,operations:{operation_id:record}}`；对未知字段/版本/重复 key 拒绝。
普通 inspect 零写；只有明确授权 mutation 的 root lease 内可升级或原子替换 ledger。
新记录保留 v2 的 operation_id、plan_id、public_plan_id、replay_key、source_revision、
policy_fingerprint、reservation、local_estimate、provider_usage、generation_id、last_error_code。

| v3 字段 | 取值与约束 |
| --- | --- |
| `record_origin` | `native_v3` 或 `legacy_v1` / `legacy_v2` |
| `identity_schema` | 新记录 `pkv.embedding.transition.v2`；legacy 保留原 schema 标识，不猜新 identity |
| `data_root_identity_sha256`,`runtime_snapshot_sha256`,`contract_sha256` | 新记录必填 SHA；legacy 缺失为 NULL |
| `budget_check_period` | `{timezone,local_day,local_month}`；新网络必填，legacy 从 reservation 取值或 NULL |
| `provider_effect` | `not_started`,`unknown`,`completed`；替代语义不足的 provider_attempted 布尔 |
| `state` | `processing`,`awaiting_publish`,`activation_intent`,`completed`,`failed`,`budget_paused`,`repair_required` |
| `stage_key` | 仅内部的单段 stage 目录名；新 operation 在 A 分配后必填，尚未分配或 legacy 无证明时 NULL |
| `grant_sha256`,`proof_sha256` | grant marker / proof 原始字节 SHA，未产生时 NULL |
| `usage_completeness` | `complete`,`partial`,`unknown`；不把 NULL 变成 0 |
| `settlement_basis` | `provider_reported`,`conservative_reservation`,NULL；与已 settlement 记录一致 |

旧 v1/v2 ledger 的闭合路径是：v2 inspect 在内存中执行第 5.1 节严格分类；network /
publication plan 展示 `ledger_upgrade=null` 或
`{from_schema:1|2,to_schema:3,source_sha256,operation_count,blocking_operation_count}`。
source_sha256 绑定旧 JSON 原始文件字节；该对象进入 plan_id，不进入 material replay key。
存在 blocking operation 时，inspect 返回 repair_required、不能生成新的 network 执行计划；
正常历史终态不属于 blocking。用户确认该计划后，execute 在 A 的 root lease 内复核原文件
SHA、计数与完整分类，先原子升级 v3，再进行 reservation 或发布。任一变化使计划 stale，
不以当前文件代填旧确认。空 ledger 的 ledger_upgrade 为 null，新写直接使用 v3。

这一步升级已经包含在用户确认的 mutation 内：升级成功、后续 reserve 失败时保留合法 v3，
不回退文件，也不谎称整体零持久副作用；Provider 和新 reservation 仍可保持为零。升级文件
替换后、响应前中断，后续 inspect 展示 v3；旧计划因 upgrade material 已变须重新确认，
不能反复升级或保留旧计划作通用许可。publication 的 legacy 升级仅可对有可验证完成事实的
`reconcile_completion` 进行，不能给没有 proof 的旧 processing 生成 publish-only。

新版 SDK 的 v1 façade 面对空/已 v3 ledger 可使用共同 Core（保留 D 的 pending error/details）；
面对 legacy v1/v2 的 mutation 返回 `embedding_ledger_upgrade_required`，引导上述 v2 显式
计划，不自动升级。旧软件仅认识 <=2 时必须按未知未来 schema 拒绝 v3 写入。普通 v1/v2
inspect 不能为迁移调用 writer 或建立文件。API major 切换本身不改写任何 ledger。

`stage_key` 必须匹配 `.stage-g-[0-9a-f]{16}-[0-9a-f]{16}`，只经内部 layout 拼接和 no-follow
验证；从不接收客户端路径，也不通过 DTO 暴露。新 v3 不继续写 provider_attempted；旧值在
升级分类时消费，不作为未来调用许可。usage 各维度与 reservation 的原有形状/时区/期间
保持，新增 completeness 表示 Provider 报告是否覆盖所有已完成调用；合计中的未知维度为 NULL。

A 内在 Provider 可能获准运行前，把 provider_effect 从 not_started 持久改为 unknown；
离开 lease 后不再写共享账本。只有完整 C proof 可将 effective provider_effect 投影为 completed。
活进程可以在确认 Provider 从未开始的失败路径重新取得 lease 后 release；重启仅凭旧
provider_attempted=false 不足以证明未开始。

预算拒绝、未开始失败、in-flight、sealed、completed 分别应用 R4-P1 的 replay 状态矩阵。
replay key 排除 force/预算期间；它不是 public plan_id。跨日/月 publish-only 沿用原 reservation
期间，不新建预留；结算取 `max(reserved_tokens,known_provider_total)`，未知事实继续为 NULL，
超出预估的已发生用量如实保留并阻止后续超额调用，不能伪造 hard cap 从未被超过。

### 5.1 v1/v2 升级分类

原文件在验证全部记录后一次性转成 v3；任一记录无法解析就整体拒绝，不跳过坏行或截断旧事实。
成功升级不调用 Provider、不移动 stage、不改变 runtime pointer。分类如下：

| 旧事实 | v3 结果 |
| --- | --- |
| budget_paused，零 reservation，provider_attempted=false，无 usage/generation | 保留拒绝事实；not_started，不消耗后续 replay |
| failed，reservation 已 released，provider_attempted=false，零 usage | not_started；新确认可建立新 operation |
| completed 且 generation/settled reservation 完整 | 保留 completed、原 usage/期间；provider_effect=unknown、proof_valid=false；不制造 proof、不重发布，只作历史已结算事实 |
| failed 且 provider_attempted=true、settled reservation | 保留已发生费用及失败终态，不授权重跑旧 operation |
| processing / activation_intent，无可核验 v3 proof | repair_required，provider_effect=unknown；保留 reservation，不自动 release/retry |
| 字段组合自相矛盾、旧缺失费用或旧 identity 无法验证 | 整体失败或 repair_required；不猜零消费/完成 |

legacy 未终结操作或未结算的未知外部影响阻断该根新的手动 network rebuild，直到独立 repair
合同解决；不通过新 schema/新 plan 绕过。`provider_effect=unknown` 单独不构成整根围栏：
已经完整结算的 legacy completed/failed 保留历史事实，允许当前根按新的明确 plan 工作，
不因为旧记录没有 proof 而永久禁用该根。旧 completed 不是新 public plan 的合法确认凭据。
旧阶段 marker v1 不可
被升级成“曾合法封存”的 v2 grant/proof；无 proof 的 B/C 强杀恢复仍后置。

## 6. private grant v2 与 sealed proof

### 6.1 grant 与封存

grant marker 继续命名 `.generation-stage-grant.json`，schema_version=2。精确字段：
`schema_version,operation_id,owner_fence,plan_id,public_plan_id,source_revision,
data_root_identity_sha256,runtime_snapshot_sha256,contract_sha256,stage_key,issued_at_ms,
expires_at_ms`。ID/fence 沿用既有校验，时间为非负 Unix UTC 毫秒、expires>issued。
ledger 在 A 保存该 marker 的原始 SHA；marker 不保存 secret，也不接受客户端注入。

C 完成四个 artifact 和 generation manifest 的持久发布及 strict readonly 验证后，在同一
operation 窄 grant 下独占、不可覆盖地发布 `.publish-ready.json`。每次写仍验证 marker、
layout、owner fence 和 expiry；最后一次封存校验必须满足 issued<=sealed_at<=expires。
proof 发布成功立即撤销本 capability 的后续写许可；即使旧对象尚存，也须因 proof 已存在
而拒绝任何 stage write。proof 前失败不构成 awaiting_publish，不凭“文件看似齐全”代造 proof。

### 6.2 proof JSON 字段（不允许额外字段）

| 字段 | 规范 |
| --- | --- |
| `schema` | `pkv.embedding.publish-ready.v1` |
| `operation_id`,`plan_id`,`public_plan_id` | 原 operation / core plan / 用户确认计划 |
| `data_root_identity_sha256`,`runtime_snapshot_sha256`,`source_revision`,`contract_sha256`,`policy_fingerprint` | 与 A 接受的身份一致的 SHA |
| `grant_sha256`,`owner_fence`,`stage_key`,`sealed_at_ms` | 原 marker digest、原 fence、内部 stage key、封存时间 |
| `generation_id` | 原 manifest 的 `g-...` identity |
| `manifest_sha256` | generation-manifest.json 原始 SHA |
| `artifact_sha256` | 精确四键：doc_vectors.idx、doc_vectors_metadata.json、chunk_vectors.idx、chunk_vectors_metadata.json，各为原始 SHA |
| `provider_effect` | 固定 `completed`，表示已结束本次 Provider work，不表示 usage 已知 |
| `provider_call_count` | 非负整数；与完成结果一致，不通过新调用补齐 |
| `provider_usage` | 原 TokenUsage 对象或 NULL；各已知维度为非负整数，source=provider_reported |
| `usage_completeness` | complete/partial/unknown；unknown 时 provider_usage=NULL |
| `reservation_id` | A 中原 reservation 的 32 位 hex identity |

proof 存储采用第 2 节 canonical JSON 加一个 LF；`proof_sha256` 是这份完整原始文件字节的
SHA，不在 proof 内自引用。marker 同样采用 canonical JSON + LF。manifest 使用现有版本，
不为了塞入 proof 改其 schema。proof/marker 均留在私有 stage，不进入公开 final generation。
它们是产品受控文件完整性证据，不是防同用户篡改文件的密码签名或用户授权凭据。

### 6.3 只读发现与有 lease 的采用

lookup 仅从该 operation 的 ledger.stage_key 定位私有 stage，验证 no-follow、marker hash、
operation/fence/root/source/contract、seal 时间和全部文件摘要，才可投影 awaiting_publish。
不得遍历任意路径猜 operation，不写 ledger。D 竞争返回 embedding_publication_pending 及
安全 operation/effective_state；公开仅能出现 proof_valid/proof_sha256，不暴露 grant/fence/path。

重新采用先明确 inspect→publish plan→confirm，在新 root lease 内重复验证；旧 grant 已过期
只禁止旧写，不单独拒绝有效期内封存产物。新 publish grant 只授权既有只读 artifact 的
validate/publish/CAS，不延长 stage grant、不构造 Provider。lease 内先把有效 proof hash 与
usage 对齐 ledger，再记录 activation_intent 和原 generation identity；final generation 只含
四 artifact + manifest。私有 proof/marker 保留为完成证据，本阶段不定义自动清理。

发布期间不能先删除唯一 proof 再移动最后一份 artifact：保留 sealed stage 的只读副本至完成，
按现有 final-directory 保留/验证合同发布独立 generation 副本；已有同 generation final 仅在
完整字节一致时采用，部分 final 为明确 repair。snapshot CAS 成功后 pointer 是成功判据；
ledger/audit 未对齐只允许 action=reconcile_completion，不再做 CAS 或 Provider。若根/source/
contract/policy/snapshot 漂移导致不可发布，安全终结或 repair，并在有 lease 时保守结算原费用。

### 6.4 跨进程完成对齐的权威

当前 AuditTrace 仅有 `audit.jsonl` append/fsync 与进程内 terminal 标记，并无跨进程去重。
W4 必须在既有文件格式/路径上补齐以下规则；不得把某次异常后的内存 bool 当作重启后的事实。

- `publication_committed` 对新操作由当前 root binding、operation 对应 generation/manifest、
  已提交 snapshot pointer（或明确保留的成功发布事实）共同证明；仅 activation_intent 不证明成功。
  `ledger_completion_pending` 表示已证明发布完成，但同 operation 的 ledger 还不是 completed
  或其 reservation 尚未 settled；lookup 只推导，execute 在 lease 内幂等结算，不重复预留。
- 新 completed 审计事件沿用 `operation=embedding_rebuild,phase=completed`，其 result 必含
  `operation_id,generation_id,manifest_sha256,completion_id`。completion_id 使用 domain
  `pkv.embedding.audit-completion.v1` 和 payload `{operation_id,generation_id,manifest_sha256}`。
  其余安全 context/previous generation 保持原合同；不因该索引读取而把旧 audit 正文投影出来。
- 只读 status 通过 layout/no-follow gateway 读取已有 JSONL，匹配精确 completed event；存在
  同 completion_id 的完整一致记录才表示 audit 已完成。recorded_at 不参与身份。旧格式完成
  事件无 completion_id 时，只在其 result.operation_id/generation_id 与同 operation 的有效
  activation_intent.manifest_sha256 和已验证发布事实同时一致时采用为历史完成旁证。
- 未发现匹配记录且文件可完整读取/解析时，`audit_completion_pending=true`。无 audit 文件
  可视为缺记录；权限/IO、截断行、冲突的同 identity 记录或无法判断格式均返回 repair_required，
  不猜 pending=false，也不删除/截断用户日志。旧 completed 已结算本身不是 audit 完成证明。
- reconcile_completion execute 在 root lease 内重新确认完成事实，重新查精确完成事件；已有
  一致事件则零追加，否则经 AuditTrace append/fsync 一次完成事件。append 已成功但响应或
  后续 ledger 写中断时，下次从文件识别同 identity，不再追加；不同 identity 不得互相代替。
  若 pointer 已不再指向旧 generation，须有已验证保留的 generation/manifest 与历史完成证据
  才可认定过去成功；不确定则 repair，不通过重新 CAS 使它“再次成功”。

因此 `audit_completion_pending` 没有必须新增的 SQLite table 或共享 ledger 布尔；其权威是
已有 durable audit 完成事件。完成费用结算与审计追加各自幂等，失败保留已提交 generation，
只报告相应 pending/repair，不把已完成工作转换成重新收费许可。
