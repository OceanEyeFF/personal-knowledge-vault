## 项目概述

### 1.1 项目背景与问题

在信息爆炸的时代，我们每天接触大量有价值的内容：
- 📚 **书籍**: PDF、电子书、读书笔记
- 🌐 **网页**: 微信文章、知乎回答、技术博客
- 🎬 **视频**: B站视频转录、讲座记录
- ✍️ **个人**: 日记、项目总结、思考记录

**现有知识管理工具的痛点**：
- ❌ **处理效率低**: 手动复制粘贴、整理耗时
- ❌ **检索不智能**: 关键词匹配不准确，找不到相关内容
- ❌ **缺乏语义理解**: 无法理解"概念性"查询
- ❌ **工作流割裂**: 收集、整理、检索是独立的工具和步骤
- ❌ **过度依赖某一技术**: 要么全是关键词检索（不理解语义），要么全是向量检索（成本高、不适合精确查询）

### 1.2 项目定位

本项目旨在构建一个 **AI-First 的个人知识库系统**，核心特点：

**设计哲学**：
1. **AI 作为协作者，而非纯工具**: 以 Claude Code/CodeX 作为智能协作伙伴，支持人机协作式知识处理
2. **智能混合检索**: 根据内容特点自动选择最优检索策略，而不是一刀切
3. **工作流驱动**: 一切操作皆工作流，可编排、可观测、可中断
4. **本地优先**: 数据完全掌控，隐私安全

**核心价值主张**：
- **效率**: 一条命令完成"链接→知识库"全流程
- **智能**: 精确关键词 + 语义理解 + 上下文感知的混合检索
- **沉淀**: 自动摘要、打标签、建立关联，形成知识网络
- **个性化**: 支持人机协作，融入个人思考和判断

### 1.3 项目范围

#### 第一期（MVP）范围：
- ✅ 网页内容归档（微信、知乎、通用网页）
- ✅ B站视频处理（转录 + 评论分析）
- ✅ 智能混合检索（BM25 + 向量）
- ✅ 命令行界面（Slash Commands）

#### 第二期（扩展）范围：
- ⏸️ PDF 书籍处理
- ⏸️ Web 可视化界面
- ⏸️ 知识图谱可视化
- ⏸️ 个人经历时间轴

#### 明确不做的事：
- ❌ 公开分享/社交功能
- ❌ 移动端应用
- ❌ 多人协作
- ❌ 云服务版本（第一期）

## 核心设计理念

### 2.1 AI-First 工作流体系

**理念**: 将 AI 从"自动化工具"提升为"智能协作者"

**传统方式**（机械化）:
```
用户 → 输入 URL → 黑盒脚本处理 → 输出结果 → 存档
         ↓ 问题：无法干预、无法融入思考、过程不透明
```

**本项目方式**（AI 协作）:
```
用户 → Slash Command → Claude Code 工作流引擎
                          ↓
                     【分步骤协作处理】
                          ↓
        阶段1: 内容抓取与初步解析
                ↓ (可人工确认)
        阶段2: AI 增强（摘要、标签、关键点）
                ↓ (可调整 AI 输出)
        阶段3: 知识关联与索引
                ↓ (可手动建立关联)
        阶段4: 存储与反馈
                          ↓
                   生成个性化知识库
```

**关键差异**：
- ✅ **透明性**: 每个步骤可见、可理解
- ✅ **可控性**: 关键节点可人工干预和调整
- ✅ **个性化**: 支持融入个人思考和判断
- ✅ **可观测**: 实时进度反馈、日志记录

### 2.2 核心设计原则

#### 原则1: 工作流即一切

**理念**: 每个常用操作都应该是一个清晰、可编排的工作流

**实践**：
- 所有功能通过 Slash Commands 暴露（如 `/kb:archive-url`）
- 工作流配置化（YAML 定义流程）
- 支持嵌套工作流（复杂任务拆解）
- 每个步骤有清晰的输入/输出契约

**好处**：
- 用户知道"发生了什么"
- AI 可以学习和优化工作流
- 易于扩展新功能（添加新的工作流）
- 便于测试和调试

#### 原则2: 智能检索策略 - 不是所有内容都需要向量化

**核心洞察**: RAG（向量检索）并非银弹，应根据内容特点选择最优策略

**策略决策树**:
```
内容特征分析
    ↓
├─ 短文本（< 2000字）且查询偏精确
│  → BM25 关键词检索
│  → 理由: 精确匹配更准、速度快、零成本
│
├─ 中等文本（2000-5000字）且查询有语义
│  → BM25 粗排 + 向量精排（混合检索）
│  → 理由: 兼顾精确性和语义理解
│
├─ 长文本（> 5000字）且需要语义理解
│  → 向量分块检索 + 上下文合并
│  → 理由: 适合"哪里提到过XX"类查询
│
└─ 结构化内容（如视频带时间轴）
   → 专用结构化索引
   → 理由: 支持时间点定位和跳转
```

**设计依据**：
1. **性能**: BM25 比向量检索快 10-100 倍
2. **成本**: BM25 零成本，向量需要 API 调用
3. **准确性**: 精确查询（如专有名词）BM25 更准
4. **适用性**: 不同查询类型需要不同技术

**成本对比**: 混合策略比纯向量方案节省 **85% API 成本**

#### 原则3: 渐进式实施 - MVP 优先

**理念**: 先验证核心价值，再扩展功能

**实施策略**：
- **Phase 0 (3-5天)**: 端到端原型，验证可行性
- **Phase 1 (2周)**: MVP 核心功能（网页归档 + 基础检索）
- **Phase 2 (2周)**: 扩展能力（B站、智能检索）
- **Phase 3**: 根据使用反馈迭代优化

**并行化开发**：
- 基础设施、工作流引擎、内容处理器、检索引擎可并行开发
- 通过接口约定解耦依赖
- 每个模块独立测试

#### 原则4: 本地优先，数据主权

**理念**: 个人知识应该完全掌控在自己手中

**实践**：
- 所有数据本地存储（PostgreSQL + 文件系统）
- API 调用仅用于 AI 处理（不传输敏感数据）
- 支持完整数据导出（Markdown + JSON）
- 未来可扩展云端备份（加密）
