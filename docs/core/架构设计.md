## 总体架构

### 核心理念

工作流驱动 + 插件化处理 + 灵活深度

**关键洞察**: 不同内容类型的处理深度完全不同，不应强行用统一的层次结构

### 架构图

```
┌──────────────────────────────────────────────────────────────┐
│                      用户交互层                               │
│  ──────────────────────────────────────────────────────      │
│  • Slash Commands (/kb:archive-url, /kb:search)             │
│  • Rich Console 界面（进度、确认、结果展示）                  │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│                   工作流编排引擎                               │
│  ──────────────────────────────────────────────────────      │
│  • 解析 Slash Command → 加载对应的工作流配置 (YAML)         │
│  • 根据内容类型路由到不同的处理插件                           │
│  • 协调 Claude Code 与处理器的协作                           │
│  • 进度追踪、日志记录、错误处理                               │
└──────────────────────────────────────────────────────────────┘
                            ↓
        ┌───────────────────┴────────────────────┐
        │                                        │
        ↓                                        ↓
┌─────────────────────┐              ┌─────────────────────┐
│  简单内容 Pipeline   │              │  复杂内容 Pipeline   │
│  (微信/知乎短文)     │              │  (B站视频/PDF书籍)   │
├─────────────────────┤              ├─────────────────────┤
│ 1. 抓取            │              │ 1. 下载/OCR        │
│ 2. 提取正文         │              │ 2. 转录/分章节      │
│ 3. 生成摘要+标签    │              │ 3. 深度分块        │
│ 4. 存储            │              │ 4. 评论/图表分析    │
│                    │              │ 5. 时间轴/知识图谱  │
│ (3-4 步骤)         │              │ 6. 向量化+索引     │
│                    │              │ 7. 存储            │
│                    │              │ (6-8 步骤)         │
└─────────────────────┘              └─────────────────────┘
        │                                        │
        └───────────────────┬────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│                    存储与检索层                                │
│  ──────────────────────────────────────────────────────      │
│  • PostgreSQL: 元数据、索引、向量（pgvector）                │
│  • 文件系统: Markdown 文档、附件                              │
│  • 智能检索: BM25 / 向量 / 混合 / 结构化（自动选择策略）      │
└──────────────────────────────────────────────────────────────┘
```

### 架构设计要点

#### 1. 工作流驱动，而非分层调用

- 每种内容类型是一个独立的处理 Pipeline
- Pipeline 的深度由内容复杂度决定，不是架构强制
- 工作流配置化（YAML），易于调整和扩展

#### 2. 插件化处理器

- 每个处理器是独立插件（微信处理器、B站处理器、PDF处理器等）
- 处理器可以自由组合所需的 AI 能力（摘要、向量化、分析等）
- 新增内容源只需添加新插件，不影响现有代码

#### 3. AI 能力作为工具库，而非单独一层

- LLM Service、Embedding Service 是工具函数库
- 各个处理器按需调用，不是必须经过某一层
- 避免过度抽象和无谓的层次穿透

#### 4. 轻量化存储

- 只有两个存储：PostgreSQL（结构化+向量）+ 文件系统（Markdown）
- 避免 Repository 模式的过度抽象
- 直接使用 SQL 和文件操作，简单高效

### 不同内容的处理深度对比

| 内容类型 | Pipeline 步骤 | 处理时间 | AI 调用 |
|---------|--------------|---------|---------|
| **微信短文** | 抓取 → 摘要 → 存储 | ~10秒 | 1-2次 |
| **知乎长文** | 抓取 → 摘要 → 关键词 → 向量化 → 存储 | ~30秒 | 3-4次 |
| **B站视频** | 下载 → 转录 → 分块 → 评论 → 时间轴 → 存储 | ~5分钟 | 10+次 |
| **PDF书籍** | OCR → 分章节 → 深度分析 → 知识图谱 → 存储 | ~10分钟 | 20+次 |

### 为什么不用传统分层架构？

**传统分层的问题**：
- ❌ 所有内容都要走相同的层次（6层太重）
- ❌ 短文本被迫经过不需要的层（如向量化层）
- ❌ 复杂内容被限制在固定层次中（无法扩展深度）
- ❌ 层与层之间的接口成为负担

**工作流驱动的优势**：
- ✅ 每种内容自定义处理流程
- ✅ 简单内容走简单流程（3步）
- ✅ 复杂内容走复杂流程（8步）
- ✅ 灵活性高，易于调整和优化

## 目录结构设计

### 项目目录结构

```
personal-knowledge-vault/
├── .claude/                      # Claude Code 配置中心
│   ├── commands/                 # Slash Commands 定义
│   ├── prompts/                  # AI Prompt 模板库
│   └── workflows/                # 工作流编排配置
│
├── docs/                         # 知识内容存储（Markdown + 附件）
│   ├── books/                   # 书籍
│   ├── web-archives/            # 网页归档
│   └── experiences/             # 个人经历
│
├── src/                          # 源代码
│   ├── agents/                   # AI Agent 核心
│   ├── core/                     # 基础设施（存储、RAG、LLM）
│   ├── api/                      # API 接口（未来）
│   └── cli/                      # 命令行工具
│
├── config/                       # 配置文件
├── tests/                        # 测试
└── scripts/                      # 脚本工具
```

### 设计考量

- **`.claude/`**: 将 AI 工作流配置集中管理
- **`docs/`**: 内容与代码分离，便于 Git 管理和备份
- **`src/`**: 模块化分层，每个模块职责清晰

## 数据规范

### Markdown Front Matter 设计

本系统使用 YAML Front Matter 作为 Markdown 文档的元数据存储标准。

**核心理念**：
- **Markdown 为主，PostgreSQL 为辅** - 数据主权在文件中
- **人工友好** - 可直接在编辑器中查看和修改
- **工具兼容** - 支持 Obsidian、VSCode、Typora 等
- **版本控制** - 元数据和内容一起进行 Git 管理

**详细规范请参阅**: [数据规范文档](./数据规范.md)

内容包括：
- 完整的 YAML 字段标准（15个字段）
- 双重存储策略（Markdown + PostgreSQL）
- 同步机制（写入流程、读取流程、手动编辑同步）
- 文件命名规范
- 目录结构规范

## 双 Git 仓库策略

### 设计理念

代码架构与知识内容分离管理

### 实现方案

嵌套独立仓库

```
personal-knowledge-vault/          # 主仓库（代码+配置）
├── .git/                         # 主仓库 Git
├── .gitignore                    # 忽略 docs/ 目录
│
├── docs/                         # 独立仓库（知识内容）
│   ├── .git/                     # docs 自己的 Git
│   └── .gitignore                # 内容仓库的忽略规则
│
└── [其他代码目录...]
```

### 配置方法

**主仓库 `.gitignore`**:
```gitignore
# 忽略知识内容目录（独立仓库）
docs/

# 其他标准忽略项
__pycache__/
*.pyc
.env
*.db
```

**docs 仓库 `.gitignore`**:
```gitignore
# 忽略大型附件（可选）
*.mp4
*.avi
*.zip

# 系统文件
.DS_Store
Thumbs.db
```

### 核心优势

#### 1. 隐私分离
- 代码仓库可公开分享（开源知识库系统）
- 内容仓库保持私密（个人知识）

#### 2. 独立管理
- 不同的提交频率（代码周更新，内容日更新）
- 不同的备份策略（代码 GitHub，内容私有服务器）
- 独立的版本历史（代码重构不影响内容历史）

#### 3. 灵活部署
- 内容仓库可选择性推送到不同远程
- 支持多设备同步（仅同步内容仓库）
- 便于迁移和备份（两个仓库独立操作）

### 使用示例

```bash
# 主仓库操作（代码）
git add src/ .claude/
git commit -m "feat: 添加微信处理器"
git push origin main

# 内容仓库操作（知识）
cd docs/
git add web-archives/
git commit -m "归档: 添加5篇微信文章"
git push personal-backup main
```

## 数据流设计

### 示例: 归档一篇微信文章的完整流程

```
用户输入: /kb:archive-url https://mp.weixin.qq.com/xxx

   ↓ (1) Slash Command 路由

WorkflowEngine 加载 "web-to-markdown.yaml"

   ↓ (2) 工作流执行

步骤1: WebArchiver.detect_source(url)
   → 识别为微信文章

步骤2: WeChatProcessor.extract(url)
   → Playwright 抓取页面
   → Readability 提取正文
   → 转换为 Markdown 正文

步骤3: ContentAnalyzer.analyze(content)
   → 计算长度: 1500字 → 策略=keyword
   → LLM 生成一句话摘要（DeepSeek）
   → LLM 生成100字摘要（DeepSeek）
   → LLM 提取关键词（DeepSeek）
   → LLM 生成标签（DeepSeek）
   → 无需向量化（短文本）

步骤4: MarkdownGenerator.build()
   → 构建 YAML Front Matter:
      ---
      title: "文章标题"
      source_type: "wechat"
      tags: ["技术", "AI"]
      keywords: ["RAG", "检索"]
      abstract: "文章摘要..."
      summary_one_sentence: "一句话总结"
      summary_100_words: "100字摘要"
      search_strategy: "keyword"
      word_count: 1500
      ---
   → 拼接正文内容
   → 生成完整 Markdown 文件

步骤5: FileSystemStorage.save()
   → 保存到 docs/web-archives/wechat/文章标题.md
   → 计算文件哈希

步骤6: PostgreSQLStorage.sync()
   → 解析 YAML Front Matter
   → 提取关键字段存入数据库
   → 建立全文检索索引
   → （可选）生成并存储向量

步骤7: GitManager.commit()
   → 检查文件变化
   → Git add + commit（可选）

步骤8: 反馈用户
   → 显示摘要、标签
   → 展示文件路径：docs/web-archives/wechat/文章标题.md
   → 提示可编辑 YAML

   ↓ (3) 用户可选操作

用户可以:
- 立即搜索验证: /kb:search "关键词"
- 手动编辑 YAML: 在编辑器中打开文件，修改 tags/rating 等
- 建立关联: 在 YAML 的 related_docs 中添加链接
- 添加笔记: 在 YAML 的 notes 字段添加个人想法
```

### 关键设计点

1. **YAML 优先**: 元数据首先写入 YAML Front Matter，数据库是同步副本
2. **透明可控**: 每个步骤都有清晰的输入输出
3. **可中断**: 用户可以在任何节点暂停或调整
4. **可观测**: 实时进度反馈，用户了解发生了什么
5. **灵活路由**: 根据内容类型自动选择处理策略
6. **人工修正**: 用户可以直接编辑 Markdown 文件修改元数据
